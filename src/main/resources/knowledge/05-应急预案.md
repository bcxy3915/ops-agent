# 应急预案（Incident Response Plan）

> 文档元数据
> - 版本：v1.1
> - 适用环境：ops-agent 监控体系（服务、数据库、告警、诊断）
> - 分级标准：按影响面与恢复时限分级，与告警规则、值班升级路径联动
> - 参考来源：Google SRE 事件响应、PagerDuty Incident Response、ITIL Incident Management 分级实践

## 1. 事件分级（SEV 模型）

| 级别 | 定义 | 典型场景 | 首次响应 | 集结时限 | 恢复目标 | 升级时限 |
| --- | --- | --- | --- | --- | --- | --- |
| SEV0（P0） | 核心服务完全不可用 / 数据丢失 / 安全事件 | 数据库宕机且不可恢复、ops-agent 主服务崩溃、数据被删除 | ≤5 分钟 | ≤15 分钟 | ≤1 小时 | 立即升级至项目负责人 + 群内通报 |
| SEV1（P1） | 核心服务严重劣化，影响大部分用户 | 服务 DOWN、接口大面积 5xx、内存 OOM 持续 | ≤15 分钟 | ≤30 分钟 | ≤2 小时 | 15 分钟未解决 → 升级负责人 |
| SEV2（P2） | 部分功能受损，有替代方案 | 单个服务 DOWN（如 todo-service）、告警风暴、慢查询 | ≤30 分钟 | ≤60 分钟 | ≤4 小时 | 30 分钟未解决 → 升级 |
| SEV3（P3） | 非关键问题，无用户影响 | 告警阈值误报、日志堆积、监控指标异常 | ≤4 小时 | 当日 | 当日 | 4 小时未解决 → 记录并跟进 |
| SEV4（P4） | 低优先级优化项 | 文档更新、指标补充、体验优化 | 记录即可 | 排期 | 按排期 | 按排期处理 |

> 分级依据：参考 Google SRE 事件分级、ITIL 事件管理分级（P0-P3），并结合本系统实际规模简化。响应/恢复时限为建议默认值，可按 SLA 调整。

## 2. 应急响应流程

```
发现事件（告警触发 / 用户上报 / 巡检发现）
  │
  ▼
1. 确认：登录系统 → 查看告警事件、服务状态、指标
  │
  ▼
2. 定级：按上表判断 SEV 级别 → 启动对应响应
  │
  ▼
3. 响应：通知对应人员，建立应急组织（见 §3）
  │
  ▼
4. 处置：按《02-故障处理手册.md》执行，优先恢复服务
  │
  ▼
5. 升级：超过升级时限未解决 → 按升级路径上报
  │
  ▼
6. 复盘：恢复后 48 小时内完成故障复盘，回填《09-故障案例模板.md》
```

## 3. 应急组织（Incident Command）

| 角色 | 职责 |
| --- | --- |
| 故障指挥官（IC） | 事件总负责人，判断定级、指挥处置、对外沟通 |
| 操作执行人 | 按 Runbook 执行处置操作（值班人员） |
| 沟通联络人 | 群内通报、对接服务负责人与升级对象 |
| 记录员 | 记录时间线、操作与观察（用于复盘） |

- 小型事件（SEV2/SEV3）：IC 由值班人员担任，可一人兼多职
- 大型事件（SEV0/SEV1）：IC 由负责人担任，明确分工

## 4. 通知与升级路径

```
告警触发
  ├─ 值班人员收到通知（渠道：notification_channel 配置）
  │
  ├─ 一线：值班人员 15 分钟内未响应 / 未解决 → 升级服务负责人（ops_service.owner）
  │
  ├─ 二线：服务负责人 15 分钟内未解决 → 升级项目组 / 运维负责人（二线技术专家）
  │
  ├─ 三线：二线 15 分钟内未解决 → 项目负责人 / 技术负责人（三线，重大决策）
  │
  └─ SEV0/SEV1 → 立即升级 + 群内通报（值班、负责人、项目组）
```

- **升级原则**：响应超时即升级（P0 超 5 分钟、P1 超 15 分钟），不等待处置失败才升级
- **值班人员**：当日值班表人员（见《07-值班与响应流程.md》）
- **服务负责人**：`ops_service.owner` 字段（每个服务必须配置）
- **通知渠道**：告警通过配置的渠道（如邮件/IM）发送，见 `notification_channel` 表

## 5. 关键场景应急预案

### 5.1 数据库（ops-postgres）故障
1. **症状**：ops-agent 连接失败、健康检查 DB DOWN、告警触发
2. **快速处置**：
   ```powershell
   docker ps --filter "name=ops-postgres"        # 容器是否存活
   docker logs ops-postgres --tail 100           # 查看日志
   docker restart ops-postgres                   # 简单故障先重启
   ```
3. **数据恢复**（容器损坏时）：
   ```powershell
   # 使用备份恢复（见《04-部署手册.md》第 3.4 节）
   docker cp D:\backup\opsdb_最近.dump ops-postgres:/tmp/opsdb.dump
   docker exec ops-postgres pg_restore -U postgres -d opsdb -c /tmp/opsdb.dump
   ```
4. **升级**：SEV0/SEV1，立即通知负责人
5. **预防**：定期备份（每日）、数据卷持久化、磁盘告警

### 5.2 核心服务（ops-agent）故障
1. **症状**：前端无法访问、API 无响应、服务 DOWN
2. **快速处置**：
   ```powershell
   # 检查进程与端口
   Get-Process | Where-Object { $_.ProcessName -like '*java*' }
   netstat -ano | findstr :8080
   # 重启
   cd "D:\my projects\java ai\ops-agent\ops-ai-agent"
   .\mvnw spring-boot:run -Dspring-boot.run.profiles=local
   ```
3. **升级**：SEV0/SEV1，立即升级
4. **预防**：健康检查、自动重启、日志留存

### 5.3 被监控服务（如 todo-service）DOWN
1. **症状**：告警 `todo-service DOWN`、指标无法采集
2. **快速处置**：按《02-故障处理手册.md》第 1 节排查重启
3. **升级**：SEV2，30 分钟未解决升级负责人

### 5.4 告警风暴
1. **症状**：短时间内大量同类告警
2. **快速处置**：调整告警规则（提高阈值 / 增加 duration / 设置 silence），见《02-故障处理手册.md》第 6 节
3. **升级**：SEV2（影响告警有效性）
4. **预防**：默认阈值合理、静默期配置、聚合告警

### 5.5 LLM / 诊断链路故障
1. **症状**：diagnosis_record FAILED、问答异常
2. **快速处置**：检查模型配置与 API Key，重试诊断
3. **升级**：SEV3（不影响核心监控），4 小时未解决记录跟进
4. **预防**：诊断环节独立容错（诊断失败不影响告警与通知）

## 6. 事件期间沟通规范

- **群内通报**：SEV0/SEV1 事件在项目群通报：事件级别、影响范围、当前状态、预计恢复时间
- **更新频率**：SEV0/SEV1 每 15 分钟更新一次状态，SEV2 每 30 分钟
- **恢复宣告**：功能恢复后发布恢复通告，并在 48 小时内完成复盘

## 7. 复盘要求

1. 每次 SEV2 及以上事件必须复盘
2. 复盘模板见《09-故障案例模板.md》，与 diagnosis_record / failure_snapshot 联动
3. 复盘输出：根因、处置过程、改进项、责任人、时间线
4. 改进项进入变更管理流程（《06-变更管理规范.md》）
5. 复盘时机：恢复后 24-48 小时内召开（记忆新鲜，参考 Google SRE Postmortem 实践）
