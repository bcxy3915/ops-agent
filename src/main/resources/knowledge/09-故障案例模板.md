# 故障案例模板（Postmortem Template）

> 文档元数据
> - 版本：v1.0
> - 用途：故障复盘标准模板，沉淀为可检索的运维案例（进入知识库，供后续诊断与问答参考）
> - 联动：与 `failure_snapshot`（故障快照）、`diagnosis_record`（LLM 诊断记录）数据表对接，自动带入结构化字段

## 1. 模板结构

```

## 1. 事件概览（自动生成）
| 字段 | 值 | 来源 |
| --- | --- | --- |
| 事件编号 | {alert_event_id} | alert_event 表 |
| 服务 | {service} | failure_snapshot |
| 触发规则 | {rule_name} | failure_snapshot |
| 监控指标 | {metric} | failure_snapshot |
| 触发值 | {当前值 vs 阈值} | alert_event |
| 事件级别 | SEV{0-4} | 按应急预案分级 |
| 开始时间 | {created_at} | failure_snapshot |

## 5. 根因确认（人工复盘）
- **最终根因**：
- **根因分类**：代码缺陷 / 配置错误 / 资源不足 / 外部依赖 / 变更引入 / 数据问题 / 其他
- **为什么 LLM 诊断与实际一致/不一致**：

## 6. 影响评估
- 影响时长：{HH:mm - HH:mm}
- 影响范围：{服务/功能/用户}
- 数据影响：{无/部分/恢复情况}

## 7. 改进措施（Action Items）
| 编号 | 改进项 | 负责人 | 截止时间 | 状态 |

- **教训**：
- **是否更新《02-故障处理手册.md》**：{是/否，更新内容}
```

## 2. 与系统数据表的字段映射

| 模板字段 | 数据来源 |
| --- | --- |
| 事件编号 / 触发值 / 事件时间 | `alert_event`（id, current_value, created_at 等） |
| 服务 / 规则 / 指标 / 快照 | `failure_snapshot`（service, rule_name, metric, snapshot_json, created_at） |
| 根因 / 证据 / 建议 | `diagnosis_record`（root_cause, evidence JSON, suggestions JSON） |
| 规则配置 | `alert_rule`（name, metric, operator, threshold, duration_seconds） |

## 3. 案例沉淀流程

```
告警触发（alert_event）
  │
  ▼
自动抓快照（failure_snapshot）
  │
  ▼
自动 LLM 诊断（diagnosis_record: root_cause/evidence/suggestions）
  │
  ▼
人工处置 → 恢复
  │
  ▼
48 小时内复盘 → 按本模板填写（自动字段 + 人工字段）
  │
  ▼
改进项落地（变更管理）→ 经验回填知识库（更新手册/阈值/规则）
  │
  ▼
案例入库 → 成为后续故障检索与诊断的参考
```

## 4. 复盘质量要求

1. **事实优先**：自动字段不改写，人工字段基于事实
2. **根因不止一层**：区分直接原因与深层原因（如「OOM」vs「代码缓存无上限」）
3. **改进可执行**：每条改进项有负责人与截止时间
4. **48 小时原则**：SEV2 及以上事件 48 小时内完成复盘，防止遗忘
5. **闭环验证**：改进项落地后验证是否解决，未闭环的持续跟踪

## 5. 复盘方法论（参考 Google SRE Blameless Postmortem）

### 5.1 Blameless 无指责文化
- 聚焦系统和流程问题，**不追责个人**；假设所有人都在当时信息下做了最佳判断
- 复盘目的是防止复发，不是追责

### 5.2 5 Whys 根因分析法
逐层追问「为什么」直到找到根本原因：
```
症状：todo-service DOWN
Why1：健康检查失败
Why2：进程未运行
Why3：被手动停止后未重启
Why4：停机操作没有通知值班/没有自动拉起
Why5：缺少进程守护/自动重启机制 ← 根本原因
```
- 区分：直接原因、促成因素（流程缺口、技术缺口、文化因素、环境因素）、根本原因
- 每条行动项必须有：Why（防复发原理）、Who（负责人）、When（截止日期）、How to verify（验证方式）

### 5.3 行动项分级
| 优先级 | 定义 | 示例 |
| --- | --- | --- |
| P1 | 导致本次故障的直接修复 | 重启脚本自动拉起 |
| P2 | 防止同类复发的改进 | 增加进程守护 |
| P3 | 优化项 | 交接流程优化 |

## 5. 案例示例（基于真实系统字段）

```
# 故障案例：todo-service - 服务不可用（2026-10-18）

## 1. 事件概览
| 事件编号 | ev_20261018_001 |
| 服务 | todo-service |
| 触发规则 | todo-service-health-check |
| 监控指标 | service.health.status |
| 触发值 | DOWN |
| 事件级别 | SEV2 |
| 开始时间 | 2026-10-18 09:15 |

## 2. 故障快照
- 服务状态：DOWN
- 健康检查超时：连接被拒绝
- 端口 8081 无监听

## 3. LLM 诊断
- 根因：todo-service 进程未运行
- 证据：端口 8081 无监听、进程列表无 java 进程
- 建议：检查启动日志，重启服务

## 4. 处置过程
| 09:16 | 确认告警 | 值班 | - |
| 09:20 | 查看端口与进程 | 值班 | 确认进程未运行 |
| 09:25 | 重启 todo-service | 值班 | 恢复 UP |
| 09:30 | 验证健康检查 | 值班 | 恢复 |

## 5. 根因确认
- 最终根因：手动停止后未重启
- 分类：人为操作 / 外部依赖

## 6. 影响评估
- 影响时长：09:15 - 09:25（10 分钟）
- 影响范围：todo-service 示例服务
- 数据影响：无

## 7. 改进措施
| A1 | 服务注册负责人 | 项目组 | 2026-10-25 | 待办 |
| A2 | 增加服务自动重启机制 | 项目组 | 2026-11-01 | 待办 |

## 8. 经验教训
- 教训：演示环境服务停止后需及时恢复
- 更新手册：否
- 更新规则：否
```
