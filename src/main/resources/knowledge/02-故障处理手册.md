# 故障处理手册（Runbook）

> 文档元数据
> - 版本：v1.0
> - 适用环境：Windows（本地开发/部署）+ Docker（PostgreSQL 容器化）
> - 编写原则：每条处理步骤均为当前环境可执行的真实命令；通用经验保留并标注来源
> - 更新策略：每次故障复盘后回填，新增场景需标注验证来源

## 0. Runbook 使用方法

- **先看症状**：按故障类别定位到对应场景（第 1-8 节）
- **快速诊断**：每节先执行「快速检查」，确认影响范围
- **分级处理**：涉及数据、不可恢复、影响面大的操作，遵循第 9 节优先级
- **验证来源**：每条命令后标注「已验证」或「参考来源」

### 0.1 Playbook 标准结构（参考 Google SRE / 腾讯云）

每个故障场景按以下标准结构编写（本手册第 1-8 节均遵循）：

| 要素 | 说明 |
| --- | --- |
| 故障现象（Symptom） | 告警触发条件、用户可见表现、日志特征 |
| 影响范围（Impact） | 受影响服务、影响程度、严重等级 |
| 可能根因（Root Cause） | 按概率排序的根因假设 |
| 排查步骤（Diagnosis Steps） | 先看监控 → 再查日志 → 最后复现，按优先级排列 |
| 处理方案（Mitigation） | 紧急止血 → 临时恢复 → 永久修复（含回滚/扩容/重启） |
| 预防措施（Prevention） | 监控补全、容量规划、架构改进 |

**Playbook 原则**：可执行（具体到命令）、可验证（每步有预期结果）、有时间限制（排查超时升级）、定期演练验证。
必备要素：故障指挥官（IC）角色、沟通渠道、升级路径、回滚预案。

> 参考来源：[腾讯云 SRE 故障处理手册](https://cloud.tencent.com/developer/article/2488556)、[Google SRE Book - Handling Incidents](https://sre.google/sre-book/handling-incidents/)

## 1. 服务不可用 / 健康检查失败

### 症状
- 服务状态 DOWN / DEGRADED，`/actuator/health` 返回非 UP
- 告警规则触发：`service status = DOWN`

### 快速检查
```powershell
# 1) 本地服务进程是否存在（以 todo-service 为例）
Get-Process | Where-Object { $_.ProcessName -like '*todo*' -or $_.ProcessName -like '*java*' }

# 2) 直接探测健康端点
Invoke-WebRequest -Uri http://localhost:8081/actuator/health -UseBasicParsing | Select-Object StatusCode

# 3) 数据库（ops-agent 依赖 PostgreSQL）
docker ps --filter "name=ops-postgres"
```

### 排查步骤
1. **进程级**：进程不存在 → 启动失败或已崩溃，查看日志（第 1.1 节）
2. **端口级**：进程存在但连接被拒 → 端口占用/绑定失败：
   ```powershell
   netstat -ano | findstr :8081
   ```
3. **应用级**：端口可连但 health 非 UP → 检查健康详情：
   ```powershell
   (Invoke-WebRequest -Uri http://localhost:8081/actuator/health -UseBasicParsing).Content
   ```
   `show-details: always` 时可直接看到磁盘/数据库等组件状态。
4. **网络级**：跨服务访问失败 → 防火墙/容器网络：
   ```powershell
   docker network ls
   docker inspect ops-postgres --format '{{json .NetworkSettings.Networks}}'
   ```

### 处理方案
- 本地服务：重启
  ```powershell
  cd "D:\my projects\java ai\ops-agent\todo-service"
  .\mvnw spring-boot:run   # 前台启动观察日志
  ```
- 容器服务：重启容器
  ```powershell
  docker restart ops-postgres
  ```
- 自动恢复：健康检查周期后状态自动更新；持续 DOWN 走告警升级（第 10 节）

### 验证
- `Invoke-WebRequest http://localhost:8081/actuator/health` 返回 `{"status":"UP"}`
- ops-agent 侧状态恢复 UP，告警解除

> 验证来源：健康检查端点行为为 Spring Boot Actuator 官方定义；`show-details` 配置来自 todo-service 真实 application.yml。

## 2. CPU 使用率过高

### 症状
- 告警触发：`system.cpu.usage` / `process.cpu.usage` 超过阈值（如 85% 持续 5 分钟）
- 服务响应变慢，接口耗时上升

### 快速检查
```powershell
# Windows 查看 CPU 占用 Top 进程
Get-Process | Sort-Object CPU -Descending | Select-Object -First 10 Name, Id, CPU, WorkingSet64

# 当前系统 CPU 利用率
Get-CimInstance Win32_Processor | Select-Object LoadPercentage
```

### 排查步骤
1. 确认是哪个进程：`todo-service` 高 → 应用内问题；`postgres` 高 → 数据库问题；系统整体高 → 机器问题
2. Java 应用内定位（todo-service / ops-agent）：
   - 通过 Actuator 指标查看 JVM CPU：
     ```
     GET /actuator/metrics/system.cpu.usage
     GET /actuator/metrics/process.cpu.usage
     ```
   - 线程转储（生产建议保留，此处为开发演示）：
     ```powershell
     jcmd <pid> Thread.print > thread_dump.txt
     ```
3. 数据库 CPU 高：
   ```powershell
   docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT pid, state, query FROM pg_stat_activity WHERE state='active';"
   ```

### 处理方案
- 死循环/异常请求：定位线程 → 重启服务（先恢复，再复盘根因）
- 慢 SQL 打满 CPU：见第 5 节
- 资源不足：评估扩容或优化查询

### 验证
- CPU 回落到阈值以下并持续稳定
- 接口耗时恢复正常

> 阈值参考：CPU 使用率 70%-85% 为常见告警区间（阿里云 ARMS 默认 CPU 使用率 P3 70%、P4 85%）；具体见《03-指标字典.md》阈值表。

## 3. 内存泄漏 / OOM

### 症状
- 告警触发：`jvm.memory.used` 接近堆上限，`jvm.memory.max` 持续高位
- 日志出现 `OutOfMemoryError`，服务重启或卡死

### 快速检查
```powershell
# JVM 堆使用情况（通过 Actuator）
# GET /actuator/metrics/jvm.memory.used
# GET /actuator/metrics/jvm.memory.max

# Windows 内存占用 Top
Get-Process | Sort-Object WorkingSet64 -Descending | Select-Object -First 10 Name, Id, WorkingSet64
```

### 排查步骤
1. 确认堆内存趋势：连续采样 `jvm.memory.used`，若只升不降 → 疑似泄漏
2. 区分堆内/堆外：`jvm.memory.used` 按 area=heap / area=nonheap 分别查看
3. GC 状态：查看 `jvm.gc.pause` 与 GC 次数（FullGC 频繁通常是内存压力信号）

### 处理方案
1. **立即止血**：重启服务（若配置了 JVM 参数，可保留 `-Xmx` 限制防占满宿主机）
2. **临时缓解**：扩容内存 / 调整堆上限（需重启生效）
3. **根治**：复盘代码（缓存无限增长、大对象未释放、连接未关闭等）

### 验证
- 重启后堆内存曲线平稳
- `jvm.memory.used` 与 GC 次数回到基线

> 验证来源：JVM 内存指标为 Spring Boot Actuator 标准指标（jvm.memory.* / jvm.gc.*）；FullGC 频繁视为风险（阿里云默认 FullGC 3 次/5 分钟告警）。

## 4. 磁盘空间不足

### 症状
- 日志写入失败，`/actuator/health` 中 diskSpace 组件 DOWN
- Docker 容器启动报 `no space left on device`

### 快速检查
```powershell
Get-PSDrive C | Select-Object Used, Free

# Docker 数据卷占用
docker system df
```

### 排查步骤
1. 定位占用大头：应用日志目录、Docker 数据目录（`C:\ProgramData\Docker`）、临时文件
2. 日志文件清理：
   ```powershell
   # 查看日志目录占用
   Get-ChildItem "D:\my projects\java ai\ops-agent" -Recurse -Filter *.log | Measure-Object -Property Length -Sum
   ```
3. Docker 垃圾清理（先确认无需要的镜像/容器）：
   ```powershell
   docker system prune   # 谨慎：删除停止容器、未用网络、悬空镜像
   docker builder prune  # 构建缓存
   ```

### 处理方案
- 应用启用日志滚动：`logback` 配置 `maxFileSize`/`maxHistory`（生产必须）
- Docker 日志限制：compose 中配置 `logging: driver: json-file, options: {max-size, max-file}`（见《04-部署手册.md》）
- 定期巡检 + 磁盘告警规则（`disk.free` 阈值）

### 验证
- 磁盘剩余空间回升，health 中 diskSpace 恢复 UP

> 验证来源：Docker 日志限制与 `docker system prune` 为 Docker 官方命令；磁盘告警为通用 SRE 实践。

## 5. 数据库连接 / 慢查询问题

### 症状
- 应用报连接池耗尽：`Connection is not available, request timed out`
- 接口耗时上升，数据库 CPU 高
- 健康检查组件（DB）DOWN

### 快速检查
```powershell
docker exec ops-postgres psql -U postgres -d opsdb -c "\conninfo"

# 活跃连接与等待
docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT count(*) AS active FROM pg_stat_activity WHERE state='active';"

# 慢查询（运行超过 5 秒的）
docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT pid, now()-query_start AS duration, query FROM pg_stat_activity WHERE state='active' AND now()-query_start > interval '5 seconds';"
```

### 排查步骤
1. 连接数是否打满：连接池指标（ops-agent 的 HikariCP：`hikaricp.connections.active` / `hikaricp.connections.pending`）
2. 慢查询来源：`pg_stat_activity` 中的长事务与长查询
3. 锁等待：`pg_locks` 与 `pg_stat_activity.wait_event`

### 处理方案
- 慢查询：优化 SQL / 加索引 / 拆大事务
- 连接池打满：调大 `maximum-pool-size`（需确认数据库 max_connections），或定位未释放连接
- 紧急终止长事务（谨慎，先确认）：
  ```powershell
  docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT pg_terminate_backend(<pid>);"
  ```

### 验证
- `hikaricp.connections.active` 回落，pending 为 0
- 接口耗时恢复基线

> 验证来源：HikariCP 指标为 Spring Boot Actuator 标准指标（hikaricp.*）；pg_stat_activity 为 PostgreSQL 官方视图。

## 6. 告警风暴 / 通知异常

### 症状
- 同一规则短时间重复触发大量告警
- 告警渠道（通知）未送达或延迟

### 快速检查
```powershell
# 查看最近告警事件（表：alert_event）
docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT * FROM alert_event ORDER BY created_at DESC LIMIT 20;"

# 查看通知记录（表：notification_record）
docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT * FROM notification_record ORDER BY created_at DESC LIMIT 20;"
```

### 排查步骤
1. 是否配置了 `silence_seconds`（静默期）：无静默 → 每次评估都触发 → 风暴
2. 阈值是否过敏感：结合《03-指标字典.md》复核默认阈值
3. 通知渠道配置是否正确：检查 `notification_channel` 表
4. 通知失败原因：查看 notification_record 中的状态与错误信息

### 处理方案
- 短期止血：调整告警规则（提高阈值 / 增加 duration_seconds / 设置 silence_seconds）
- 通知渠道故障：修复渠道配置，重发测试消息
- 复盘：检查触发场景是真实故障还是误报

### 验证
- 告警频率回到合理区间，通知送达成功

> 验证来源：duration_seconds / silence_seconds 为本系统 alert_rule 真实字段；告警静默为通用监控最佳实践。

## 7. LLM 诊断失败 / 知识库问答不准

### 症状
- `diagnosis_record` 状态 FAILED，`error_message` 有值
- 对话问答答非所问或编造（幻觉）

### 快速检查
```powershell
docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT id, status, error_message FROM diagnosis_record ORDER BY created_at DESC LIMIT 10;"

# 向量库是否有文档
docker exec ops-postgres psql -U postgres -d opsdb -c "SELECT COUNT(*) AS doc_count FROM vector_store;"
```

### 排查步骤
1. 诊断失败：查看 error_message（模型调用超时 / Token 超限 / 向量检索失败 / 快照缺失）
2. 问答不准：
   - 知识库未加载（vector_store 空）→ 检查 `src/main/resources/knowledge/` 是否有 md/pdf
   - 检索质量差 → 确认文档内容与运维场景匹配（本批官方手册已按此要求编写）
   - 服务相关查询 → 确认服务已注册（否则触发"服务未注册"兜底话术）

### 处理方案
- 模型调用失败：检查 LLM API Key / 模型配置（AiConfig），重试
- 知识库缺失：将官方手册放入 knowledge 目录，重启触发 DocumentLoader 增量加载
- 检索不准：优化文档结构（标题清晰、要点分段、术语统一）

### 验证
- diagnosis_record 状态 SUCCESS
- 问答可正确引用知识库内容并给出依据

> 验证来源：DocumentLoader 启动增量加载逻辑（按 source 去重）为系统真实实现；检索链路（向量+BM25+RRF+Reranker）为 HybridRetriever 真实实现。

## 8. 部署 / 配置类问题

### 症状
- 服务启动失败，端口被占
- 配置不生效

### 快速检查
```powershell
# 端口占用
netstat -ano | findstr :8080
netstat -ano | findstr :8081
netstat -ano | findstr :5433

# Docker 容器状态
docker ps -a
```

### 排查步骤
1. 端口冲突：`8080`（ops-agent）/ `8081`（todo-service）/ `5433`（postgres）被占用
2. 配置加载：检查 `application.yml` / `application-local.yml` 的 profile 是否生效
3. 依赖未起：ops-agent 启动需 PostgreSQL 就绪（docker compose 中 `depends_on` + healthcheck）

### 处理方案
- 端口冲突：结束占用进程或改端口配置
  ```powershell
  # 找到 PID 后（谨慎，确认是占用进程）
  taskkill /PID <pid> /F
  ```
- 数据库未就绪：`docker compose up -d` 后等待健康检查通过再启动应用
- 配置不生效：确认 profile 与配置文件位置，重启应用

### 验证
- 端口监听正常，服务 health UP
- 功能接口可调用

> 验证来源：docker-compose.yml 真实配置（postgres 5433、healthcheck）；端口 8080/8081 为项目真实配置。

## 9. 故障处理优先级与通用原则

1. **先恢复，后复盘**：优先止血（重启/隔离/回滚），不纠结根因
2. **单点改动**：一次只做一个操作，验证效果后再继续
3. **命令确认**：`docker system prune`、`taskkill /F`、`pg_terminate_backend` 等破坏性命令执行前先确认影响面
4. **记录时间线**：从告警触发到恢复的每个动作记录时间（用于复盘与《故障案例模板.md》）
5. **升级规则**：P1 故障 15 分钟未恢复 → 升级负责人；P0 故障立即升级（见《05-应急预案.md》）

## 10. 告警升级路径

```
告警触发 → 值班人员处理（15 分钟内响应）
   ├─ 未解决/超时 → 服务负责人（owner）
   ├─ 服务负责人无法解决 → 项目组 / 运维负责人
   └─ P0 级别 → 立即升级 + 群内通报
```

> 升级路径与《05-应急预案.md》《07-值班与响应流程.md》保持一致。
