# 服务清单（Service Catalog）

> 文档元数据
> - 版本：v1.0
> - 维护方式：与 `ops_service` 表联动，本页为登记规范 + 当前真实服务快照
> - 更新策略：服务注册/变更后同步更新本页
> - 适用范围：ops-agent 监控体系内的全部被监控服务

## 1. 服务资产登记字段规范

服务注册后写入 `ops_service` 表，字段说明如下（与系统实现保持一致）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | VARCHAR(32) | 是 | 服务唯一 ID |
| name | VARCHAR(128) | 是 | 服务名（唯一），聊天中直接使用，如 `todo-service` |
| base_url | VARCHAR(255) | 是 | 服务基础地址，健康检查与指标采集的根地址，如 `http://localhost:8081` |
| health_path | VARCHAR(128) | 否 | 健康检查路径，默认 `/actuator/health` |
| metrics_path | VARCHAR(128) | 否 | 指标采集路径，默认 `/actuator/metrics` |
| owner | VARCHAR(64) | 否 | 负责人（团队/个人），用于告警升级和通知 |
| env | VARCHAR(32) | 否 | 环境标识，默认 `dev`，取值建议 `dev/test/prod` |
| tags | JSONB | 否 | 扩展标签，如 `{"layer":"app","critical":"true"}` |
| auth_token | VARCHAR(255) | 否 | 采集端点鉴权 Token（敏感，建议由凭证管理） |
| status | VARCHAR(16) | 否 | 最近健康状态：UNKNOWN / UP / DOWN / DEGRADED |
| last_checked_at | TIMESTAMP | 否 | 最近健康检查时间 |
| registered_at / updated_at | TIMESTAMP | 否 | 注册/更新时间 |

**注册方式**：调用服务注册 API（`POST /api/services`，含 baseUrl、healthPath、metricsPath、owner 等），系统会周期健康检查并更新状态。

## 2. 当前真实服务清单

> 本清单基于当前环境真实部署情况整理；新服务注册后应及时更新本节。

### 2.1 ops-agent（本系统，监控端）
- **职责**：运维智能体主服务。提供服务注册、指标采集、健康巡检、告警评估、故障快照、LLM 智能诊断、通知、RAG 问答 API。
- **地址**：`http://localhost:8080`
- **健康端点**：`/actuator/health`
- **指标端点**：`/actuator/metrics`
- **技术栈**：Spring Boot 3.4.13 / Java 21 / MyBatis-Plus / Spring AI 1.1.0 / pgvector
- **依赖**：PostgreSQL（pgvector，端口 5433）
- **负责人**：运维智能体项目组
- **关键接口**：
  - `POST /api/auth/login` 登录
  - `POST /api/services` 注册服务
  - `GET /api/metrics/history?service=&metric=` 指标历史
  - `GET /api/alerts/rules` 告警规则
  - `POST /api/diagnoses/snapshot/{id}` 触发诊断
  - `POST /api/chat` 运维问答（RAG + 工具）

### 2.2 todo-service（被监控示例服务）
- **职责**：示例业务服务（待办事项），用于演示监控、告警、诊断闭环。
- **地址**：`http://localhost:8081`
- **健康端点**：`/actuator/health`
- **指标端点**：`/actuator/metrics`
- **暴露端点**：`health,metrics,info`，健康详情 `show-details: always`
- **技术栈**：Spring Boot 4.1.1 / Java 21
- **依赖**：无外部依赖（演示用）
- **负责人**：示例服务负责人（待定）

### 2.3 ops-agent-frontend（前端）
- **职责**：运维智能体一体化工作台（对话默认首页 + 服务管理/指标监控/审计日志/用户管理侧栏）。
- **地址**：本地开发 `http://localhost:5173`（Vite），生产构建产物 `dist/`
- **技术栈**：Vue 3 + Element Plus + Pinia + Vue Router + ECharts
- **依赖**：ops-agent 后端 API
- **负责人**：运维智能体项目组

### 2.4 ops-postgres（数据库）
- **职责**：系统元数据与向量存储（pgvector），承载 13 张表。
- **地址**：`localhost:5433`（容器映射），容器名 `ops-postgres`
- **镜像**：`pgvector/pgvector:pg16`
- **负责人**：运维智能体项目组

## 3. 服务依赖关系

```
ops-agent-frontend ──▶ ops-agent (8080)
                          │
                          ├──▶ PostgreSQL ops-postgres (5433)  [pgvector 向量/业务表]
                          │
                          └──▶ todo-service (8081)  [被监控：健康检查 + 指标采集]
```

## 4. 服务与告警规则关联

- 告警规则（`alert_rule` 表）通过 `service` 字段关联服务：`alert_rule.service = ops_service.name`
- 指标采样（`metric_sample` 表）通过 `service` 字段标识数据来源
- 故障快照（`failure_snapshot`）、诊断记录（`diagnosis_record`）均以 `service` 关联
- 告警事件（`alert_event`）记录触发事件的服务、规则、当前值

## 5. 服务清单最佳实践（参考 CMDB 规范）

> 参考来源：[阿里云开发者社区 - CMDB 最佳实践](https://developer.aliyun.com/article/1762055)

### 5.1 CMDB 分层模型
| 层 | 内容 | 示例 |
| --- | --- | --- |
| 业务层 | 业务系统/应用 | 待办业务系统 |
| 应用层 | 服务/模块 | todo-service、ops-agent |
| 资源层 | 主机/容器/中间件 | ops-postgres、Docker 容器 |

三层通过服务名/标签关联：服务清单必须与监控、告警、日志系统打通。

### 5.2 字段标准化建议
- 每个服务必须有**唯一标识**（name 唯一，当前实现即如此）
- 建议补充：服务等级（Tier1/Tier2/Tier3）、SLA 等级、RTO/RPO、代码仓库地址、部署方式、数据存储位置、依赖服务（上游/下游）
- 字段标准化，避免同义不同名（如 owner/负责人 统一为一个字段）

### 5.3 维护机制
- **自动发现优先于人工录入**：通过健康检查/注册机制自动登记，减少人为遗漏
- **定期审计**：每季度核对服务清单与实际运行服务一致性，清理已下线服务
- **依赖图**：维护服务依赖关系（谁调用谁）、运行时拓扑、数据流向，便于故障影响评估

## 6. 服务生命周期与维护规范

1. **注册**：新服务上线 → 调注册 API → 等待首次健康检查 → 确认状态 UP
2. **更新**：端口/地址/负责人变更 → 调更新 API → 系统自动重新健康检查
3. **下线**：服务下线 → 注销服务 → 归档历史指标（保留查询）
4. **命名规范**：服务名使用小写连字符（如 `todo-service`），与聊天识别一致
5. **责任人**：每个服务必须填写 owner，告警通知与升级依赖该字段
6. **等级标注**：核心服务标注 Tier1，告警升级路径优先保障
