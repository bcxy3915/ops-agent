一、死锁的成因与 InnoDB 锁基础

死锁的定义是两个或多个事务各自持有一部分资源并互相等待对方持有的资源，等待关系形成环且任何一方都无法继续推进。InnoDB 的锁体系是理解死锁成因的起点，而理解锁体系的第一件事是接受一个反直觉的事实：InnoDB 的行锁不是加在行上而是加在索引记录上的。当一条 UPDATE 的 WHERE 条件能命中唯一索引的等值查询时，加的是记录锁 Record Lock，只锁命中那一行；当条件是范围查询、非唯一索引等值或没有合适索引可用时，加的就不只是记录，而是区间锁 Gap Lock 与临键锁 Next-Key Lock，锁定的是索引上的一段区间而不仅仅是命中的行。这个设计的目标是防止幻读，在可重复读隔离级别下保证同一事务内两次相同范围查询看到相同的行集合，但防幻读的代价是锁的范围被放大，死锁概率随锁范围一起放大，这是生产库上死锁高发的机制根源。

Gap Lock 的另一个特性是它经常被误解为排他，实际并非如此：两个事务可以同时对同一个间隙持有 Gap Lock，它们之间不互斥，这与记录锁的排他性形成鲜明对比。死锁的陷阱恰恰埋在这里，两个事务同时对一段间隙加锁都能成功，看似相安无事，随后任何一个事务试图向这段间隙插入数据时，插入动作需要申请插入意向锁 Insert Intention Lock，插入意图锁必须在目标位置的前一个间隙上不存在任何其他事务的 Gap Lock 时才能获得。于是经典的对峙局面出现了：事务甲持有间隙一，事务乙持有间隙二，甲要向间隙二插数据等乙放锁，乙要向间隙一插数据等甲放锁，环就此闭合。Gap Lock 与插入意图锁这对组合是生产库死锁档案中出现频率最高的模式，本文档将用专门章节展开它的完整行为。

锁冲突的第二座隐蔽来源是二级索引与回表的组合。当查询使用二级索引但该索引不覆盖查询需要的全部列时，InnoDB 需要回表，即在主键索引上再做一次查找，这个过程会在二级索引与主键索引上分别留下锁。很多研发同学只分析了二级索引上的加锁范围，以为锁范围很小，实际主键上的同步加锁让冲突面扩大了一倍。更隐蔽的是更新语句的隐式锁升级：一条 UPDATE 用二级索引定位行，除了二级索引记录上的锁，还会在对应主键记录上加记录锁，如果优化器在执行中途放弃索引选择全表扫描，锁范围会瞬间扩大到全部记录。分析任何一条可能引发死锁的语句时，必须把主键与二级索引两条路径上的锁全部画出来，只看单条索引路径得出的结论在死锁复盘会上屡屡被现场证据推翻。

锁等待与死锁是两条不同的处理路径，排查前必须先分清手上是哪种情况。锁等待的参数是 innodb_lock_wait_timeout，默认五十秒，一个事务等待他方持有的锁超过该时长后报 1212 错误并回滚本次等待的语句，等待方是受害者，持有方毫发无损；死锁检测则是另一条路径，InnoDB 实时维护一张锁等待图，每当新的等待关系建立就检测是否存在环，一旦发现死锁立即介入仲裁，选择回滚代价较小的事务作为牺牲者，回滚其全部操作，代价大小的度量标准是事务已产生的 undo 量，这个仲裁行为无法人工指定。被牺牲的事务收到 1213 死锁错误，另一个事务继续执行。应用侧对 1213 的标准动作是捕获后整体重试整个事务而不是只重试最后一条语句，因为整个事务已经被回滚，只补最后一句会造成半截事务的逻辑错误。死锁是系统的自动保护行为，应用必须具备消化它的能力，这个认知是本手册反复强调的第一原则。

二、SHOW ENGINE INNODB STATUS 的解读

排查死锁的第一手材料永远是死锁现场日志，获取命令是 SHOW ENGINE INNODB STATUS。这条命令的输出很长，包含大量引擎状态段落，死锁排查只关心其中名为 LATEST DETECTED DEADLOCK 的段落，它保存着数据库最近一次检测到的死锁完整现场，包含参与死锁的每个事务的编号、活跃状态、正在执行的 SQL、持有的锁 HOLDS THE LOCK、等待的锁 WAITING FOR THIS LOCK TO BE GRANTED，以及锁的具体类型、锁定的索引名与记录值，段落末尾一行 WE ROLL BACK TRANSACTION 指明被仲裁回滚的一方。这个段落只有最近一次，新的死锁发生后旧现场被覆盖，因此值班纪律要求收到死锁告警后的第一动作就是把完整输出保存到工单附件里，任何先做其他排查再回来取现场的做法都要承担现场被覆盖的风险，一分钟的拖延可能让唯一的证据消失。

读死锁日志的核心技巧是抓住索引名。每段锁信息里 index PRIMARY of table 加表名说明锁落在主键上，index 加二级索引名说明锁在二级索引上，锁类型可能出现的值包括 record lock 表示记录锁、gap lock 表示区间锁、insert intention lock 表示插入意图锁，前缀加 S 或 X 区分共享与排他。解读的标准流程是把两个事务各自持有的锁与等待的锁抄下来画成有向图，事务甲持有锁一等待锁二，事务乙持有锁二等待锁一，两个箭头首尾相接，环就找到了，环上的每一条 SQL 都参与构造成冲突对。画图这一步看起来原始，实际是把日志语言翻译成结构语言的最快方式，跳过画图直接凭日志文本想象的排查，在复杂的三事务环上必然出错。画完环之后，拿冲突对的 SQL 去业务代码里定位调用位置与执行顺序，死因的链条就完整了。

死锁日志只保留最近一次的限制有一个正式的解法：开启参数 innodb_print_all_deadlocks，开启后每次死锁的现场都会完整写入 MySQL 错误日志，不再随新死锁覆盖。死锁反复发生的核心业务库应当默认开启该参数，开启的代价只是错误日志的体积增长，与排查收益相比完全可以接受，平台已经在核心库模板中预置了该参数。需要注意错误日志中的死锁段落格式与 SHOW ENGINE INNODB STATUS 输出一致，解析脚本可以复用，但错误日志里的时间戳精度到秒，多个死锁密集发生时排序要靠时间戳加日志序号双保险。除死锁段落外，错误日志里 DEADLOCK 关键字的增速是死锁频率监控的原始信号源，平台告警规则设置为每分钟超过五次触发告警，告警内容附最近一次死锁的摘要供值班快速分类。

看懂现场之后还需要确认隔离级别，因为加锁行为在可重复读与读已提交两种级别下差异巨大。可重复读级别下范围查询加 Next-Key Lock 锁住记录加间隙，前文的区间锁死锁模式都发生在该级别；读已提交级别下没有 Gap Lock，只有记录锁，区间锁类的死锁在该级别下天然消失。因此死锁排查的固定动作之一是执行 SELECT 确认当前库的隔离级别，再决定套用哪套锁行为模型去解释现场。业务侧曾有过在测试库排查三天无果的案例，原因是测试库是读已提交而生产库是可重复读，同一句 SQL 在两边的加锁行为根本不同，这个案例的教训写进了平台的排障清单：环境差异是死锁排查的第一类排查项，任何脱离环境谈 SQL 锁行为的分析都是空中楼阁。

三、间隙锁与插入意向锁

间隙锁锁定的是索引记录之间的开区间，它阻止的不是读取而是插入，其他事务向被锁间隙插入数据时必须等待。它的触发条件值得逐项列清：在可重复读级别下，使用非唯一索引做等值查询时，命中记录两侧的间隙都会被锁定；做范围查询时，覆盖范围内全部记录及其间隙被锁定；唯一索引等值且记录存在时退化为纯记录锁，记录不存在时锁定目标位置所在的间隙；没有索引可用时锁范围退化为全表扫描路径上的全部间隙，等于把整张表的写入都锁死。这里最后一条是生产事故的高发点：一条 WHERE 条件写错字段类型导致索引失效，语句从毫秒级的记录锁退化成整表区间锁，后续所有写入排队，死锁检测器随即报告大量死锁，值班初看日志会误以为发生了大面积业务冲突，实际只是一条走错索引的语句。分析任何区间锁现场时，第一步用执行计划确认语句走的索引。

插入意图锁是插入操作在等待 Gap Lock 释放时持有的等待标记，理解它的关键有两点。第一点，插入意图锁之间的兼容性很好，两个事务向同一间隙的不同位置插入互不阻塞，它只与 Gap Lock 冲突，也就是说只要没有其他事务锁住目标间隙，插入永远不需要等待；第二点，插入意图锁是请求中的锁而不是已持有的资源，但它的存在让死锁图上多了一类节点，一个事务持有着 Gap Lock 又申请插入意图锁，另一个事务同样如此且目标交错，环就形成了。生产上最典型的复现场景是两个事务先各自执行了带范围的 SELECT 加 FOR UPDATE，各自锁住了一段间隙，然后各自向对方的间隙里插入数据，两条插入全部进入等待，双向等待成立，死锁检测介入回滚一方。修复这类死锁的思路是压缩区间锁的存在时间或压缩插入落在被锁间隙的概率，具体手段按业务语义选择，常见的是把先锁后插的两步合并成一条语句，让区间锁的持有窗口从毫秒级消失。

唯一索引的等值插入还有一类隐藏冲突值得单独交代。事务一执行 INSERT 遇到唯一键冲突报错，但注意报错语句在默认行为下不会自动回滚整个事务，事务在报错后继续持有的锁不释放，其中就包括冲突检查时在唯一索引记录上加的锁。事务二随后 INSERT 同一键值，需要等事务一的锁；事务一此时如果执行后续语句再次触碰该索引区间，可能反过来需要事务二的资源，死锁形成。这类现场的死锁日志里会出现 lock mode S 与 X 的组合，看起来费解，根因其实是报错后不回滚导致的锁残留。平台编码规范对应的条目是：INSERT 捕获唯一键冲突异常后必须显式执行 ROLLBACK 或保证事务立即结束，绝不让事务带着报错残留的锁继续跑后续语句；能改写为 INSERT 加 ON DUPLICATE KEY UPDATE 原子形态的场景一律改写，让冲突的检查与处理在引擎内部一次完成。

四、加锁顺序规范

消灭死锁的最有力武器不是数据库调优而是代码侧的加锁顺序统一，原理很朴素：环的构成需要两个方向的等待，如果所有事务以相同顺序申请资源，单向排队永远构不成环。平台编码规范将锁的申请次序要求固化为三条强制条款。第一条，凡涉及多行更新的语句，主键列表必须按升序排列后再传入 SQL，禁止依赖 IN 列表的书写顺序，因为优化器在扫描时是按索引顺序加锁而不是按书写顺序，两个事务传入了互为倒序的列表，就会在两把锁上形成交叉等待，这一条是三类条款中收效最显著的一条，平台推行后整体死锁量下降了六成。第二条，凡涉及多表更新的操作，各表的处理顺序在同一业务内全局统一，以表名字典序或业务流程序为准，跨服务的流程由接口契约锁定顺序。第三条，先锁后改的操作中，SELECT 加锁的 WHERE 条件与后续 UPDATE 的条件保持一致，避免锁住的范围与更新的范围不一致引发的额外锁申请。

条款之外需要理解一个深层逻辑：由小到大排列的约束对象是锁的获取次序而不是语句文本顺序，只有当所有可能冲突的事务都遵循同一个顺序时保护才成立。规范推行时遇到过一个反面案例：团队把主键由小到大写进了新代码，但同表的另一条历史代码仍然按业务时间倒序更新，新旧两条路径的顺序相反，死锁率不降反升，直到把历史路径一并改正。结论是锁的申请次序是一个需要全量覆盖的属性，百分之九十的遵守等于零，全量核对的责任在评审环节，评审人必须对同一张表的全部写入路径提问：它们按什么顺序加锁。为了降低核对成本，平台推荐把热点表的更新入口收敛到少数几个 DAO 方法，路径少了核对就可行，散落的更新语句是锁次序失控的温床。

有了顺序规范仍然需要兜底，因为第三方组件、批量任务与人工操作不承诺遵守内部规范。兜底的第一层是死锁重试，捕获 1213 错误后休眠随机时长再整体重试，重试上限三次，随机休眠是为了避免冲突双方同步重试再次相撞，重试后仍然失败的上抛业务异常进入告警。第二层是锁等待超时的收紧，核心库将 innodb_lock_wait_timeout 从默认五十秒调整为五秒，让拿不到锁的事务尽快失败尽快释放，避免长时间僵持拖垮连接池；注意该调整对正常的长事务是额外压力，配套要求是核心库事务内的远程调用与文件操作必须移出。第三层是热点更新走内存排队，对极少数更新顺序无法统一的场景，在应用层把并发更新串行化，把数据库层面的竞争前移到应用层可控的位置。三层兜底的设计目标不是消灭死锁而是把死锁的影响压到毫秒级且业务无感。

五、典型案例复盘

案例一的现场是账务互转。死锁日志显示事务一执行 UPDATE account SET balance = balance 加负数 WHERE id IN (1, 2)，事务二执行同样语句但 IN 列表为 (2, 1)，LATEST DETECTED DEADLOCK 段落中两个事务在 id 为一和二的主键记录上交叉持锁，事务一 HOLDS THE LOCK 于记录一等待记录二，事务二持记录二等记录一，被回滚方为 undo 量更小的事务二。根因符合预期：IN 列表书写顺序不影响优化器取锁的次序，两边都按索引由小到大锁，看似安全，实际真正的差异在两条 UPDATE 各自是单条语句内部按顺序逐行加锁，两条语句对两行的锁获取节奏交错，第一条语句锁住行一的同时第二条语句锁住行二，随后的第二把锁互相等待。修复动作是把互转逻辑改为应用层先排序两个账户号再按升序执行两条单行 UPDATE，从机制上消除同语句内的交错可能。这个案例的教育价值在于：单条多行语句并不天然安全，语句内部的逐行加锁节奏本身就是交错源，涉及资金的多行操作优先拆成按序单行。

案例二的现场是库存预占与释放的间隙冲突。业务流程是事务一先执行 SELECT 加 FOR UPDATE 锁定某商品的一段库存区间，随后在同一事务内向同区间插入预占记录；事务二执行相同流程但锁定与插入的区间交错。死锁日志中两个事务各持有一段 gap lock，各自等待对方区间上的 insert intention lock。根因是先范围锁后插入的两段式流程让 Gap Lock 与插入意图锁的申请顺序在两个事务间相反。修复方案评估了三个方向：把两步合并成一条存储过程内的原子操作可以消灭区间锁窗口但增加维护成本；把库存模型从区间锁改为行级原子扣减语句，放弃 FOR UPDATE 改用条件更新的乐观并发，是最终选型；业务侧保留两段式的场景引入区间预分配，让插入落在各自预先划定的子区间内互不侵入。选型评审的结论具有通用价值：区间锁冲突的解法优先从业务模型入手，让锁的粒度从区间退化到记录，模型改不动时再做流程级的顺序控制。

案例三的现场是唯一的隐匿死锁，表象为偶发的插入超时伴随低频死锁。日志显示事务一 INSERT 唯一键冲突报错后未回滚继续执行，事务二同键值 INSERT 进入等待，事务一的后续语句又在等待事务二持有的资源，环闭合。业务代码的写法是先 INSERT 再捕获异常后改走 UPDATE 分支，异常分支没有显式回滚残留了共享锁。修复动作是改写为 INSERT 加 ON DUPLICATE KEY UPDATE 的一条原子语句，同时把插入意图区分开：存在即更新的场景一律用原子形态，存在即报错的场景捕获异常后立即回滚重开事务。复盘时确认该模式在三个业务中复制存在，全部整改。这个案例的推广结论是：死锁个案的修复价值有限，把个案归因到编码模式并在规范层禁止该模式，才能防止下一个团队踩同一个坑。

六、业务侧预防与监控闭环

预防体系的顶层是事务粒度控制，原理是锁持有时间与事务时长严格成正比，事务越长锁交叉的窗口越大。平台对核心库事务的要求量化为三条红线：事务内禁止任何远程调用，一次二十毫秒的下游超时会乘以并发数放大成锁等待雪崩；事务内禁止文件与消息发送操作；单事务语句数上限十条、执行时长上限两百毫秒，超过即告警。压测数据显示同一业务在把事务内的非数据库操作移出后，死锁发生率下降了一个数量级，这一条是所有预防手段中投入产出比最高的。其次是为高频更新语句补齐索引，全表扫描的锁范围覆盖全部记录，是区间锁之外另一个锁范围放大器，平台巡检脚本定期抓取全表扫描类语句并按执行频次排序，高频的挂账整改。两条手段的共同底层逻辑是压缩每个事务的锁覆盖面积与持有时间，面积与时间的乘积就是死锁概率的量级。

监控闭环依赖两个数据源：错误日志中的死锁段落数与性能模式表 data_lock_waits 的实时锁等待。告警规则分两级，每分钟超过五次死锁触发低级别告警要求当班分析；伴随业务错误率上升的立即触发高级别告警要求介入。工单流程要求收到告警后半小时内完成现场保存、等待环绘制与冲突 SQL 的代码定位，按本手册案例归类归因；修复上线后观察一周死锁曲线确认收敛，曲线未收敛的工单不允许关闭；每月汇总死锁工单，把高频模式与修复方案沉淀进编码规范，本手册的案例库即来自该月度沉淀机制。衡量死锁治理成效的指标是死锁引发的业务错误数而不是死锁本身的发生次数，被应用重试消化掉的死锁是系统正常运转的一部分，这一指标定义写进平台考核文件。最后声明本手册的边界：主从切换与复制运维、备份与恢复操作分别由对应的兄弟文档规定，死锁排查中遇到这些场景请直接查阅对应文档，本手册不展开。
