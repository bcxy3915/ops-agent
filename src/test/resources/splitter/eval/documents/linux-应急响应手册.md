## 1. 总则与应急响应流程

### 1.1 应急基本原则

Linux 服务器的应急响应遵循三条铁律。第一条是先固化现场再动手：服务器异常状态是易逝证据，进程死了、连接断了、文件删了，证据就永久消失，因此处置任何异常的第一动作永远是执行第 7.2 节的现场快照脚本，把时间、负载、内存、磁盘、连接、进程、内核日志七类信息固化到 /tmp/snapshot.txt 再做后续操作；二四年复盘的多起事故因值班人员直接重启服务器导致无法定位根因，此后"重启前三分钟快照"被写入值班红线。第二条是先止血再根因：业务恢复优先级永远高于完美定位，快速止血手段（隔离故障节点、切换备用、临时清理）应当并行推进，根因分析可以在业务恢复后从容展开。第三条是双人复核原则：涉及删文件、杀进程、重置连接的破坏性动作，必须在告警群同步并得到二线或值班经理确认后执行，单人深夜处置尤其不允许跳过这一步。

### 1.2 响应时限与升级路径

P1 类告警（核心服务不可用、服务器失联、疑似入侵）要求五分钟内响应、十分钟内给出初步判断；P2 类（单机性能异常、磁盘水位告警）三十分钟内响应。应急事件的升级路径为：一线值班十五分钟无明确结论升级二线系统管理员、二线三十分钟无结论拉入研发与网络组联合处置、任何疑似安全事件立即抄送安全组而不等待结论。处置全程的每个动作要求在值班群以"动作 + 依据 + 结果"三段式回报，回报本身就是复盘时间线的原始素材。事件关闭后五个工作日内产出复盘文档，复盘必须回答三个问题：为什么会发生、为什么告警没有更早、为什么花了这么久，答案对应的改进项落实到人与期限。

### 1.3 工具基线

应急工具的基线命令集为 top、vmstat、磁盘 IO 统计工具、pidstat、mpstat、lsof、ss、strace 五分钟内可达，公司镜像已内置 sysstat 与 lsof 包，值班人员在接入新机型时必须核对工具齐备，缺包的服务器在巡检时会被打回。所有命令的输出格式在本文档中均以生产实测为准，不同发行版的列名差异（如 %iowait 的显示位置）值班人员应当熟悉本机型基线，避免在应急时刻读错列。手册命令中的尖括号占位符（如 <pid>）按实际值替换，处置时禁止把手册命令不加理解地整段粘贴执行，任何命令都应当知道它在看什么。

## 2. CPU 异常定位

### 2.1 负载形态判读

CPU 告警到达后的第一步是 `top` 看三行关键信息：load average 三元组的绝对值与趋势、CPU 行的用户态与内核态比例、以及 wa 列即 iowait 占比。CPU 使用率高的四种形态对应完全不同的故障域：us 高说明用户态计算密集，指向业务热点方法、低效算法或死循环，用 `top -Hp <pid>` 找到热点线程、配合 `pidstat -t -p <pid> 1 3` 采样确认后转给应用组抓线程 dump；sy 高说明内核态消耗大，典型于频繁系统调用与锁自旋，用 `vmstat 1` 看 cs 列的上下文切换次数，每秒超过十万且伴随 sy 高通常是线程数配置过大或锁竞争，`pidstat -w -p <pid> 1` 看非自愿切换（nvcswch）占比可进一步确认调度饥饿；wa 高即 iowait 占比突出，说明 CPU 在等待磁盘，瓶颈根本不在计算而在存储，转 2.2 节流程处置；si 高说明软中断占用大，指向网络包处理集中，`mpstat -P ALL 1` 观察软中断是否集中在个别核心，网卡单队列场景的流量集中是典型形态。四形态分诊是 CPU 应急的第一分叉点，走错方向会浪费整个黄金二十分钟。

### 2.2 IO 等待场景的深挖

当 iowait 成为主要形态时，排查的第二层是确认慢在哪个设备、哪些进程。`iostat -x 1` 的输出重点看四列：设备级 %util（该盘一秒内处理 IO 的时间占比，机械盘接近百分之百即饱和）、await（平均每次 IO 的等待毫秒数，机械盘超过二十毫秒、SSD 超过五毫秒即异常）、以及 r/s 与 w/s 的读写方向分布。确认设备瓶颈后用 `iotop -o` 列出实际产生 IO 的进程，再以 `lsof -p <pid>` 或 `strace -p <pid> -e trace=read,write -f` 确认进程具体在读写的文件路径。案例库速查口诀：MySQL 突发 IO 高通常是大查询或批量导入，先看慢 SQL 与 binlog 行为；ES 节点 IO 高通常是段合并与分片再平衡，查对应手册处置；日志盘 IO 高通常伴随应用疯狂报错打堆栈，根因在业务侧报错风暴而不在盘本身——三个高频结论覆盖了公司历史 IO 告警的八成，先对口令再深挖能显著缩短定位时间。若 %util 不高但 await 仍高，怀疑对象转为存储链路（云盘限速、虚化层争抢、RAID 卡异常），需要平台组介入，值班人员采集设备 IO 统计两分钟采样输出后升级。

iowait 类故障有两类高频根因值得单独成段。第一类是单盘打满而其余盘空闲，通常由分区规划不当造成——应用日志、数据库数据与容器目录挤在同一块云盘上，一次日志风暴就把数据库的读写延迟从两毫秒拖到两百毫秒，处置手段是临时限流日志写入并把高频写路径迁往独立盘，根治靠分区重规划；公司基线要求日志目录与应用数据目录物理分盘，这一条在新机交付检查单上属于强制项。第二类是文件系统级异常，xfs 在异常断电后可能出现分配器行为劣化、ext4 出现碎片化加剧，两者的表现都是设备统计数值正常但 await 异常高，需要在维护窗口执行文件系统检查确认。值班层面对 IO 类故障的汇报口径有固定模板：设备名、%util、await、await 基线值、占用前五的进程，五项齐全才允许升级二线，这个模板显著减少了升级过程中的来回追问成本。

### 2.3 现场保全与收敛

对 CPU 异常的现场保全要求在动手干预前完成三样采集：`top -b -n 1 > /tmp/cpu.txt` 固化全局快照、`ps -eLf > /tmp/threads.txt` 固化线程级清单、以及 Java 应用执行 `jstack <pid> > /tmp/jstack.txt` 抓线程栈（或对支持的应用 `kill -3 <pid>` 让堆栈输出到应用日志）。保全完成后才允许采取干预动作，干预优先级从轻到重为：摘除节点流量观察是否收敛（与业务确认）、对失控进程降权（renice）、最后才是重启进程。杀进程前的最后一次提醒适用于所有场景：杀掉的是证据，确认快照已落盘再动手。CPU 异常收敛后的复盘要求还原出完整的负载曲线截图，监控图表与快照文件一起归档到事故单。

## 3. 内存异常与 OOM 处置

### 3.1 内核 OOM 判定

应用进程无故消失或服务器在凌晨出现批量进程重启时，第一怀疑对象是内核 OOM killer。判定命令为 `dmesg -T | grep -i -E 'killed process|out of memory'`，输出会明确记录被杀进程的 PID、进程名、内存占用与 oom_score 打分；`/proc/<pid>/oom_score` 的规则是占内存越多打分越高、越先被杀，绑定关键业务的服务器要靠 oom_score_adj 把数据库等核心进程调成受保护对象。dmesg 是 OOM 判定的唯一权威来源，因为进程被杀后应用自身日志可能来不及留下任何痕迹；反之如果 dmesg 没有 OOM 记录而进程消失，怀疑对象转向应用自行崩溃（按第 2.3 节保全后看 core 与退出码）或被人为终止。处置内存不足的顺序是：先看本节 3.2 的真实分布确认是页缓存误判还是真不足，再评估临时扩容交换分区止血的可行性，最后走加内存或降消耗的根治流程，禁止在未确认前直接重启了事。

### 3.2 内存分布判读与交换治理

内存判读的第一原则是看 available 而不是 free：`free -m` 的 free 列低是 Linux 的常态（空闲内存被用作页缓存），available 列才是应用实际可用的余量，把 free 低当故障的误报占内存类工单的四成。真实内存归属按 PSS 口径统计：`smem -rk | head -20` 输出按比例分摊共享内存后的排序，比 RSS 直接相加科学得多。交换分区的治理基线是 si/so 有持续交换即异常：`vmstat 1` 的 si 与 so 列非零表示正在换入换出，这是延迟抖动的直接元凶；把 `sysctl vm.swappiness` 调到 10 能降低交换倾向、缓解症状，但要明白 swappiness 只是倾向参数、不能根治物理内存不足，根治只能靠降内存占用或加物理内存——这个"缓解与根治"的区分在应急沟通中必须向业务方讲清楚，避免"调了参数就没下文"的处置半途而废。僵尸进程属于内存篇的常见误报：`ps aux | awk '$8 ~ /Z/'` 列出状态为 Z 的进程，僵尸已死不占内存、堆积说明父进程不回收子进程退出状态，修复对象是父进程（补 wait 调用或重启父进程），对僵尸本身 kill -9 无效，处理完要回工单说明成因。

内存泄漏的判别方法值得每位值班人员掌握：正常的业务内存曲线呈锯齿状、峰值随流量涨落回落，泄漏形态则是波谷逐日抬升、即使深夜低谷也不回落。确认手段分三步，先用 vmstat 的 si/so 观察是否有持续交换，再用 smem 按天截取同一进程的 PSS 序列对比增量，最后对嫌疑进程间隔一小时抓两次应用的内存明细（Java 用 jmap -histo 或堆 dump 对比对象增量）交给应用组定位。处置节奏上，泄漏进程不需要立刻重启，按剩余可用内存能支撑的天数决定重启窗口，低于两天就必须当周安排；重启前按 1.1 节留全快照，快照里的 smem 输出是日后复盘泄漏速率的关键证据，二五年两起 Java 堆泄漏事故的定级与容量补偿决策都直接引用了这类序列数据。

## 4. 磁盘打满与已删除文件句柄

### 4.1 定位路径与常规黑洞

磁盘打满的标准定位流程两步走：`df -h` 先确定打满的挂载点，随后 `du -xh --max-depth=2 <挂载点> | sort -rh | head -20` 找目录大头，-x 参数禁止跨文件系统、避免 du 把挂载进来的外部卷一起统计导致误判。公司环境中的常规黑洞有五处：应用日志未配置轮转（logrotate 配置缺失或 cron 失效）、core dump 文件堆积（/var/lib/systemd/coredump 或应用目录的 core.* 文件）、Docker 的镜像与容器日志（见 OPS-DOCK-004 手册第三章）、数据库 binlog 与归档未按保留期清理、以及 tmp 目录被大文件占用。五处黑洞的清理动作各有规范，日志类清理前确认日志平台已采集完成，core 与 tmp 类可直接删，binlog 清理必须与 DBA 确认可清理位点。此流程的隐含要求是删除动作走 1.1 节的双人复核，尤其 binlog 与归档类文件属于删错即丢数据的类别。

### 4.2 已删除文件句柄的识别与释放

磁盘打满场景中有一类最经典的疑难形态：df 显示使用率百分之百、du 把目录翻遍却只能找到几个 GB 的文件，二者对不上账的根因是有进程持有大文件的打开句柄、文件已在文件系统层面被 unlink 删除、但描述符未关闭，内核为持有进程保留数据块直到最后一个句柄释放，此类文件在进程的 fd 表中标记为 deleted 状态。识别命令是 `lsof +L1`，该命令只列出链接计数小于一（即已被删除但句柄仍被持有）的文件，输出的 SIZE/OFF 列可以看到每个被删文件的真实体积、NODE 列确认 inode，定位到持有进程后有两个处置选项：选项一是直接重启或优雅重启持有进程（对支持重开日志文件的进程 `kill -USR1 <pid>` 触发日志重开是首选），句柄释放后空间立刻归还；选项二是不中断进程、用 `: > /proc/<pid>/fd/<描述符编号>` 把文件描述符指向的内容清空，适合进程不能立即重启的窗口期。为什么会出现 deleted 文件是运维必须理解成因的：典型场景是日志文件被 rm 或 truncate 后进程仍持有旧句柄继续写，公司两起典型案例分别是值班人员直接 rm 大日志文件（正确方式是 mv 后让进程重开）与业务侧脚本清理缓存文件误删了应用正在写的文件，两起事故的处理时长都超过一小时，根因都是不认识这个形态。

### 4.3 预防机制

已删除文件句柄问题的预防机制有两层：监控平台对"df 使用率减去 du 归属之和"的差值做周检，差值超过总盘百分之五即告警，能在用户感知之前暴露幽灵占用；规范层面禁止对进程正在写的文件直接 rm，操作 SLP 规定为先确认进程的日志重开机制（或用 mv 改名让进程按固定路径重建新文件）。磁盘水位的告警阈值沿用基础架构基线（百分之八十 P2、百分之九十 P1），阈值告警的处置时限要求确保永远不会走到空间耗尽才响应，这一条对本章两个场景都适用——空间未耗尽之前处置的从容度是完全不同的。

## 5. 网络连接异常排查

### 5.1 分层连通性框架

网络异常的快速分诊沿用分层连通性框架的三步验证：`ping -c3 <目标>` 验证三层 IP 可达、`telnet <目标> <端口>` 验证四层端口可达、`curl -v http://<目标>:<端口>/路径` 验证七层应用语义。三层不通查路由（`ip route`）与 ARP 表；三层通而四层不通查防火墙（`iptables -L -n` 与 firewalld zone）与对端监听（`ss -lntp | grep <端口>`）；四层通而七层异常看应用日志与超时配置。该框架在本手册仅作为入门导引，跨网段丢包、路由质量与传输链路深挖由 OPS-NET-010 网络诊断手册承载、值班人员判明方向后即应转网络组，不要在主机侧空耗。本章节的真正主场是主机侧连接表本身的异常，即 5.2 与 5.3 两节的内容。

### 5.2 CLOSE_WAIT 堆积处置

`ss -antp | awk '{print $1}' | sort | uniq -c` 做状态分布统计时，看到等待关闭状态的连接数量达到数百以上即进入本节流程。该状态的语义是对端已发送 FIN 关闭连接、本端内核完成半关闭并等待应用调用 close，堆积的唯一根因是应用代码收到对端断开后没有关闭连接（连接泄漏），典型于短连接调用下游服务、下游异常断开后本端资源未回收的形态。定位持有者用 `ss -antp state close-wait | head -20` 看到堆积连接的进程与对端地址，对端地址分布能直接告诉你是哪个下游的断开未被处理；随后把进程 PID 与堆栈证据（Java 抓 jstack 看关闭调用路径）交给应用负责人修复代码。必须旗帜鲜明地传达给业务方的结论是：此类等待关闭连接的堆积是代码缺陷，内核参数救不了——调整任何 sysctl 项（fin_timeout、tw_reuse 等）都不会让应用去调用 close，堆积依旧、最终句柄表耗尽，唯一出路是修代码。止血手段有两个层次：临时把该实例摘出流量避免句柄继续增长，对已堆积的连接可执行 `ss -K state close-wait dst <对端>` 主动杀连接回收句柄（内核 4.9 以上支持），但修复上线前的堆积还会复发，止血与修复必须成对出现。

### 5.3 TIME_WAIT 与连接数水位

TIME_WAIT 是本端主动关闭后的正常协议状态，持续二倍最大段生存期后自动回收，它不泄漏句柄、不占资源，大量出现只说明短连接高频（每秒数千次新建关闭的 RPC 场景很常见）。处置口径分三档：连接数健康时无需任何动作，把它当正常现象；本地端口（ephemeral port）耗尽压力（`ss -s` 中 estab 加 timewait 总量逼近 ip_local_port_range 上限）时把 `net.ipv4.tcp_tw_reuse` 开启缓解新连接端口紧张，并推动应用侧长连接化改造；客户端长连接池配置不当导致每请求建连的场景推动应用调整池参数。与之相对的 estab 数水位告警指向容量问题：`ss -s` 的 estab 数接近应用 backlog 或 somaxconn 上限时新连接将被拒绝，确认后扩容或上调 backlog（该动作需评估对端处理能力，禁止单方面拉大）。句柄层面用 `cat /proc/<pid>/limits | grep files` 与 `ls /proc/<pid>/fd | wc -l` 对比进程级句柄水位，达到 nofile 上限的过程句柄告警要区分是真实业务量还是泄漏，曲线形态（缓涨型为泄漏、锯齿型为业务量）是判别依据。

## 6. 入侵迹象排查与处置

### 6.1 常见入侵迹象清单

疑似入侵（异常外连告警、性能异常且进程可疑、安全组通报）的第一小时按六条线索排查。线索一是异常进程：`ps auxf` 全树观察陌生进程，重点甄别伪装成系统进程名的可疑项（如 kworker 变体多一个字母、路径在 /tmp 或 /dev/shm 下、可执行文件最近七天新增），配合 `top` 看 CPU 占用异常高的陌生进程。线索二是异常连接：`ss -antp | grep -v -E ':22|:443'` 过滤出非 SSH 与 HTTPS 的外连，矿池端口（3333、4444、5555、7777、14444 等）与非常见地区 IP 直接坐实挖矿外连。线索三是定时任务：`crontab -l`、`/etc/cron.d/` 目录与 `/var/spool/cron/` 逐个检查，木马普遍用定时任务实现自我复活，删主程序不删 cron 等于白干。线索四是 SSH 后门：`/root/.ssh/authorized_keys` 与所有用户家目录的 authorized_keys 是否被追加了陌生公钥，known_hosts 里出现业务无关节点也是横向移动痕迹。线索五是登录痕迹：`last`、`lastb`（爆破尝试记录）、`history` 与 `/var/log/secure`（Debian 系为 auth.log）还原登录时间线，异常时段的失败登录爆量是爆破证据。线索六是新增文件：`find / -mtime -7 -type f -perm -111 2>/dev/null` 列出近七天新增可执行文件做人工甄别。六条线索全部留档输出到安全事件单，即使初步判断为误报也要留痕。

### 6.2 挖矿木马标准处置流程

确认为挖矿木马后的处置纪律是先隔离后清理：第一步断网隔离（拔网线或安全组收紧为仅管理通道），隔离是止损与防止横向扩散的第一优先级动作，未隔离状态下木马可能持续更新、加密或删除自身；第二步取证，抓样本与 IOC（矿池域名、外连 IP、落地路径、cron 内容、可疑公钥）打包给安全组，证据链完整是后续溯源与全司排查的依据；第三步才执行清理，kill -9 可疑进程、清空相关 crontab 与 systemd timer、删除落地文件与 authorized_keys 追加项，清理后重启观察是否复活，复活说明有未发现的守护进程或持久化点，回到第 6.1 节重新排查。第四步复盘入侵入口：公司历史案例集中在三个入口——SSH 弱口令爆破、暴露在公网的未授权 Redis、以及存在已知漏洞的 Jenkins，入口修复完成前不允许恢复该节点到生产网络。绝对禁止的动作是未隔离直接删文件：既破坏证据、又大概率被守护进程复活，看起来清理干净了实际还在跑。

### 6.3 事后加固与移交

安全事件的恢复上线条件是：入口修复验证完成、全盘木马复扫两轮干净、安全组完成同网段横向排查抽查、以及 root 与应用账号口令全部轮换。恢复后一周内该主机进入重点观察名单，监控侧对其外连流量保持白名单模式（仅放行业务目标）。事件全部材料（时间线、IOC、样本哈希、入口分析、修复措施）整理进安全事件单并移交安全组归档，主机侧重装系统作为可选手段由安全组评估后决定——对无法确保清理彻底的节点，重装的确定性优于反复排查的不确定性，这是历史处置中沉淀的判断标准。

### 7.2 现场快照脚本

应急第一分钟执行以下快照，输出固化到单一文件便于事后分析与群内回传，该脚本是所有场景的第 0 步，不依赖任何判断即可先跑：

```bash
date > /tmp/snapshot.txt
uptime >> /tmp/snapshot.txt
free -m >> /tmp/snapshot.txt
df -h >> /tmp/snapshot.txt
ss -s >> /tmp/snapshot.txt
ps auxf >> /tmp/snapshot.txt
iostat -x 1 3 >> /tmp/snapshot.txt
dmesg -T | tail -100 >> /tmp/snapshot.txt
```

| 用途 | 命令 |
|------|------|

| 进程句柄水位 | `ls /proc/<pid>/fd \| wc -l` |
