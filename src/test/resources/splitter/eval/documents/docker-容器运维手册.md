## 1. 总则

### 1.1 运行时架构与值班职责

公司存量宿主机中还有相当一部分业务直接以 Docker Compose 或裸 docker run 方式部署（非 K8s 编排），这部分机器的运行时稳定性由容器运行时组负责。Docker 架构上分为 daemon（dockerd）、客户端与运行时组件，daemon 承担镜像管理、网络配置、卷管理与日志轮转等职责，daemon 一旦重启，除非配置了 live-restore，所有容器都会被连带重启——这是运行时运维必须刻在脑子里的前提，任何 daemon 级变更都必须先评估容器重启影响面。生产宿主机的 daemon 配置统一由配置管理工具下发，标准配置包含日志驱动上限（3.2 节）、数据目录迁移与仓库镜像加速地址，值班人员巡检时应核对 /etc/docker/daemon.json 与标准模板一致，发现漂移立即登记并回炉。daemon 配置变更的执行窗口与审批要求在变更纪律中统一约定。

### 1.2 操作纪律

容器运行时层的操作纪律有三条强制要求。第一条，daemon 配置变更必须走变更单、在低峰窗口执行，且执行前必须核对受影响容器清单与业务负责人确认，daemon 重启即业务重启，不存在"只改配置不影响容器"的侥幸；开启 live-restore 后例外情形在 1.1 节已说明，但仍需在变更单中写明例外依据。第二条，任何清理类命令（prune 家族）在生产宿主机执行前必须先执行对应的查看命令确认清单，`docker system prune -a --volumes` 属于禁用级命令，它会把未被任何容器引用的卷一并删除，而卷里可能是数据库数据，该命令只允许在可随时重建的临时环境使用，生产环境必须按镜像、容器、卷逐类精确删除并留档删除清单。第三条，进入容器排查不允许改动容器内应用文件后直接退出，任何修复动作必须回到镜像或配置层固化，否则容器一重启修复就消失，此类"幽灵修复"在二四年出现过四次，全部演变为二次故障。

## 2. 容器生命周期与 OOM 治理

### 2.1 容器生命周期与重启策略

容器生命周期从 docker run 创建开始，依次经历运行、暂停、停止与删除，运维高频接触的是停止与重启环节的语义细节。停止容器时 daemon 先向主进程发送 SIGTERM，随后进入停止宽限期（默认十秒，可通过 stop-timeout 调整），宽限期到仍未退出则发送 SIGKILL 强杀，因此应用能收到的唯一优雅退出机会就是宽限期内的 SIGTERM 窗口。重启策略的基线选择是 `--restart=on-failure:5`，它只对非零退出码重启且限制五次上限，防止启动即崩的应用陷入死循环重启把宿主机日志盘写穿；always 策略仅保留给守护型基础组件。需要特别注意的交叉点是 ENTRYPOINT 的写法陷阱：shell 形式（ENTRYPOINT java -jar app.jar）会让 java 成为 shell 的子进程，SIGTERM 被shell 吞掉、应用收不到停止信号，宽限期一到被 SIGKILL 强杀，正在处理的请求与消息全部丢失，这是公司二四年消息丢件事故的根因，正确写法必须是 exec 数组形式，配合 STOPSIGNAL SIGTERM 与业务侧的 shutdown hook 联动，该检查已纳入发布准入。

### 2.2 OOMKilled 的判定与治理

容器以退出码 137 终止时必须首先怀疑因内存超限被杀，137 的构成是 128 加信号编号 9（SIGKILL），而触发 SIGKILL 的常见来源就是 cgroup 内存超限时的 OOM killer。确认动作分两步：第一步执行 `docker inspect <容器> --format '{{.State.OOMKilled}}'`，输出 true 即确认为内存超限；第二步看内核日志 `dmesg | grep -i -E 'oom|killed process'`，找到 oom-kill 事件记录中 total-vm 与 rss 的实际值，对比容器的 memory 限额，判断是"限额设小了"还是"应用真的泄漏了"。两种结论的后续路径完全不同：限额不合理则按 4.1 节的评估方法重新核算并走变更流程上调；应用内存持续爬升则抓堆 dump 交给应用组分析，同时临时把该容器摘出流量。这里有个高频误区必须澄清：把 memory-swap 调大等于允许容器用交换分区，确实能让内存超限杀进程的现象暂时消失，但代价是 JVM 堆被换出到磁盘、GC 暂停从毫秒级飙到秒级，对延迟敏感业务等于慢性自杀，公司基线是 memory-swap 与 memory 相等（即完全禁用交换），宁可让它快速死也不让它慢慢卡，这条取舍原则应用负责人必须知晓。

治理的长期机制是让内存画像透明化。容器平台为每个业务容器采集 RSS 曲线并计算 P99 峰值与均值的比值，比值大于一点五的应用被标记为"锯齿型内存"，进入容量治理例会跟踪；Java 应用则要求按 5.2 节的 MaxRAMPercentage 方式声明堆上限，让堆外内存（直接内存、线程栈、元空间）留足余量。经验数值是 Java 容器的限额至少为堆大小的两倍，只给堆留百分之五余量的配置曾在压测中表现为"一切正常、容器突然因内存超限被杀"，根因就是堆外内存没有任何余量。

### 2.3 退出码速查与现场保全

非 137 的异常退出码各有指向：139（128+11，SIGSEGV）表示段错误，典型于 JNI 或 Netty 原生库崩溃，需要抓 core 文件与原生库版本；125 表示 docker daemon 自身错误（参数非法、挂载冲突）；126 与 127 分别表示容器内命令不可执行与不存在，常见于 ENTRYPOINT 脚本调用路径错误。处置任何异常退出前先做现场保全：`docker ps -a --filter status=exited --format` 列出退出时间、`docker logs <容器> --tail 500 > /tmp/容器名.log` 落盘最后的日志、`docker inspect` 全量输出存档，三样齐备后才允许删除或重建容器，因为没有现场的重启等于把唯一证据销毁。历史教训是某次值班直接 docker rm 了 139 崩溃的容器，事后定位只能从零开始，该案例已写进值班培训教材。

## 3. 存储驱动与日志盘治理

### 3.1 overlay2 与镜像层清理

Docker 的镜像与容器可写层由 overlay2 联合文件系统承载，全部存放在 /var/lib/docker/overlay2 目录下，该目录的磁盘占用异常增长有三个黑洞来源。第一个黑洞是悬空镜像：CI/CD 环境每次重复构建都会让旧层失去标签、变成标签为 <none> 的 dangling 镜像，构建频繁的机器上悬空层可以累积到几百 GB，识别命令是 `docker images -f dangling=true`，清理命令是 `docker image prune -f`，平台基线要求构建类机器每日自动执行清理、生产机器每周巡检一次。需要提醒的是清理动作的副作用评估：dangling 镜像确认无容器引用即可安全删除，但 `docker image prune -a` 会把不在运行中的历史版本镜像全部删除、导致回滚时要重新拉取，该命令必须限定在构建机使用。第二个黑洞是已退出但未删除的容器，`docker container prune` 清理，注意先按 2.3 节保全退出容器里的现场再清理。第三个黑洞是容器内应用直接往可写层写大文件，定位方法在 3.3 节展开。

### 3.2 默认文件日志驱动治理

容器日志默认走文件日志驱动：daemon 把容器 stdout/stderr 的每一行包装成一个 JSON 对象写入 /var/lib/docker/containers/<容器ID>/<容器ID>-json.log，原始行为符合运维直觉（一个进程一行日志）、且 docker logs 命令可以直接读取，但它的默认配置不设任何上限，一个每秒打印五千行堆栈的失控容器可以在数小时内写满整块数据盘，公司二四年最严重的一次宿主机故障正是报错风暴写满根分区导致 daemon 失联。治理基线是在 daemon.json 中显式声明 `log-driver` 为该文件驱动并配置 `log-opts` 的 `max-size: 100m` 与 `max-file: 3`，即单文件一百兆、最多三个轮转文件，单容器日志占用封顶三百兆。配置样例如下，该块由配置管理工具统一下发：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "100m", "max-file": "3" }
}
```

该配置有一个关键局限必须在变更时向业务方讲清楚：daemon.json 的日志选项只对配置生效后新建的容器生效，存量容器不会自动继承，必须配合容器重建（热重建）才能套上新上限。实施节奏上公司采用滚动方式：宿主机按业务低峰分批执行 daemon reload 后逐个热重建容器，重建前确认业务侧有实例冗余。另一个运维要点是即便配了上限，该文件驱动的轮转本质是删旧文件，docker logs 仍能读到当前轮转窗口内的内容，跨窗口的历史查询要依赖日志采集器（Filebeat/Vector 从 json 文件采集后发往日志平台），所以平台同时要求采集器的 tail 必须跟得上写入速率，采集延迟本身要纳入监控。

### 3.3 磁盘占用定位三板斧

宿主机数据盘告警时的标准定位动作分三步。第一步 `docker system df -v`，该命令逐项列出镜像、容器、卷、缓存各自占用与明细归属，是容量巡检的第一命令，正常水位下镜像与容器可写层占用应低于数据盘的六成，超过即进入第二步细查。第二步把 overlay 层映射回具体容器：`docker ps -q | xargs docker inspect --format '{{.GraphDriver.Data.MergedDir}} {{.Name}}' | sort`，输出可写层路径与容器名的对照表，用 du 对可疑路径求和即可锁定"容器内写大文件"的元凶，此类元凶九成是应用往容器文件系统直接写日志或临时文件，根治方法是业务改造为挂载卷或走 stdout，临时止血是重绑定日志目录到宿主机卷。第三步检查 /var/lib/docker/containers 下的 json 日志文件尺寸，配合 3.2 节判断是否上限配置缺失。三步定位的产出必须回帖到容量工单，形成"告警—定位—处置—验证"闭环，不允许只删文件不留记录，因为删了还会长回来。

## 4. cgroup 资源限制

### 4.1 内存与 CPU 限额的设定方法

Docker 的资源限制本质是对每个容器创建独立的 cgroup 组并向其写入配额，内存方向的核心参数是 --memory（配额上限）与 --memory-swap（内存加交换总量），公司基线是两者相等以完全禁用交换，理由在 2.2 节已阐述。CPU 方向的参数有两组口径：--cpus=1.5 是总体口径（等效于 --cpu-period=100000 加 --cpu-quota=150000 的组合），表示该容器最多使用一点五个核；--cpu-shares=512 是相对权重口径，只在宿主机 CPU 争抢时生效、按比例分配空闲算力，不争抢时不产生任何限制。两个口径的适用场景不同：与业务方约定明确资源边界时用 --cpus，同优先级混部想提高整机利用率时叠加 --cpu-shares。生产基线的评估方法沿容量例会口径：以应用压测的 P99 CPU 均值乘以一点五倍冗余作为 --cpus 值，内存以 2.2 节画像的 P99 峰值乘以一点三作为 --memory 值，取整后登记进容量台账，任何调整必须重新走例会评审，防止"谁报的故障谁随手加资源"的无序状态。

### 4.2 cgroup 层面的观测与排查

理解资源限制的底层是 cgroup 文件系统后，很多疑难问题可以直接读文件定位。CPU 方面，容器被限流（throttle）的证据在 /sys/fs/cgroup/cpu/<容器路径>/cpu.stat 的 nr_throttled 与 throttled_time 字段，应用表现为"CPU 使用率不高但接口周期性卡顿"时，先看这两个字段是否增长——增长说明配额不足，业务高峰期被按周期卡住，处理办法是上调 --cpus 或排查毛刺来源；不增长则说明卡顿来自应用自身（锁、外部依赖）。内存方面，容器视角的 /proc/meminfo 默认显示宿主机全局数值，在旧内核上会误导按宿主机总量决策的应用，较新内核的 lxcfs 已将其隔离，值班人员判断内存水位的正确入口是 docker stats 与 cgroup 的 memory.current 文件，而不是进容器看 free。PIDs 方向的 --pids-default 限制防的是线程爆炸型故障，JVM 应用某次线程泄漏创建了几万个线程把宿主机拖垮后，公司基线统一加了每容器五百线程的上限，该案例的详细复盘在运行时 Wiki 存档。

### 4.3 限制变更的联动约束

cgroup 参数的变更必须识别联动关系，孤立调整会引发次生问题。最典型的是内存限额与 JVM 堆的联动：下调 --memory 前必须先评估 JVM 堆配置是否仍满足"限额至少两倍于堆"的经验比，否则堆外内存余量消失、因内存超限被杀的概率上升，正确顺序是先在变更单中写明两者比例核算再执行。其次是 CPU 限额与吞吐容量的联动：--cpus 砍半后应用的处理能力同比例下降，业务侧的排队与超时参数（上游重试、消息消费并发）必须同步评估，否则队列积压以另一种形态爆发。最后是 daemon 重启的联动：虽然直接编辑 cgroup 文件可以临时止血（应急场景允许），但容器重启后由 docker run 参数重新渲染，任何未回到 run 参数与编排文件固化的调整都会丢失，应急操作必须在四十八小时内完成固化回写，这是运行时组的 SLA 承诺。

## 5. JVM 容器感知

### 5.1 UseContainerSupport 与堆计算原理

Java 应用的容器内存事故有一个共同的技术根源：老版本 JVM（JDK 8u191 之前完全失效、8u191 到 JDK 9 之间部分生效）不感知 cgroup，默认堆大小按宿主机物理内存的一半计算，在 256GB 的宿主机上跑 2GB 限额的容器，JVM 理直气壮地申请 128GB 堆，实际用到 2GB 上限时立刻因内存超限被杀，表象是"JVM 看着挺健康、容器突然就死了"。从 JDK 10 起 JVM 默认开启 UseContainerSupport 标志，该机制让 JVM 读取容器所属 cgroup 的内存限额并以此为基数计算堆默认值，配合 -XX:MaxRAMPercentage 按百分比声明（如 50.0 表示堆为限额的一半），堆大小随容器限额自动伸缩、免除了按机器规格写死 -Xmx 的维护负担。公司基线要求所有容器化 Java 应用运行 `java -XX:+PrintFlagsFinal -version | grep -i container` 确认输出中该标志为 true，并且用 MaxRAMPercentage 替代写死的 Xmx，双保险防止退化。

### 5.2 堆外余量与 GC 观测

容器感知机制只保证堆的计算正确，而内存超限被杀的另一半元凶是堆外内存：JVM 的总内存等于堆加元空间加线程栈加直接内存加 JIT 缓存，MaxRAMPercentage 设到 75 以上的配置意味着堆外只剩四分之一的余量，Netty 重度使用直接内存的应用几乎必然在峰值期越界。公司压测结论是常规 Spring Boot 应用 MaxRAMPercentage 取 50（堆为限额一半）、堆外余量百分之五十，重度堆外应用（网关、推送类）取 25 到 35，该取值写入应用交付模板。观测层面，容器平台采集 JVM 的 GC 暂停时间与元空间使用曲线，GC 暂停 P99 超过五百毫秒或元空间持续爬升的应用进入 5.3 节的排查流程；同时 cgroup 的 memory.current 减去 RSS 峰值的差值需要保持正余量，余量低于百分之十即触发预警。二五年上半年内存超限类事故同比降七成，复盘归因中 MaxRAMPercentage 基线覆盖率的提升是第一贡献项。

### 5.3 疑难场景的排查路径

仍出现容器内存问题的 Java 应用按序排查：第一步确认 JDK 版本与小版本（决定容器感知能力），第二步确认启动参数中是否有显式 -Xmx 覆盖了百分比机制（历史配置残留的常见形态），第三步用 jcmd VM.native_memory baseline 与 detail-diff 对比堆外增量、定位是直接内存还是线程栈膨胀，第四步检查 -XX:MaxDirectMemorySize 是否未设而默认等于 Xmx（Netty 场景的直接内存翻倍陷阱）。四步排查的命令模板与输出解读示例存放在运行时 Wiki 的"容器内存专项"页面，值班人员遇到疑难案例应先对照该页历史案例再开新工单，案例库中已有十六个已归档的容器内存故障，覆盖了九成以上的常见形态。

## 6. 运行时故障排查

### 6.1 网络模式与端口映射故障

Docker 网络的默认模式是 bridge：daemon 创建 docker0 网桥，容器通过 veth 接入网桥、经 iptables MASQUERADE 规则出网，端口映射（-p）由 dockerd 在 nat 表写入 DNAT 规则实现。网络故障的高频形态有三类。第一类是容器间互访不通：默认 bridge 上容器名不能互相解析，公司基线要求服务间互访一律建自定义网络（docker network create app-net），自定义网络内置嵌入式 DNS、容器名即域名；排查时先 `docker network inspect app-net` 确认双方容器都挂在该网络，再从容器内 ping 与 telnet 分层验证。第二类是宿主机端口映射不通：先 `docker port <容器> <端口>` 确认映射关系，再 `iptables -t nat -L DOCKER -n` 看 DNAT 规则是否存在，规则丢失的典型原因是 firewalld 或网络策略服务重启时清空了 docker 写入的链，处置办法是重启 docker 服务重建规则链，该操作必须按 1.2 节评估 daemon 重启影响面。第三类是子网冲突：自定义网络的默认地址池与办公网 VPN 网段重叠时会出现"容器访问内网某网段莫名走错路"，基线要求建网络时显式 `--subnet` 指定已登记的免冲突网段。

### 6.2 daemon 级故障与日志

daemon 失联（docker ps 无响应、超时）时不要急于重启 daemon，先分层取证：`journalctl -u docker --since "10 min ago"` 看 daemon 日志确认是卡死还是崩溃，`systemctl show docker -p PID` 配合查看 dockerd 进程的线程与内存状态，再看 /var/lib/docker 目录所在盘是否写满（历史案例中 json 日志写满数据盘导致 daemon 全部调用阻塞）。确认必须重启后，重启前执行 `docker ps -q` 导出容器清单留档，重启后核对清单中容器是否按重启策略自动拉起，未拉起的逐一查明退出原因。daemon 配置错误导致起不来的场景，恢复路径是按标准模板重建 daemon.json 而不是手工逐行猜改，模板由配置中心版本化管理，这就是 1.1 节强调配置必须回炉到配置管理工具的原因。

### 6.3 健康检查与编排联动

单机容器的自愈能力由 HEALTHCHECK 指令与重启策略组合提供：`HEALTHCHECK --interval=30s --timeout=3s --retries=3 CMD curl -f http://localhost:8081/actuator/health || exit 1` 让 daemon 周期探测应用端点、连续三次失败把状态置为 unhealthy，配合编排工具或巡检脚本对 unhealthy 容器执行重建。两个使用要点：其一，探的是应用真实健康度而不是端口通断，Java 应用建议探 actuator/health 且健康实现里只检查进程自身（外部依赖的检查放 readiness 语义，与 K8s 手册的探针红线一致）；其二，运行在 K8s 上的容器不需要镜像内 HEALTHCHECK（探针由编排层接管），双份健康检查逻辑互相打架的案例在 K8s 手册已有记载，混合部署场景按部署形态裁剪。

## 7. 监控与告警

### 7.1 指标采集与告警基线

容器指标的采集由 cAdvisor 承担（每宿主机部署，与 node exporter 同机），采集 CPU、内存、网络 IO 与块设备 IO 的容器级时序，docker stats --no-stream 作为人工快照命令使用、不作为监控来源。告警基线五项：单容器内存使用达限额百分之九十持续五分钟（P2，内存超限前兆）；容器十分钟内重启超过三次（P2，on-failure:5 连续触发的表现）；宿主机 /var/lib/docker 所在盘使用率超过百分之八十（P2，参照 3.3 节定位）；宿主机 docker daemon 重启事件（P1，意味着业务全量重启）；单容器日志文件写入速率异常（配合 3.2 节的日志治理）。所有告警的处置动作必须回写到告警工单，闭环率纳入值班组月度指标。

### 7.2 例行巡检与容量治理

每周例行巡检执行三项：docker system df -v 的磁盘分布趋势比对（上周与本周边化）；dangling 镜像与退出容器清理台账核对；以及容量台账中各容器限额与实际 P99 峰值的偏离度排名，偏离度超过两倍的容器进入容量例会调整议程。每季度的容量评审输出下季度宿主机采购与容器限额调整计划，评审输入包括业务增长预测、当前整机利用率分布与历史故障率。巡检与评审的全部产出物归档在运行时 Wiki 的容量页签下，作为容量决策的唯一依据来源，任何口头承诺的调整不具执行效力。
