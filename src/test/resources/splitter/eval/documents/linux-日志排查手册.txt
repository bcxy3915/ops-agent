一、日志体系总览：syslog 与 journal 双轨

Linux 主机上的日志体系是新旧两套机制并存的格局，排查前先确认目标主机上服务跑在哪套体系里，这是所有排查动作的第一步。老一代体系是 syslog 家族，由 rsyslog 守护进程按配置把内核与各设施的日志写入文本文件，文本全部集中在 /var/log 目录下，其中 CentOS 系列的系统综合日志文件名是 messages，Ubuntu 系列对应的是 syslog，两套命名在线上环境混用，排查脚本必须对两个文件名做兼容处理；认证与登录类事件的文件在 CentOS 上是 secure，Ubuntu 上是 auth.log，同样是同一类内容的双命名；内核环形缓冲区的日志用 dmesg 命令查看，缓冲区在重启后清空，持久化版本落在 /var/log/dmesg，这意味着宿主机突然崩溃后要在重启前抢救缓冲区内容，否则内核留下的最后遗言会永久丢失，值班人员对疑似内核崩溃的机器有一条铁律：重启之前先把 dmesg 输出重定向保存到远端。

新一代体系是 systemd journal，由 journald 守护进程收集全部单元的标准输出、标准错误与 syslog 事件，按二进制结构存储，配套 journalctl 命令检索。二进制结构带来的核心优势是元数据完备：每条日志自带产生它的单元名、进程号、主机名与可信的时间戳，因此 journalctl 可以按服务名、时间窗、优先级任意组合过滤，这是文本日志做不到的；代价是文件不能直接用文本工具打开，必须通过 journalctl 检索。两套体系的关系不是互斥而是接力：journald 收集一切，rsyslog 从 journald 接走一部分按规则写入文本文件，因此同一条日志经常既能在 journal 里查到也能在文本里查到，只是检索手段不同。判断一条服务日志去哪查的依据是服务的启动方式，systemd 托管的服务其 stdout 与 stderr 默认全部进 journal，服务自身写文件的那些需要去应用目录找，这个判断在排查开始前必须先做，否则会浪费时间在错误的地方翻找。

应用自定义日志是第三块版图。常见路径按应用类型有固定惯例：Nginx 在 /var/log/nginx，MySQL 在 /var/log/mysql，自研 Java 应用集中在 /app/logs 或 /data/logs，具体路径以各应用的部署文档为准，值班平台的主机档案里登记了每台机器的应用清单与日志路径。应用日志的格式由应用自己决定，排查前先 tail 看几条摸清字段结构再动手，直接套用标准日志的列序假设是新手最常见的翻车点。应用日志与系统日志的时间戳经常不一致，应用写的是 UTC 时间而系统日志是本地时间，差八小时的坑在容器化环境里尤其常见，多源日志对齐之前必须先核对时区，时间对不齐的排查结论全部不可信，这一条写在排查清单的第一项。

判断一个日志文件是否还在活跃写入有两个快速手法。第一种是 ls -lht 看 mtime，修改时间停在几小时前的文件大概率已经轮转或服务挂了；第二种是 tail -f 挂上去观察是否持续滚动，结合前者可以区分服务已死与日志切走两种情况。文件轮转的痕迹是同名文件带数字后缀，最新的历史是 messages 之类加 .1 后缀，更老的加 .2，再老的压缩成 .gz。有一个高频的误操作需要提前打预防针：看到 .gz 后缀先解压再 grep 是浪费磁盘与时间的双重错误，标准做法是用 zgrep 直接在压缩文件里检索，本手册在历史日志检索章节会展开这套压缩包内检索命令的完整用法。另外提醒一点，ls 看到日志文件体积是零不代表没日志，正在被进程持有的文件被误删后就表现为零可见但内容仍被句柄锁住，这类句柄泄漏场景用 lsof 配合加deleted 标记排查。

二、登录与安全日志的爆破排查

登录审计的核心文件是 /var/log/secure 或 /var/log/auth.log，两者是同一类内容在不同发行版上的命名。这一类文件记录全部认证事件：成功与失败的密码登录、公钥登录、sudo 提权、用户创建与删除、登录会话开关。爆破排查的标准入口是检索失败登录关键字，执行 grep 'Failed password' /var/log/secure 可以列出全部失败登录的原始记录，每条记录自带时间戳、目标用户名、来源 IP 与尝试的端口，这是爆破证据链的第一环。原始记录通常海量，单台被爆破的主机一夜可以积累上万条，逐条阅读没有意义，统计聚合才是正确姿势：管道接 awk 提取来源 IP 列再接 sort 与 uniq -c 计数，最后按计数降序排列，一条组合命令就输出按次数排序的来源 IP 榜单，榜单头部某个 IP 出现几百次即可基本判定为爆破源，判定后把证据原样保存进工单再实施封禁。

失败登录的记录文件有专门的结构化来源，lastb 命令读取 /var/log/btmp 文件展示全部失败登录尝试，输出按时间倒序，每行含用户名、来源 IP 与时间窗。lastb 与 grep secure 的区别值得分清：lastb 的数据来自二进制结构的 btmp 文件，输出已经过格式化，适合快速浏览失败登录的时间分布与总量；grep 方式作用于文本日志，适合精细过滤与复杂统计。两者互为印证，爆破工单的取证模板要求两个来源各截取一份。配套的 last 命令读取 wtmp 展示成功登录历史，last -F 显示完整时间戳，排查爆破时必须同时看成功侧：如果失败的洪水里混进了几条 Accepted 记录，说明爆破已经成功，事件性质立即从骚扰升级为入侵，响应动作随之升级，先取证再处置，重置凭据、排查持久化后门、评估横向移动范围按序展开。

排查成功登录的检索串是 grep 'Accepted password' 加 grep 'Accepted publickey'，拿到结果后逐条核对是否合法人员从合法跳板机登录，核对的依据是堡垒机的审批记录与人员白名单。查新增账号用 grep 'new user' 检索，入侵者建后门账号的动作会在这里留下 useradd 的痕迹，同时交叉比对 /etc/passwd 的文件修改时间与内容。需要特别提醒的是历史命令审计的局限：用 history 查看命令痕迹时，历史记录可以被环境变量 HISTFILE 指向空文件的手法绕过，入侵者普遍掌握这个技巧，因此入侵溯源不能只依赖 history，要把 shell 历史、认证日志、进程痕迹、网络连接四个维度拼起来，单维度证据链的结论都要打折扣。sudo 提权的审计同样在 secure 文件里，检索关键字是 session opened 与 COMMAND 加等号，排查异常提权时按用户名过滤后逐条核对授权清单。

爆破的常态化治理依赖两个配置。第一个是 sshd 的登录失败锁定，通过 pam_faillock 或 pam_tally2 配置连续失败阈值，平台标准是连续五次失败锁定账户十五分钟，让在线爆破在速率上失去意义；第二个是登录方式收敛，线上主机的密码登录默认全部关闭，只允许公钥登录且禁止 root 直连，这一条让 Failed password 的洪水在生产上只剩下服务自带的本地认证尝试，真正从互联网暴露的入口统一收到跳板机。值班人员收到爆破类告警的处置口径是固定的：先取证据再封 IP，封禁动作在防火墙层执行而不是从应用层动手，事后把 IP 与证据归档到安全组的黑名单库。误封业务方正常机器的案例出过一次，根因是把业务方的健康检查 IP 判成了爆破源，处置口径因此追加了核对环节：封禁前用资产系统反查 IP 归属，云厂商与合作伙伴的 IP 段清单每周同步。

三、journalctl 的检索技巧

journalctl 的价值在于多维度过滤的组合能力，排查服务故障的第一入口永远先想它。按单元过滤是最高频用法，journalctl -u 加服务名可以只看指定 systemd 单元的日志，例如 journalctl -u order-service --since today 输出该服务今天的全部日志， -u 参数后面接的是单元名，单元名可以不带 .service 后缀；配合 -n 200 只看最近两百行，配合 -f 持续跟随，组合起来就是服务状态监控的完整工具链。服务启动失败的场景中，标准顺序是先用 systemctl status 看状态与最近几条日志，再用 journalctl -u 按更长时间窗回看完整过程，启动失败的根因几乎都在 journal 里，因为 systemd 托管服务的 stdout 与 stderr 全部进 journal，包括应用崩溃前的最后几行输出，这几行往往就是死因。

按时间窗过滤是故障回放的核心能力。journalctl --since "2026-10-30 09:00" --until "2026-10-30 09:15" 精确回放十五分钟窗口内的全部日志，故障时间窗的还原完全依赖这个用法，since 与 until 也支持 today、yesterday 这类相对表述，值班人员在处理任何带明确时间点的工单时的固定动作就是先用时间窗切割出故障片段再分析。按优先级过滤用 -p 参数，journalctl -p err 过滤错误级别及以上，快速筛查一夜之间系统报过什么错，级别从 emerg 到 debug 共八级，常用组合是 err 加 crit。三类过滤可以自由组合成一条命令，单元加时间窗加优先级同时限定，输出就是某服务在某时段的某级别日志，这种组合过滤是文本日志体系的 grep 加 awk 组合难以企及的效率，也是本手册把 journalctl 定位为服务故障第一入口的原因。

journal 自身的磁盘占用是巡检必查项。journal 默认按持久化配置运行，日志落在 /var/log/journal，若配置为 volatile 则只存内存重启即丢，线上主机统一要求持久化模式。查占用用 journalctl --disk-usage，输出当前 journal 的磁盘总量，平台巡检阈值定为主机日志盘的百分之二十，超限即处置。收缩占用有两类参数：--vacuum-time=7d 删除七天前的旧日志，按时间维度收缩；空间维度对应的参数把总量压到五百 MB 以内，两个参数可以单独也可以并用，用 vacuum 系列收缩比手工删除 journal 文件安全得多，手工删文件会让 journald 的空间记账失真，删完之后 journald 可能继续按旧水位写入，出现磁盘已清但占用不降的假象。除这套收缩子命令之外还有 SystemMaxUse 配置项写进 /etc/systemd/journald.conf，让 journal 自动限制上限，平台标准模板配置了自动上限加巡检双保险，自动上限是常态约束，手动收缩是超限后的修正动作。

journald 与 rsyslog 的存储分工常引发排查困惑，这里把规则讲透。journald 有自己的保留策略，默认策略下空间紧张时旧日志先被挤掉，所以 journal 里查不到一周前的记录是正常现象，不是日志丢了；文本文件走 logrotate 的保留策略，保留周期独立配置，所以老记录要去文本文件里找。排查的时间越久远越依赖文本侧：三天内的故障优先查 journal，元数据齐全检索快；一个月前的回溯直接查文本加压缩文件。两套体系的保留周期在主机档案里登记，值班人员查不到日志时先确认是不是已经超过了对应体系的保留窗口，把查不到误判成被删是入侵方向的常见误报来源，安全事件的定性必须有证据支撑，超期缺失是运维常识不是可疑行为。

四、日志轮转与磁盘占用治理

日志的磁盘占用治理是轮转体系的日常运转问题。轮转由 logrotate 统一管理，配置主文件在 /etc/logrotate.conf，按应用拆分的子配置在 /etc/logrotate.d 目录下每个应用一个文件，cron 每天驱动一次主程序。子配置文件里有三个必查项：rotate 保留份数决定历史文件留几轮，compress 决定历史文件是否压缩成 gz，weekly 或 daily 决定轮转周期。轮转机制有两种切割方式，copytruncate 先复制再清空原文件，优点是不需要通知应用，缺点是复制与清空之间有一个短窗口内新写入的日志会随清空丢失；postrotate 方式直接改名原文件再给应用发信号让它重开文件句柄，没有丢失窗口但要求应用响应信号，写死文件句柄不响应的应用会在改名后继续往旧句柄写，日志看起来停了实际全在写入已经改名的文件。两类方式的选择按应用行为定，排查时发现轮转后日志不更新，第一怀疑就是句柄没重开，用 lsof 看进程持有的文件句柄即可证实。

磁盘被日志打满是线上高频事件，处置顺序有讲究。先用 df 确认打满的分区，再用 du 逐层下钻定位大文件，日志盘的元凶几乎都在 /var/log 下；找到大文件后注意区分文件是否仍被进程持有，被持有的文件删除并不释放空间，句柄还锁着 inode，磁盘占用分毫未动，这类文件必须通过重启对应服务或给进程发信号让它释放句柄才真正回收，删完不降的现场先执行 lsof 检索带 deleted 标记的句柄再决定下一步。紧急窗口内用 truncate 清空活跃日志文件比删除安全，清空保留句柄让应用继续写入。日志盘治理的常态手段是收紧 rotate 份数加开启 compress，把三十天的文本历史压到磁盘可承受的体积，治理动作完成后在巡检台账登记该主机的保留周期变更，避免下次回溯时按旧周期找日志。

logrotate 的另一个经典故障是轮转静默失效。logrotate 每次运行会在 /var/lib/logrotate 状态文件里记录每个配置的上次轮转时间，如果状态记录的时间戳异常或者权限配置错误，轮转条件永远不满足，文件就一天天膨胀下去。排查命令是 logrotate -d 加配置文件路径做干跑，dry run 模式输出判定过程但不实际执行，会明确说明该配置为什么今天不轮转；确认需要立即轮转的用 logrotate -f 强制执行一次。新增应用接入轮转的规范路径是在 /etc/logrotate.d 下新建子配置，内容包含路径、周期、份数、压缩与切割方式五要素，新建后必须做一次干跑验证再等自然周期触发，接入台账里登记子配置文件名。应用方直接用 rm 清理日志文件而不配轮转的做法一律在巡检中挂账，无轮转的日志文件只涨不缩是打满事故的种子。

journald 侧的占用治理在第三章的收缩参数之外还有一个系统性配置值得说明。journald.conf 里的 SystemMaxUse 控制总配额，SystemKeepFree 保证磁盘保留多少剩余空间，RuntimeMaxUse 控制内存中的运行时配额，平台标准模板把 SystemMaxUse 设为日志盘的三分之一并强制开启持久化，让 journal 的增长有硬上限。云主机的小规格机型日志盘只有二十 GB，journal 配额与文本轮转份数要一起压缩，模板按机型分档，小机型 journal 上限五百 MB 加文本保留七天，标准机型上限两 GB 加文本保留三十天。轮转与配额的参数不是一成不变的教条，按磁盘规格分档的原则比具体数字更重要，数字随硬件演进调整，分档逻辑保持稳定。

五、历史日志的压缩检索

历史日志的形态以压缩文件为主，logrotate 开启 compress 后历史文件逐轮转成 gz 压缩包，磁盘收益大约是文本体积的十分之一，这是三十天以上历史得以保留的技术前提。压缩文件不能用普通文本工具直接处理，配套的工具家族是 z 开头系列：zcat 直接输出压缩文件内容，zgrep 在压缩文件里检索等价于 gunzip 加 grep 的组合但一步完成且不落盘解压文件，zless 分页浏览压缩文件。以该命令带 -i 参数检索 app.log.4.gz 中的 error 为例，直接命中压缩包里的错误行并保持压缩包原样，整个过程不产生任何中间解压文件。先解压再查再删的三步走是典型的错误流程，多两个步骤意味着多占十倍磁盘空间与两倍的 IO 消耗，历史窗口内逐个文件解压的脚本一旦忘了清理就把日志盘打满，这类事故在多个团队重复出现过，规范层面直接禁止批量解压。

压缩包内检索的成本与压缩算法有关，gz 是流式压缩，检索必须从头解压到目标位置，单个大文件的检索耗时与文件体积成正比。批量检索一个月的历史时把这条压缩检索命令放进 find 或 for 循环逐个文件执行，全部历史都扫一遍的耗时可能到分钟级，应急场景下可以用时间约束先收窄文件范围再检索，因为轮转文件的序号天然按时间排列，序号越大的文件离现在越远，按时间窗定位目标文件的序号段再只对段内文件执行检索，可以少扫大部分文件。检索结果里的行号与时间戳的对应关系要注意：检索输出的行号是压缩文件内逻辑文本的行号，不是任何全局坐标，跨文件的统计必须按文件分组处理，把多个文件的检索结果直接 sort 到一起再统计时间分布的错误在值班记录里出现过。

压缩历史的另一种高频用法是取证导出。安全事件与故障复盘都要求把历史证据打包归档，标准的导出命令是 zcat 加管道接重定向把某个压缩文件还原成文本落盘，或者直接把压缩文件本体拷贝归档，后者保留原始证据形态，取证场合优先拷贝本体，工作场合为了后续检索方便才做还原。归档目录的命名规范是主机名加日志类型加时间窗，归档动作在工单内留痕。涉及资金与审计的日志在归档保留上有单独的合规要求，本手册合规章节统一说明。历史检索的最后一条经验留给排查者：检索一无所获时先核对文件保留窗口再怀疑检索方式，文件可能早就被轮转清理了，按保留周期表确认文件应该还在的，再回头检查检索命令的关键字拼写与大小写参数。

六、留存合规与操作纪律

线上日志的最低留存要求按日志类型分档：应用错误日志保留三十天，访问日志保留十五天，认证日志保留九十天，涉及资金与审计的日志保留一年以上并要求异地归档副本。留存周期是合规红线，删除任何日志前必须先对照本表确认不违反要求，安全事件的取证窗口经常落在事发后数周，被清理的日志等于被销毁的证据。应急场景下磁盘打满需要紧急清理时，宁可先把日志打包转移到归档存储再清理本地，也不做就地删除，归档动作本身就是工单记录的一部分。轮转配置的任何收紧调整都要对照留存表复核，曾经有团队为了救磁盘把认证日志的 rotate 份数砍到两轮，一个月后的安全事件取证时发现关键窗口已被清掉，教训直接促成了留存表与本手册的联动，轮转配置变更工单现在必须附留存合规的核对结论。

操作纪律是排查安全的底线，第一条铁律是动手改任何东西之前先把相关日志拷贝到安全位置。排查过程中重启服务、清理文件、切换配置都可能让现场证据消失，标准动作序列是取证、变更、复核三段式，取证段把相关时间窗的日志原样拷贝，变更段执行处置，复核段对照留档验证处置效果。第二条是任何清理动作必须可追溯，删了什么、什么时候删的、依据什么工单，写进值班日志。第三条是日志中的敏感内容要保护，排查手机号、身份证号等字段时的脱敏要求同样适用于日志导出场景，向外发送日志样本前先做脱敏处理，sed 的正则批量替换可以完成打码，导出脚本里内置了脱敏步骤的不要绕过。三条纪律的共同目的是保证任何一次排查动作在事后都能被完整还原，能被还原的处置才是负责任的处置。

本手册的边界需要明确声明：主机侧的应急响应流程，包括 CPU 飙高、IO 打满、内存不足的场景化处置步骤，由应急响应兄弟文档规定，本手册只在与日志证据相关的环节与之衔接；具体应用中间件的日志格式与排障方法在各自组件的专项文档中维护。日志排查是几乎所有故障处理的必经环节，掌握本手册的双体系检索、爆破审计、轮转治理与压缩检索四项基本功后，值班人员应当能够在十分钟内完成一次标准的事件证据固定，这是本手册对读者的最低能力要求，部门季度演练会按这个标准做实操考核。
