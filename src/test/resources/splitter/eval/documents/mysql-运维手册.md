## 1. 总则

### 1.1 编制目的与适用范围

本手册用于规范公司生产环境 MySQL 数据库的运维工作，覆盖高可用架构管理、从库延迟治理、在线 DDL 与大表变更、主从一致性校验、误操作跳过与慢查询治理六个方面，是数据库运维组与业务研发处理数据库相关事务的强制依据。本手册适用于 MySQL 8.0 版本、InnoDB 存储引擎、一主多从加半同步复制加自动切换组件的标准架构，预发环境参照执行但可放宽审批层级。SQL 开发规范、备份恢复体系与性能压测标准由其他专项文档承接，本手册不重复展开，涉及跨文档场景以本手册的变更审批与操作纪律为准。所有高危操作（DDL、批量数据变更、位点类操作）必须走变更审批并安排在低峰窗口，这一原则无例外条款，紧急止血场景也须事后两小时内补单并说明，事后不补单的操作无论结果如何均按违规处理。业务方与外包人员一律通过数据库自助平台执行查询与申请，直接登录数据库实例的权限仅授予数据库运维组成员并全程审计。

### 1.2 变更分级与审批链

数据库变更分为三级：一级变更包含实例重启、主库切换、在线 DDL、单表千万行级数据变更、复制位点操作与参数基线调整，须提前三个工作日提单，经数据库组负责人、业务方负责人与 DBA 值班经理三方审批后在凌晨零点到六点执行；二级变更包含索引新增、小范围数据订正、监控阈值调整，一个工作日审批；三级变更为纯查询类工单与知识库更新，登记生效。任何一级变更必须附带完整的回滚方案，回滚方案须具体到反向 SQL 或恢复步骤，写「出问题再定」的变更单一律驳回。变更执行人须在执行前完成三项检查：确认目标实例与工单一致（防止串库）、确认备份已就绪且可恢复、确认影响面评估中的行数与实际预估偏差在 10% 以内。变更完成后 24 小时内回填验证记录，包含执行时长、影响行数与关键指标前后对比，验证记录缺失的变更计入团队合规率考核，合规率低于 95% 的团队冻结一级变更权限一周并组织复盘。

## 2. 高可用架构管理

### 2.1 标准架构与切换组件

生产数据库标准架构为一主两从起步，主从间开启半同步复制，至少一个从库确认接收 binlog 后主库才向客户端返回提交成功，防止单点故障时的数据丢失。故障切换统一由高可用组件托管，公司主用方案在 8.0 集群上基于管理节点比选最新位点的从库提升为新主，切换决策的仲裁节点三台部署防脑裂，切换动作全自动执行，人工仅做事后确认，端到端切换目标时长为 60 秒内完成、应用连接池 120 秒内完成收敛。切换组件的配置任何修改都属一级变更，特别是退化参数与剔除名单（failover 黑白名单），误把真实主库加入黑名单的后果是故障时拒绝切换。每日巡检核对高可用组件与数据库实例的心跳状态，心跳异常超过 5 分钟触发 P2 告警，高可用组件失明期间的人工切换须走紧急预案并逐级电话确认。半年执行一次真实故障演练：在预发与生产各选一个非核心实例制造主库宕机，验证切换时长与数据零丢失目标，演练报告归档并推动发现问题的整改，连续两次演练超标的集群挂牌督办。

### 2.2 复制状态管理

从库的复制状态通过 SHOW REPLICA STATUS 判读，三个关键位点字段是管理入口：IO 线程读取位点、SQL 线程回放位点与瞬时延迟秒数，IO 位点与回放位点的差值反映 relay log 积压，秒数字段只反映回放延迟的粗略值，精确判断须对比位点到毫秒级时间戳。复制线程状态必须为双 Yes，任一线程断开即触发 P2 告警，值班同学按错误信息分类处置：网络类错误检查主从间链路与防火墙，账号密码类错误核对近期密码轮换记录，日志被清理类错误（提示找不到 binlog 文件）说明从库落后太多而主库已过期删除，只能按第三章流程重建从库。半同步复制的退化监控同样重要：rpl_semi_sync_master_status 由 ON 转 OFF 说明半同步退化成了异步，主库在无人知晓的情况下失去了防丢数据保护，该指标翻转即 P2 告警，处置为检查从库 IO 线程与网络往返延迟。从库的过滤复制规则（库表级复制过滤）禁止在未经评估时变更，过滤规则不一致是主从数据不一致的隐蔽来源，季度一致性校验时会专门覆盖。

## 3. 从库延迟治理

### 3.1 延迟观测与根因定位

从库延迟的日常观测以延迟秒数指标为主、位点差为辅，告警基线为延迟超过 30 秒触发 P3、超过 60 秒触发 P2、影响核心业务读路径的实例超过 120 秒升级 P1。延迟根因按出现频率排序有三类，第一类是大事务：从库回放大事务期间无法并行拆分，一个影响百万行的 UPDATE 能让延迟瞬间从零跳到数十分钟，定位方式是查看从库当前正在执行的事务与 relay log 中剩余事务的大小分布，控制大事务要从源头治理，研发规范明确要求单事务影响行数不超过一万，批量任务必须拆批提交，每批之间保留间歇让从库追平。第二类是从库回放并行度不足：单线程回放已不适应公司写入规模，须开启多线程回放并配置 replica_parallel_workers，该参数默认为 4，公司基线按从库规格统一设置为 8，高写入集群的核心从库调整到 16，配合 replica_parallel_type=LOGICAL_CLOCK 与 binlog_transaction_dependency_tracking=WRITESET 获得更好的并行度，WRITESET 基于行级依赖关系判定事务可并行，比传统序列号方式在典型业务混合负载下可提升两到三倍回放速率。第三类是从库资源争抢：读写分离场景下从库承载大量分析查询，IO 与内存被抢占导致回放变慢，此类问题的处置是把重查询迁移到专用统计从库或限制其并发，从库机型规格不得低于主库是容量基线的硬性要求。

### 3.2 多线程回放配置与验证

replica_parallel_workers 的调整属于一级变更，调整前必须核对从库的 MySQL 版本与事务隔离级别，参数在线生效需要重启复制线程（STOP REPLICA 后 START REPLICA），操作须在低峰执行并预告延迟短暂波动。并行度并非越大越好，超过 16 后协调开销开始侵蚀收益，且 WRITESET 模式下主库 binlog 体积会有约 5% 的增长，容量规划须计入。参数调整后 24 小时为验证期，验证方法为对比调整前后同负载时段的延迟秒数峰值与 relay log 积压深度，若延迟无明显改善应回退参数并转向大事务治理或资源扩容方向排查，避免在无效调参上反复消耗窗口。多线程回放开销存在一个隐性坑：并行回放保留了每个并行组的事务锁关系，个别带外键依赖的业务库在并行度提高后出现回放报错，因此外键使用较多的库保持 replica_parallel_workers=4 的保守值并在容量台账中登记为特殊实例。所有从库的回放配置每季度核对一次基线，偏离基线的实例生成整改工单，配置漂移本身也纳入月度巡检通报。

## 4. 在线 DDL 与大表变更

### 4.1 在线 DDL 的适用边界

常规加索引、加列等轻量变更使用原生在线 DDL 执行，语句必须显式携带 ALGORITHM=INPLACE, LOCK=NONE 子句以强制走在线路径，若优化器无法满足该路径会直接报错而不是退化成锁表，这是保护线上流量的第一道闸。即便是在线路径，加索引仍需全表扫描重建，亿级大表在业务高峰执行会造成 IO 抖动与主从延迟放大，因此超过一亿行的表禁止直接执行在线 DDL，改走在线变更工具流程。变更时长预估公式为表空间大小除以磁盘顺序写吞吐再乘以 1.5 系数，预估超过 4 小时的变更必须拆窗口或使用在线变更工具的可暂停特性跨窗口续跑。所有 DDL 变更执行期间，值班同学同步监控从库延迟与 threads_running，延迟超过 60 秒或连接数异常抬升时立即评估暂停或终止，原生 DDL 不可暂停，终止代价是全部回滚，这也是大表变更优先选用在线变更工具的核心理由。执行完成的 DDL 必须在同一变更单内附执行时长与影响行数，并在 48 小时内观察该表的查询耗时分布无劣化后才算闭环。

### 4.2 gh-ost 大表变更流程

gh-ost 通过创建影子表加 binlog 增量同步加原子切换的方式完成变更，全程业务无感且可随时暂停可回滚，公司规定超过 30GB 或一亿行的表变更一律使用该在线变更工具。标准执行命令中限流参数为强制项：--max-load=Threads_running=50 控制变更期间的负载上限，超过即暂停拷贝；--critical-load=Threads_running=200 为熔断阈值，达到即自动退出并保留现场；同时配置 --chunk-size=1000 控制每次批量拷贝行数，--throttle-query 按业务特征定制额外限流探针。变更执行流程为：变更单审批通过后先在预发完成同结构演练并记录拷贝速率，生产执行时从低峰窗口启动，观察前 30 分钟的拷贝速率与主从延迟，确认稳定后转入后台运行并每小时巡检一次，全部切换动作前再次核对复制延迟为零。该工具的妙处是发现异常可以随时停止且影子表不影响线上，但注意停止后残留的影子表与 binlog 订阅线程须清理，清理脚本已内置在运维工具集。切换完成后 24 小时内保留旧表（该工具默认不立即删除），确认业务指标平稳后清理，清理动作本身也在变更单内记录。

### 4.3 海量数据清理规范

禁止一次性执行 DELETE FROM 大表 WHERE 条件删除千万行数据，此类操作会同时引发 binlog 洪峰、从库延迟雪崩与长事务风险，公司多起延迟事故的直接诱因就是无批次的全量删除。标准做法是循环小批量删除，每批固定为 DELETE FROM 表名 WHERE 条件 LIMIT 2000，执行后判断影响行数，不为零则间歇零点一秒继续下一批，影响行数为零说明目标数据已删尽、循环终止，LIMIT 2000 这一批量是平衡删除效率与 binlog 压力的经验值，单批的 binlog 体积约在数百 KB 量级，从库回放单批耗时可控。删除脚本必须由数据库运维组统一执行，脚本内置每批次间隔与最大执行时长保护，执行期间监控从库延迟，延迟超过 30 秒自动暂停、恢复后自动续跑，业务方自建脚本一律不批准。删除完成后表空间不会自动回收，InnoDB 的空闲页仅标记复用，需要物理回收时用在线变更工具重建该表，重建流程与 4.2 节一致，重建期间磁盘须预留原表 1.2 倍的临时空间，磁盘余量不足 30% 的实例先扩容再重建。归档类长期任务统一登记在数据生命周期平台上，平台按月生成待清理清单并跟踪执行进度，未登记的手工清理视为违规。

## 5. 主从一致性校验

### 5.1 校验机制与执行周期

主从一致性不能靠假设，必须周期性用工具实测。公司统一使用 pt-table-checksum 执行校验，该工具在主库上以会话级低优先级运行，按块切分表数据计算校验和并写入校验结果表，校验结果表本身通过复制通道传播到从库，从库回放后对同样的数据块重算校验和，两边的差值即不一致证据，全程对线上流量影响极小。校验周期为：核心交易库每周全量校验一次，一般业务库每月一次，新上架从库与重建后的从库在恢复流量前必须完成一次校验通过，这是硬性关卡，跳过校验直接放量的从库一旦带了脏数据会污染读写分离的读结果。校验执行统一由平台任务调度发起，避开业务高峰与备份窗口，单库校验时长超过两小时的自动拆分到多个夜间窗口。校验结果自动汇总为一致性报告，报告中每张表给出不一致块数与差异数量，任何非零差异即生成 P2 工单，工单必须闭环到根因与修复双完成。历史数据显示，不一致的高发根因是从库被写入（开发误连从库写数据）、复制过滤规则不一致与位点跳过后的残留差异，前两类靠权限与流程封堵，第三类正是 6.1 节强制校验闭环的原因。

### 5.2 差异修复流程

发现差异后使用 pt-table-sync 执行修复，该工具按校验结果定位差异行并生成最小化的修复 SQL，在从库执行后重新校验确认归零。修复流程的纪律为：先备份差异行（工具可导出修复前数据），再在测试库演练修复 SQL，最后在从库执行，修复期间的从库暂停承接读流量直至复检通过，防止读到半修复状态。pt-table-sync 的执行模式必须选择以从库为执行目标的同步方向，方向搞反会把从库的脏数据同步回主库，造成灾难性扩散，该参数在平台封装层已做防呆。若差异行数超过一万行，修复方案须升级为按表重建：用备份加 binlog 恢复的方式重建该从库，比逐行修复更可靠且时间可控。修复完成后的一周内该表加密校验一次，确认无新增差异。每次不一致事件都须复盘并归档，复盘结论转化为流程改进项（如收紧从库写权限、增加过滤规则巡检），季度末汇总不一致事件的趋势，连续两季度出现同类根因的纳入流程缺陷专项治理。

## 6. 误操作跳过与紧急恢复

### 6.1 复制中断的跳过处置

从库回放报错 1062（主键冲突）或 1032（记录不存在）时的标准处置流程为：先用 SHOW REPLICA STATUS 确认报错事务的具体位置与语句，评估该事务的业务影响并联系业务方确认跳过是否可接受；确认后执行 STOP REPLICA，再执行 SET GLOBAL sql_replica_skip_counter=1 跳过当前这个事务，然后 START REPLICA 恢复回放，观察回放是否继续报错，若同一错误连续出现须停止机械跳过并转入根因分析。sql_replica_skip_counter 的含义是跳过主库 binlog 中的 N 个事件组，设为 1 即跳过当前卡住的事务，该参数只在传统位点复制模式下生效，GTID 模式下应使用空事务注入方式达到同等效果，两种模式的跳过命令不可混用。跳过操作本身属于二级变更但在紧急场景可先执行后两小时内补单，跳过后的闭环动作是强制的：48 小时内对受影响的库表执行 pt-table-checksum 定向校验，发现差异立即按 5.2 节流程修复，跳过校验闭环的跳过操作按未完成处置处理并考核到人。曾发生值班同学连续跳过 17 个事务后未做校验，三个月后业务对账才发现从库少了一批退款记录的事故，该案例已固化为「跳过必校验」铁律写入新员工培训。

### 6.2 误操作与数据恢复

误删除数据的恢复依赖备份加 binlog 的组合：以最近一次全量备份为基线恢复到临时实例，再用 mysqlbinlog 从备份位点回放到误操作发生前的精确位点，--start-position 与 --stop-position 的取值通过误操作时间与 binlog 内容双向交叉确认，恢复出的数据经业务方核对后回补生产。全量备份每日凌晨执行，binlog 保留至少 7 天并异地归档，恢复演练每季度一次并记录端到端耗时，RTO 目标为核心库 2 小时。误操作的预防优于恢复：生产库的 DELETE 与 UPDATE 必须带 WHERE 且开启平台的安全审计拦截（无 WHERE 的删改语句直接阻断），影响行数预估超过一万的手工语句须走工单二次确认。误操作发生在主库且已被从库复制时，跳过机制（6.1 节）配合一致性校验完成善后；发生在从库的单边误操作则直接按 5.2 节修复。所有误操作事件无论是否造成损失都须当天在故障平台登记，登记内容包含时间线、影响面与后续改进项，月底汇总为误操作专项通报，连续三个月零误操作的团队给予合规加分。

## 7. 慢查询治理

### 7.1 慢日志与阈值管理

慢查询日志是治理的唯一事实来源，公司基线要求慢日志全局开启且 long_query_time 统一从 1 秒收紧到 0.5 秒，核心交易库进一步收紧到 0.2 秒，阈值收紧采用灰度方式推进，每次收紧观察一周的日志增量，确保采集量不影响日志盘容量与采集管道吞吐。log_queries_not_using_indexes 同步开启，让未走索引的查询即使耗时未超阈值也进入日志视野。long_query_time 的调整通过 SET GLOBAL 在线生效并写入参数基线持久化，调整属二级变更。慢日志按小时滚动切分并投递到分析平台，分析平台用 pt-query-digest 做指纹化聚合，输出按总耗时排序的 TOP 榜单，每条指纹包含执行次数、平均耗时、95 分位耗时与样例 SQL，比人工翻日志更适合趋势跟踪。每周五产出慢查询周报，周报锁定 TOP 20 指纹并指定责任人与优化期限，优化完成以该指纹的周聚合耗时下降 50% 为量化标准，连续两周未改善的指纹升级到数据库组与业务方负责人的双周会对齐。治理成效的度量指标为慢查询总量与核心库 P99 查询耗时，两个指标纳入平台月报。

### 7.2 执行计划判读与索引变更

慢查询优化从执行计划判读入手，EXPLAIN 输出重点看四列：type 列出现 ALL 即全表扫描，是优化的第一优先级；key 列为 NULL 说明没用上索引；rows 列的预估扫描行数与表规模对比判断选择率；Extra 列出现 Using filesort 或 Using temporary 说明排序与临时表未消化，常见于多列排序与分组场景。索引失效的常见形态须逐项排除：字符串列传数字导致的隐式类型转换、前导模糊匹配 LIKE 以百分号开头、复合索引不满足最左前缀、OR 连接了无索引列。确认需要新增索引时走二级变更流程，小表直接用在线 DDL 加索引，大表按 4.2 节在线变更流程执行，新增索引后须复核执行计划确实生效且该表的写入耗时无劣化，同时评估冗余索引（已有同前缀索引的新索引大概率冗余）避免无谓写放大。索引下线同样走变更流程，下线前用平台查询画像确认该索引 30 天内无访问再执行。每月输出索引健康度报告，内容包含无访问索引清单、重复索引清单与 TOP 慢查询改善进度，报告评审产出的治理项录入工单系统跟踪，闭环率纳入数据库组的月度考核。
