## 1. 总则

### 1.1 编制目的与适用范围

本手册用于统一公司生产环境 Redis 实例的运维标准，覆盖部署架构、内存与淘汰策略配置、持久化管理、主从复制与哨兵故障转移、日常巡检以及应急处置六个方面，是中间件运维组执行 Redis 相关变更与值班处置的强制依据。本手册适用于 Redis 6.2 与 7.0 版本、以一主二从加三节点哨兵为标准形态的实例，预发与压测环境参照执行但可适当放宽审批层级。公司另有专项文档承接的内容不在本手册范围内，包括集群模式的槽位迁移类操作、大 Key 与热 Key 的专项治理流程以及缓存穿透击穿等业务侧防护设计，相关需求请按文档索引转至对应手册执行，禁止参照本手册跨场景套用操作步骤，避免检索与执行混淆。新入职值班同学须在导师带教下完整阅读本手册并通过内部考试后方可独立值班，考试不合格者仅可执行只读类巡检操作，不得参与任何写操作与变更执行。

### 1.2 职责分工与审批要求

Redis 日常巡检、告警响应与工单处理由各业务线 SRE 值班岗负责，实例级参数变更（包括淘汰策略调整、持久化参数修改、哨兵配置变更）统一由中间件运维组执行，业务方仅有申请权与知情权，不得直接登录实例执行 CONFIG SET 等写操作，该要求已通过堡垒机命令审计与 ACL 账号权限双重手段落地。所有变更按影响面分为三级：一级变更为实例重启、主从切换、淘汰策略与持久化开关调整等高危操作，须提前两个工作日在变更平台提交申请，经中间件组负责人与业务方负责人双重审批后在凌晨零点到六点的低峰窗口执行；二级变更为监控阈值调整、备份策略微调等低风险操作，一个工作日审批即可；三级变更为巡检计划调整等纯管理动作，登记即可生效。任何一级变更都必须附带书面回滚方案与验证清单，缺少任一项的变更单将被平台直接驳回，历史上曾发生因回滚方案缺失导致切换失败后恢复耗时超过四小时的事故，该教训已纳入公司案例库并作为新员工培训必学案例。

## 2. 部署架构与容量规划

### 2.1 标准部署形态

生产环境 Redis 统一采用一主二从三哨兵的标准架构，主从实例与哨兵进程分机部署，禁止将哨兵与 Redis 同机混部，防止机器故障时监控者与被监控者同时失效。机型统一为 16 核 32GB 内存、本地 SSD 盘的虚拟机，Redis 端口统一 6379、哨兵统一 26379，数据目录固定为 /data/redis，日志目录为 /data/redis/log，目录结构由初始化脚手架统一生成，禁止手工创建临时目录存放快照或追加日志文件，备份与传输一律经由备份平台中转。三台哨兵必须分布在三个不同的故障域并按机房机架打散，两台从库同样跨机架部署，确保单机架掉电时仍有一从可用、哨兵集群整体仍能达成多数派仲裁。实例创建时由工单系统自动分配实例名与 DNS 别名，应用侧禁止直连 IP，必须通过哨兵感知的连接方式获取当前主库地址，这是故障切换后业务无感恢复的前提条件，新应用接入评审时架构组会专门核查连接串配置，未使用哨兵接入方式的应用不予上线。

### 2.2 容量与水位规划

容量规划遵循内存水位不超过 70% 的红线，即 maxmemory 配置为物理内存的 70%（当前标准机型即 22GB），剩余部分预留给 fork 写时复制的内存开销、输出缓冲区与碎片膨胀，禁止将 maxmemory 直接配置到物理内存上限。容量评估以业务方提报的预估键数量、平均 value 大小与 TTL 周期为输入，由中间件组出具评估报告，键数量按一年增长 50% 的保守系数放大，评估结果超过单实例 70% 水位的应直接申请拆分为多实例而不是等量扩内存。QPS 层面要求单实例压测基线不低于 8 万，连接数按峰值乘以 1.5 倍冗余规划并设置 maxclients 上限为 10000，超出的连接申请将在巡检中被标记为容量风险项并要求业务方整改连接池配置。每季度末执行一次容量复盘，将实际增长曲线与年初评估对比，偏差超过 20% 的实例须重新评估并在下季度完成治理，连续两个季度触碰 85% 水位的实例列入强制拆分清单，拆分方案按一级变更流程审批执行。

## 3. 内存管理与淘汰策略

### 3.1 淘汰策略选型规范

内存达到 maxmemory 上限后实例将按 maxmemory-policy 配置执行键淘汰，策略选型错误是缓存类故障的高发根因，本节给出强制选型规范。纯缓存场景（数据可全部从下游数据库重建）统一配置 allkeys-lru，即在全键空间按最近最少使用原则淘汰，该策略对热点键天然友好，是公司内占比最高的标准配置；业务键全部设置了 TTL 且允许优先淘汰临近过期的冷数据时，可申请使用 volatile-ttl，该策略只在设置了过期时间的键中选择剩余存活时间最短的淘汰，适合数据自带明显时效性（如临时验证码、会话票据）的业务，申请时须在变更单中说明键空间全量带 TTL 的证据。元数据存储类实例（数据无法从下游重建、丢失即构成事故）必须配置 noeviction，该策略在内存写满后拒绝一切写请求并向客户端返回 OOM command not allowed 错误，业务侧会立即感知写失败，这正是保护数据完整性的设计意图。曾发生业务方在元数据实例上误配淘汰策略导致活跃元数据被静默淘汰、服务启动时读不到注册信息而批量失败的事故，因此淘汰策略变更一律按一级变更管理，变更单必须注明实例用途分类并由中间件组复核确认。

### 3.2 内存碎片治理

碎片率通过 INFO memory 输出中的 mem_fragmentation_ratio 字段判读，该值等于 used_memory_rss 与 used_memory 的比值，健康区间为 1.0 到 1.5。比值大于 1.5 说明碎片严重，典型诱因是大量不同大小的对象交替创建与删除，常见于频繁变更结构的 JSON 缓存业务；比值小于 1.0 则意味着部分内存已被交换到磁盘 swap 分区，属于最高优先级告警，此时任意命令的尾延迟都会剧烈抖动，须立即按第七章应急预案处理。碎片超过 1.5 的实例应先评估是否可启用 activedefrag yes 自动碎片整理，该特性要求 Redis 4.0 以上版本且 CPU 有 20% 以上余量，启用后整理动作在主线程分片执行，相关强度参数由中间件组统一模板下发，禁止业务方自行调整。临时性的碎片整理可在低峰期连接实例执行 MEMORY PURGE 手动触发一次，执行前须确认 instantaneous_ops_per_sec 已回落到当日峰值的三成以下，整理期间的 P99 延迟会有毫秒级抬升，需提前在值班群通报。碎片治理动作完成后 24 小时内，值班同学须复查碎片率是否回落到 1.3 以内并归档巡检记录，未回落的实例升级为容量问题重新评估拆分。

### 3.3 过期与删除的执行语义

Redis 对过期键的清理采用惰性删除与定期采样删除结合的方式，定期采样的强度由 active-expire-effort 参数控制，默认值为 1，取值范围 1 到 10，大量短 TTL 键（如秒级过期的限流计数器）的业务建议调到 7 以上，否则过期键会在键空间堆积造成内存虚高，巡检时通过 INFO stats 中的 expired_keys 增速与 keys 总数的比值来验证清理能力是否匹配写入节奏。删除类命令的阻塞风险同样纳入规范：删除 String 类型的大值或元素数上万的集合键时禁止使用 DEL，必须使用 UNLINK 异步回收，DEL 在主线程同步释放内存，曾造成线上实例 800 毫秒的停顿并触发上游调用方线程池排队；配合 lazyfree-lazy-expire yes 与 lazyfree-lazy-server-del yes 两个参数，可让过期删除与隐式删除路径同样走异步释放。上述参数属于实例模板的标准配置项，新建实例由脚手架默认开启，存量实例在年度配置基线巡检中逐台核对，与基线不一致的实例自动生成整改工单，整改完成率纳入中间件组季度考核指标。

## 4. 持久化管理

### 4.1 RDB 快照策略与风险

快照持久化将某一时刻的全量内存数据以紧凑二进制格式落盘，生产实例统一按 save 900 1、save 300 10、save 60 10000 三条规则配置自动触发，分别对应 900 秒内至少 1 次修改、300 秒内至少 10 次修改、60 秒内至少 10000 次修改，快照生成统一通过 fork 子进程完成的 BGSAVE 路径执行，任何情况下禁止在实例上执行阻塞主线程的 SAVE 命令，该命令已列入堡垒机拦截清单。fork 的耗时与实例内存体量正相关，公司标准机型的实测数据是每 GB 约 20 毫秒，22GB 实例 fork 一次约 400 毫秒，期间主线程需要复制页表，若实例存在大量小键则页表项更多、耗时更长，这正是大实例高峰期出现周期性毫秒级抖动的常见根因。系统层面必须确认 vm.overcommit_memory=1，否则内存接近上限时 fork 可能因内核内存分配策略失败直接报错，导致快照静默丢失，该内核参数由装机基线统一固化。快照方式的固有风险是两次快照之间的写入会在宕机时丢失，恢复演练数据表明 22GB 实例加载快照文件约需 3 分钟，业务方在接入评审时须书面确认该丢失窗口可接受，不可接受的业务应结合追加日志持久化并将数据安全性要求写入容量评估报告。

### 4.2 AOF 配置与重写管理

追加日志持久化以追加方式记录每条写命令，公司生产基线统一配置 appendfsync everysec，即每秒强制刷盘一次，最多丢失一秒内的写入，是性能与安全的工程折中；对丢失容忍度为零的金融类实例可申请 appendfsync always，但每条命令同步刷盘的磁盘 IO 开销会使写入吞吐下降约一半，申请须附加业务负责人签批的书面说明。该日志文件按 auto-aof-rewrite-percentage 100 与 auto-aof-rewrite-min-size 4gb 触发后台重写，即文件较上次重写后体积翻倍且超过 4GB 时由子进程重写压缩，重写期间的新写入会同时暂存到重写缓冲区，若实例写入量大且恰逢业务高峰，缓冲区膨胀会放大内存占用并造成 fsync 阻塞，因此重写窗口由中间件组统一管控在凌晨两点到四点之间，高峰期如需干预可手动执行后台重写命令提前触发或等待自动窗口。Redis 7.0 实例统一开启 aof-use-rdb-preamble 混合持久化，重写产物的前半段为全量快照数据、后半段为增量命令，恢复时先加载快照再回放命令，兼顾加载速度与丢失窗口，6.2 实例升级到 7.0 时必须在升级检查单中逐台核对该开关，漏配会导致恢复时长增加三倍以上。

### 4.3 备份与恢复演练

备份策略上，所有生产实例在每日凌晨三点由备份平台通过 BGSAVE 生成当日快照文件后拷贝至异地备份存储，保留 30 天，同时追加日志文件按小时增量归档，备份成功率纳入平台日报，连续两天备份失败的实例自动生成 P2 工单并抄送值班经理。恢复演练是持久化配置是否真正有效的唯一验证手段，公司要求每季度对随机抽取的 10% 生产实例执行一次恢复演练：在隔离环境拉起同版本空实例，加载最近一次备份快照并回放增量日志，记录从进程启动到可对外服务的完整时长与数据一致性抽检结果，抽检方式为随机抽取 100 个业务键与源实例逐一比对值与 TTL。演练报告须在一周内归档至知识库，连续两个季度演练失败的实例将被挂牌督办并由中间件组负责人牵头整改。历史上一次演练曾暴露追加日志文件在归档传输中被截断的问题，导致回放到文件末尾报 Bad file format 错误，该问题推动备份平台增加了全量文件的 md5 校验环节，此类教训已固化为演练检查单的固定条目，任何团队不得以资源紧张为由豁免季度演练。

## 5. 主从复制与哨兵故障转移

### 5.1 复制机制与 repl-backlog-size 调优

从库通过执行复制指向命令（指向主库地址 6379）建立复制关系，首次同步为全量同步：主库 fork 子进程生成全量快照传输给从库，期间的新写命令暂存在复制缓冲区，从库加载完快照后继续回放缓冲区内容，之后进入命令传播阶段。网络闪断重连后，从库会携带自身复制偏移量 offset 请求续传，若主库的复制积压缓冲区内仍保留该 offset 之后的数据，则走部分重同步只补发增量，否则退化为一次全量同步。复制积压缓冲区大小由 repl-backlog-size 参数控制，默认值仅 1MB，对写入 QPS 上千的实例来说只够承接断线几百毫秒，公司基线统一调整为 64MB，写入量特别大的交易核心实例调整到 256MB。该参数调优的收益在跨机房容灾场景尤为明显：主从跨机房部署时网络抖动概率高，backlog 偏小的实例一次 30 秒的网络闪断就会触发全量同步，多个从库同时全量同步会形成复制风暴，主库同时执行多次 BGSAVE 造成 IO 与 fork 双重压力，2024 年双十一前压测阶段曾复现该问题，backlog 调大后全量同步次数从日均 17 次降为 0。参数修改可通过 CONFIG SET 在线生效，随后必须写入配置文件持久化，防止实例重启后回退到默认值。

### 5.2 哨兵部署与 quorum 设置

哨兵集群以三节点奇数部署为最低标准，核心监控与仲裁配置统一为 SENTINEL monitor mymaster 主库IP 6379 2，其中末尾的 2 即法定票数，表示至少两个哨兵都认定主库无响应、达成客观下线结论后，集群才会进入故障转移流程。该票数取值必须少于哨兵总数且通常设为过半：取值过大将导致网络分区时无法达成客观下线、故障转移迟迟不触发，业务中断时间被人为拉长；取值过小则单台哨兵的误判（如哨兵自身所在机器高负载导致心跳超时）就可能引发误切换，公司统一三节点配票数为 2、五节点配 3，禁止运维人员私自调整。主观下线判定阈值 down-after-milliseconds 统一配置 5000 毫秒，即单个哨兵连续 5 秒 ping 失败就将实例标记为主观下线，过短的阈值在主库执行慢查询或追加日志重写的瞬时抖动下会造成误判，过长的阈值会拉长整体切换时长，5 秒是结合公司实例负载特征校准后的经验值。failover-timeout 统一 60000 毫秒，定义一次故障转移的超时上限，超时后哨兵会重新发起选举。哨兵自身的配置文件由部署脚手架统一生成，哨兵进程重启后会自动从配置文件恢复监控关系，因此任何哨兵配置变更都必须以落盘为准，仅在运行态执行 SENTINEL 命令而不落盘的修改在哨兵重启后会丢失，这是每周巡检的重点核对项。

### 5.3 故障转移过程与 replica-priority 干预

故障转移由哨兵 leader 执行，leader 通过哨兵间的选举产生，需要获得超过半数哨兵的同意票，随后按固定顺序挑选新主库：先过滤掉已下线、与主库断连时间过长的从库，再按 replica-priority 参数升序排序挑选，数字越小优先级越高，若优先级相同则比较复制偏移量，偏移量大（数据更新）者优先，全部从库的优先级配置均为 0 时哨兵将拒绝执行切换并持续告警。从库优先级配置是运维侧控制切换结果的核心抓手：跨机房容灾架构中，我们把与主库同机房的从库优先级设为 100、异地从库设为 200，确保故障时优先在同机房提升新主，避免业务写路径突然跨机房导致延迟抬升；对配置偏低、硬件偏旧的从库则显式设为 0，使其永不参选。切换完成后哨兵会向其余从库下发复制重定向命令指向新主、把旧主降级为其从库，应用侧通过 SENTINEL get-master-addr-by-name 重新获取主库地址并重建连接。每次自动切换后，值班同学须在 10 分钟内完成三项验证：新主可写、从库复制状态为 online、客户端连接池已完成切换，并将切换时间线录入故障台账，任何一项验证失败立即按应急预案升级处理。

### 5.4 常见复制故障处置

复制类故障的判读入口是 INFO replication 输出。master_link_status 字段显示 down 且持续时间超过 60 秒时，说明主从间链路中断，排查顺序为防火墙策略变更、主库实例是否存活、masterauth 密码是否在近期密码轮换中被遗漏，密码不一致时从库日志中会出现 MASTER <-> REPLICA sync 相关的报错，处置后复制会自动重连无需人工干预。master_replid 发生变化说明从库刚经历了一次全量同步而非部分重同步，若该现象频繁出现，第一嫌疑就是 repl-backlog-size 不足以覆盖断线窗口，其次是主从间网络质量，可通过网络团队的重传率监控交叉确认。复制延迟通过主从复制偏移量的差值衡量，差值持续超过 10MB 时应检查从库所在机器是否有批量离线任务抢占磁盘 IO，必要时将离线任务迁移或限流。处置复制故障的原则是优先恢复部分重同步能力、避免触发新一轮全量同步，确需手动全量同步（例如从库数据损坏）时，必须错峰逐台执行，严禁多台从库同时执行复制重置，历史处置经验表明，主库同时 fork 两次以上即可能出现秒级写入阻塞。

## 6. 日常巡检与监控告警

### 6.1 每日与每周巡检项

每日巡检在上午十点前完成，值班同学通过巡检平台自动采集的全量指标逐实例核对五项内容：内存使用率是否低于 85%、碎片率是否在 1.0 到 1.5 区间、主从复制状态是否为 online、rejected_connections 当日增量是否为零、SLOWLOG GET 10 中是否存在超过 10 毫秒的慢命令。慢日志中出现 KEYS、SMEMBERS 大集合、LRANGE 全量拉取等命令时，须当天定位来源客户端并通知业务方整改，整改闭环率是巡检质量的核心指标。每周巡检在周五下午完成，内容更深一层：核对 evicted_keys 周增量与淘汰策略是否匹配业务预期、实例键总数环比增长率是否异常（超过 20% 需要业务方书面说明）、追加日志重写是否在既定窗口内正常发生、备份文件 md5 校验是否全部通过。每周巡检还须抽取至少一台哨兵执行 SENTINEL masters 核对配置漂移，确认 down-after-milliseconds、法定票数、parallel-syncs 等关键参数与基线一致，巡检结果统一录入运维平台，连续两周异常未闭环的实例自动升级为 P3 工单并抄送中间件组负责人。

### 6.2 监控指标与告警阈值

监控采集通过 Exporter 拉取 INFO 全量输出，告警规则统一维护在告警平台，核心阈值经过多轮故障复盘校准：实例 CPU 使用率连续 5 分钟超过 80% 触发 P2 告警；内存使用率超过 90% 触发 P2、超过 95% 升级为 P1，P1 要求值班同学 5 分钟内响应；碎片率超过 1.5 或低于 1.0 触发 P3，低于 1.0 因涉及 swap 风险同时短信通知值班经理；主从断连时长超过 60 秒触发 P2；单分钟 rejected_connections 超过 100 次触发 P3 并关联 maxclients 与连接池配置核查；主从复制偏移差超过 10MB 触发 P3。instantaneous_ops_per_sec 与延迟分位数指标用于容量趋势分析而非直接告警，P99 延迟连续 3 个周期环比上涨 50% 时生成容量预警工单。所有 P1、P2 告警的处置必须在 30 分钟内于告警平台回填处理记录，包括触发原因、影响面评估与后续动作，处置超时将自动升级通知到部门接口人。告警阈值本身的调整属于二级变更，须走变更单审批后由中间件组统一修改，禁止值班同学为消除告警噪音直接在平台侧临时屏蔽阈值，屏蔽告警超过 24 小时的行为按事故管理办法追责。

## 7. 变更管理与应急处置

### 7.1 变更分级与操作纪律

除总则中的三级分级外，本节明确 Redis 的高危命令清单与操作纪律：FLUSHALL、FLUSHDB、CONFIG SET maxmemory 0、手动解除复制从属关系的操作、SHUTDOWN 以及任何形式的淘汰策略变更均列入高危命令，高危命令在堡垒机侧配置双人复核弹窗，操作者与复核者必须为不同自然人，单人无法完成执行。实例重启必须安排在低峰窗口且提前导出最新快照文件作为兜底，重启顺序为先从后主，主库重启前须确认哨兵已将切换目标锁定在健康从库，避免重启期间发生非预期切换。参数类变更执行后 30 分钟为观察期，观察期内值班同学不得离开监控面板，重点观察连接数恢复曲线、复制偏移差收敛情况与错误日志，任何异常立即执行回滚方案而不是继续观察。变更完成后 24 小时内须回填变更记录，包括变更前后关键指标对比截图，未回填的变更单会影响团队的变更合规率考核，合规率低于 95% 的团队将被暂停一周的变更权限并组织复盘整改。

### 7.2 典型应急场景处置

场景一，实例写满且策略为 noeviction，业务侧批量报 OOM command not allowed 错误：值班同学第一时间确认是否为业务突发写入导致，若是则临时扩容 maxmemory（不超过物理内存 85%）止血，同时通知业务方限流，根治方案走容量拆分流程；若为内存泄漏型增长（used_memory 单调上涨且键总数不涨），则按内存问题流程定位写入来源并通知业务方处置。场景二，碎片率低于 1.0 触发 swap 告警：立即通知业务方将读流量切换到从库以降低该实例压力，等待内存换回物理内存，严禁此时执行重启，swap 状态下重启加载会极度缓慢，历史上曾把恢复时长从 5 分钟拖到 40 分钟。场景三，主从反复全量同步：先检查 repl-backlog-size 是否为基线值 64MB 以上，再核对主库是否正在经历追加日志重写（重写期间 fork 与 IO 压力会拖慢命令传播），临时止血可将从库的重连错开，根治需按容量流程评估主库写入压力。所有应急场景处置完成后 48 小时内产出复盘报告，复盘结论须转化为巡检项或告警规则的更新，确保同类问题可被更早发现。
