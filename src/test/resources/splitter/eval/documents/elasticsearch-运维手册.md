## 1. 总则

### 1.1 集群现状与运维目标

公司当前运行三套 ES 集群：日志集群二十节点（热温冷三层）、检索集群十二节点（服务商品与订单检索）、指标集群六节点，全部为自管部署。日志集群日均写入约八十亿条、存储增量四十 TB，是三套集群中运维压力最大的一套，其磁盘水位、写入队列与分片分布需要每日巡检。ES 运维的三个核心目标是：写入链路不因容量或配置问题中断（业务日志丢一条都要追责）、查询链路不因慢查询或深分页拖垮节点、存储成本按生命周期逐层下降。为达成这三个目标，本手册将操作纪律固化为每日三巡检、每周例会、每季度演练三个层次的机制，值班人员对巡检结果的记录要求是必须留档到运维 Wiki，不允许口头交接。

### 1.2 操作纪律与访问控制

所有涉及集群级设置（cluster settings）、路由分配、索引模板的变更必须在变更窗口执行，变更前必须确认 `GET _cluster/health` 为 green（单副本集群至少要求所有主分片已分配、无 UNASSIGNED 分片）。任何路由级操作（分片迁移、节点下线）执行前必须先冻结自动均衡，操作结束后恢复，具体命令在第二章给出。访问控制方面，8.x 集群已开启 security realm，业务方通过 API Key 接入、按索引前缀授权，禁止共用超级账号；7.17 集群通过 IP 白名单加内网隔离过渡，升级到 8.x 时必须完成 API Key 迁移评审。值班人员处置故障时可以临时调整集群设置止血，但恢复动作必须在处置完成后立即执行并留档，"改了设置忘了改回去"是二四年 ES 事故复盘中的头号高频根因。

## 2. 集群健康与分片管理

### 2.1 健康状态判读

集群健康由 `GET _cluster/health` 的 status 字段给出三档判读：green 表示全部主分片与副本分片均已分配；yellow 表示主分片齐全但存在未分配的副本，双节点以上的集群出现 yellow 通常意味着单节点离线或副本无法找到可分配的目标节点；red 表示存在未分配的主分片，此时部分索引数据不完整、查询结果缺失，属于 P1 级事件。值班人员看到 red 的第一动作不是重启任何东西，而是执行 `GET _cat/shards?h=index,shard,prirep,state,unassigned.reason` 找出 UNASSIGNED 分片清单，再逐项核对未分配的常见成因——磁盘水位超限、单节点分片数超上限、节点版本不兼容等，成因不同处置路径完全不同。red 状态的处置黄金窗口是十五分钟，超时未恢复即启动集群级应急预案并通知业务方降级。

### 2.2 分片再平衡与节点维护联动

节点滚动重启或网络抖动恢复后，master 会自动触发分片再平衡，把副本在节点间重新铺开，这本身是健康行为，但在大存储量集群上会产生密集的磁盘读写压力、挤占业务查询带宽，公司日志集群曾在节点批量重启后因再平衡洪峰导致写入拒绝持续两小时。因此纪律要求任何可能触发大规模分片移动的操作之前，必须先冻结自动再平衡：`PUT _cluster/settings` 设置 `cluster.routing.rebalance.enable` 为 `none`，操作完成并确认稳定后恢复为 `all`。配套的并发控制参数是 `cluster.routing.allocation.cluster_concurrent_rebalance: 2`（集群级并发再平衡分片数）与 `cluster.routing.allocation.node_concurrent_recoveries: 2`（单节点并发恢复数），大集群默认值偏高时可以在维护窗口临时下调。这些设置的临时调整必须记录在变更单的"恢复清单"一栏，值班交接时逐项核对，恢复动作执行后要在群里回报。

### 2.3 分片数治理

单节点分片数上限的管理经验值是不超过一千，超过后 master 维护分片表的内存与 CPU 开销明显上升、集群元数据操作变慢，极端情况会引发 master 脑裂级别的元数据风暴。公司日志集群历史上峰值单节点一千六百个分片，当时 cluster state 更新耗时超过十秒、新建索引频繁超时，治理手段有三板斧：清理无主的僵尸索引（接入方已下线但索引未删）、把保留期外的索引转入 delete 阶段、以及对小分片做 shrink 合并。分片大小层面，公司基线把单分片控制在 10GB 到 50GB 区间，低于 10GB 的分片是纯粹的元数据负担，该基线的实现方式在索引滚动切换章节展开。业务方新建索引模板必须走平台工单，平台组按"分片数等于预估日增数据量除以 30GB 向上取整"的经验公式审核，超出公式的申请需要说明查询并发依据。

## 3. 索引生命周期管理

### 3.1 索引滚动切换机制

日志类索引必须基于滚动切换机制滚动，而不是按日期手写索引。rollover 的工作方式是：写入方永远写一个固定别名（如 logs-app-write），当别名背后的索引满足滚动条件时，ILM 自动创建新索引并把别名指向它，旧索引自然转为只读并进入下一生命周期阶段。相比"按天名建索引"的土办法，滚动切换的优势是滚动条件基于分片实际大小而不是日历天数，能保证每个分片都落在 10GB 到 50GB 的健康区间——流量小的索引三天滚一次、流量大的索引两小时滚一次，分片大小却始终均匀，这是分片治理的根基机制。公司基线的滚动条件是 `max_primary_shard_size: 50gb` 与 `max_age: 30d` 双阈值取先到者，30d 上限只是兜底防小流量索引无限期不滚。

基线 ILM 策略由平台组统一下发，日志类标准模板为：hot 阶段执行滚动切换；warm 阶段（滚动后两天进入）执行 shrink 把分片收缩为单分片、并执行 `forcemerge` 把段合并为 `max_num_segments: 1`，副本数从一下调为零（热层已有冗余副本换节点，温层靠快照兜底）；delete 阶段（三十天）执行删除。策略下发命令为 `PUT _ilm/policy/logs-policy`，样例如下。业务方可以申请延长保留期，但必须同步提交存储成本预估与预算编号，超过九十天的需求一律引导转投对象存储而非留在 ES 中。

```json
PUT _ilm/policy/logs-policy
{
  "policy": {
    "phases": {
      "hot":   { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "30d" } } },
      "warm":  { "min_age": "2d", "actions": { "shrink": { "number_of_shards": 1 }, "forcemerge": { "max_num_segments": 1 } } },
      "delete":{ "min_age": "30d", "actions": { "delete": {} } } }
  }
}
```

### 3.2 滚动故障与验证

索引滚动切换卡住是 ILM 机制的典型故障，表现为单索引持续膨胀远超 50GB 仍不滚动，多数根因是步骤失败后 ILM 进入 ERROR 状态（常见触发是滚动时磁盘水位封锁了新索引创建）。排查命令是 `GET logs-app-000001/_ilm/explain`，输出的 failed_step 字段直接给出卡住步骤，处置方式是修复根因后执行 `POST logs-app-000001/_ilm/retry`。新接入业务上线第一周必须人工验证滚动两次以上，方法是用 `GET _cat/indices/logs-app-*?v` 观察索引大小序列是否符合"最新索引从零增长、旧索引冻结在阈值附近"的形态。公司还曾出现别名指向漂移事故：业务方自作主张把读写写在同一别名上，滚动切换后读请求仍打在旧索引导致"查不到新日志"的工单，因此平台规范强制读写别名分离，写入方拿 write 别名、查询方拿不带后缀的读别名。

## 4. 磁盘水位与只读保护

### 4.1 三级水位线机制

ES 通过三级磁盘水位线自动保护存储：low 水位线（默认磁盘使用率 85%）触发后，调度器不再把新分片分配到该节点；high 水位线（默认 90%）触发后，调度器开始把该节点的分片迁往其它节点，产生大量磁盘与网络 IO；flood_stage 水位线（默认 95%）触发后，该节点上的所有索引（含系统索引）被强制加上只读封锁，写入请求直接报错 `FORBIDDEN/12/index read-only / allow delete`（实际报错串为 FORBIDDEN/12/index read-only / allow delete api），这是 ES 防止磁盘被写穿的最后防线。三级水位的行为特征必须烂熟于心：85% 的表现是"新索引分配倾斜"、90% 的表现是"集群 IO 莫名升高（正在搬分片）"、95% 的表现是"业务写入批量报错"。值班巡检时看到任一节点磁盘曲线逼近 85% 就要评估扩容或清理，拖到 90% 以上就意味着留给你的处置时间只剩水位爬升到 95% 的那几分钟。

### 4.2 洪泛水位应急处置

洪泛水位线触发时的标准处置时序为：第一步确认影响面，`GET _cat/allocation?v` 找出超水位节点并通知接入方写入已失败、让业务方暂停重试风暴（客户端无限重试会放大故障）；第二步腾空间，优先清理可快速释放的空间，包括手动删除已过保留期的索引（`DELETE logs-app-2025.10.01` 需双人复核）、清理温层已 forcemerge 完的中间产物、以及把冷索引发往快照后删除本地副本；第三步解除封锁，磁盘使用率回落到 90% 以下后，ES 不会自动解锁只读状态，必须手动执行 `PUT <索引名>/_settings` 并设置 `index.blocks.read_only_allow_delete: null` 逐个索引解除，实际操作中通常按前缀批量解除全部受影响索引；第四步业务确认，解除后由接入方验证写入恢复并观察五分钟拒绝数。整个时序的目标是二十分钟内恢复写入，值班组每月一次的应急演练科目就是洪泛水位保护场景。

洪泛水位应急演练的科目设置有讲究：演练环境复用预发集群的只读副本数据，人为把一块盘的使用率推到百分之九十五以上触发封锁，随后让值班人员盲演完整时序，考核点有四个——是否第一时间通知业务方暂停重试、解除封锁前是否确认水位回落到安全线、是否遗漏了按前缀批量解除的效率要求、以及解除后是否漏了五分钟观察期。二五年三月的季度演练中，首次参加的值班人员在第二步就踩了坑：磁盘还在 94% 时就去解锁，结果内核立刻重新加锁，白折腾一轮还产生了误导性的告警噪音。真实案例的复盘要点也一并归档：写入失败期间业务方的重试风暴会把无效请求放大八倍，通知措辞里必须包含"请立即暂停重试"的字样，这是演练与实战反复验证过的沟通模板。

### 4.3 水位线调优与预防

大磁盘节点使用默认水位线会浪费可观测容量：一台 38TB 的数据节点，95% 洪水线意味着留出近 2TB 的保护空间，而 1TB 级小盘节点 95% 只留 50GB、很容易被一次写入毛刺击穿。公司日志集群的实际调整是把三档水位放宽为 low 档 90%、high 档 93%、洪水位档 95%，通过 `PUT _cluster/settings` 的 `cluster.routing.allocation.disk.watermark.low/high/flood_stage` 持久化设置，调整的审批前提是节点磁盘全部为 16TB 以上规格且已有快照兜底。预防机制上，容量巡检盘面每日输出"按当前增量预计多少天达到 90%"的推演值，低于十四天即触发扩容流程；同时滚动切换机制配合 ILM delete 阶段保证常规情况下"每天新增多少、到期删除多少"的进出平衡，一旦业务方临时上调保留期而未同步扩容，值班组有权在容量例会上回退其保留期申请，这条权力写进了平台与业务方的接入协议。

## 5. 写入拒绝与刷新调优

### 5.1 写入拒绝的判读与止血

ES 的写入请求先进入节点上的写线程池排队，队列长度固定为二百（7.x）、并发线程数等于核数，当 CPU 持续高位或磁盘 IO 饱和导致消费速度跟不上生产速度时，队列打满、新请求被拒绝，指标体现为 `GET _nodes/stats/thread_pool` 中 write/bulk 的 rejected 计数增长，业务侧表现为写入被拒绝的异常报错。拒绝不是错误而是背压信号，正确的响应顺序是：先看拒绝是否集中在个别节点（分片倾斜或大查询独占该节点资源）、再看节点 CPU 与磁盘 await 是否异常、然后评估是客户端侧还是服务端侧的优化。止血手段按影响从小到大排列：客户端侧降批量与并发（bulk 单批从 30MB 降到 15MB、写入并发减半）；服务端临时扩容写入节点；最后才是动索引级的刷新参数，且必须在事后恢复。

### 5.2 批量写入与刷新参数调优

写入吞吐的三个关键参数构成一组联动配置。第一个是 bulk 请求体积：公司压测结论是单批 5MB 到 15MB 之间吞吐最高，超过 30MB 后协调节点内存压力上升、超时反而增多，接入方按每批五千条或 10MB 两者先到为准设置。第二个是 `index.refresh_interval`，默认 1s 表示每秒生成一个可见的 Lucene 段，刷新本身不做持久化但会占用 IO 与 CPU，日志场景把可见性要求放宽到 30s 后，段生成速率下降三十倍、写入吞吐提升约一倍、段数量大幅减少。第三个是 translog 策略：`index.translog.durability` 从 request 改为 async 表示 translog 异步刷盘、宕机窗口内最多丢五秒数据，日志类业务可接受，交易类业务禁止使用。导入型场景（全量重建、历史回填）的临时组合拳是：副本数设为 0、refresh_interval 设为 -1（完全关闭）、bulk 拉满、导入完成后依次恢复 30s 与副本数 1、最后对索引执行一次 `POST <索引>/_forcemerge?max_num_segments=1`。该组合已在索引重建流程中标准化，任何一项忘记恢复都会以另一种故障形态在几天后爆发（副本 0 忘改回来则是可用性隐患）。

### 5.3 forcemerge 的正确用法与禁忌

forcemerge 把索引的全部段物理合并为指定段数（通常 1），收益立竿见影：查询时需要打开的段文件 reader 数量下降、每次查询的合并开销消失、堆外内存中段元数据占用显著减少，对已转为只读的温冷索引是必做优化。但它的两个禁忌同样重要：其一，禁止对仍在写入的活跃索引执行 forcemerge，合并过程消耗大量磁盘 IO 与 CPU、直接拖垮写入链路，且后续新写入会继续产生新段、合并收益归零，唯一例外是导入完成后立即转为只读的场景；其二，禁止在集群 IO 已经吃紧时对大量索引批量执行，正确节奏是按索引串行、每个索引之间观察 IO 恢复再继续。公司标准做法是把 forcemerge 塞进 ILM 的 warm 阶段（3.1 节策略中已包含），由生命周期机制自动在索引转只读后触发，人工手动触发的场景仅限于应急重建后的一次性收尾，且必须在变更单中说明。

## 6. 深度分页与大查询治理

### 6.1 深分页问题与 10000 上限

from + size 是最直觉的分页方式，但 ES 的实现决定了它天生不适合深翻页：取第一万条之后的数据时，每个分片都要在内存里构建并排序完整的一万加 N 条结果、回传给协调节点做全局归并，页码越深、每个分片的内存与排序开销越大，恶意深分页可以直接把集群内存打穿。因此 ES 默认通过 `index.max_result_window` 限制 from+size 不能超过 10000，超出直接报错 `Result window is too large`，数值一万就是这个限制的具体体现，公司三次遇到业务方撞墙事件，每一次的业务诉求都是"导出全量对账数据"。

处置原则必须先分场景再给方案：如果业务诉求本质是"遍历全部数据"，答案是导出接口走 PIT 配合游标式翻页方案，或直接用滚动导出到对象存储，而不是调大窗口；如果业务诉求是"跳转到特定页"，应推动产品交互改造（限定排序键、按时间范围筛选后再浅分页）。平台组明确禁止业务方自行调大 `max_result_window` 绕过限制——历史上调到十万的生产事故中，三次深查询叠加就把检索集群两个节点打出 full GC。审批通过的例外场景必须配合熔断参数 `search.max_buckets` 与查询超时参数一起评估。

### 6.2 游标式翻页方案

search_after 是官方推荐的深遍历方案，工作原理是：每次查询携带排序键（通常是时间戳加唯一文档 ID 的复合键），返回结果最后一条的排序值作为下一页的游标入参，服务端从该排序位置继续向后取——它不跳页，因此没有"归并前一万条"的开销，页与页之间的复杂度恒定。配合 PIT（Point In Time）使用时，整个遍历过程基于同一份视图快照，中间的写入与合并不会导致文档漂移或重复，标准用法是先 `POST <索引>/_pit?keep_alive=5m` 拿到 pit id、之后每轮查询携带 pit 与游标参数。业务方接入游标导出必须遵守两条：每轮之间要读取响应中的 sort 值原样传递、不允许自己拼接；遍历完成后必须显式 DELETE pit，超时泄露的 PIT 会占用服务端资源。公司日志平台的导出功能已全量改造为 PIT 加游标式翻页方案，单次导出上限放宽到五亿条文档且集群毫发无损，该改造案例可在大查询治理 Wiki 找到复盘细节。

### 6.3 慢查询日志与治理例会

慢查询治理依托慢日志闭环。索引级慢日志阈值基线为 `index.search.slowlog.threshold.query.warn: 2s` 与 `index.search.slowlog.threshold.fetch.warn: 1s`，写法上 warn 级别用于观察、info 级别（500ms）只在专项排查时临时开启。慢日志的核心证据字段是 total_shards（该查询命中多少分片）与 took（耗时），公司日志集群的治理经验是：total_shards 超过两百的慢查询几乎全是时间范围过宽——时间过滤条件缺省或只给了日期没给时分，导致扫描三十天的全部索引，推动业务在查询模板中强制注入时间下界后，此类慢查询下降九成。每周慢查询例会对 top10 慢查询逐个给结论，高频反模式包括通配符前置的 terms 查询（改 wildcard 字段类型或 match_phrase）、高基数字段聚合未加 size 上限、以及 nested 查询深度嵌套（能用 flattened 替代就替代），每个反模式在治理 Wiki 都有改造范例，值班人员应能随口给出这些结论的出处。

聚合类大查询是慢查询治理中独立的一支，处置思路与检索类慢查询不同。聚合慢的典型特征是 took 耗时高但命中文档数很少甚至为零，说明时间花在桶生成与归并而不是文档扫描上；判读入口同样是慢日志，但证据字段从 total_shards 转向桶数与聚合类型分布。高频反模式有三类：terms 聚合作用于高基数字段（如用户 ID、订单号）且未加 size 上限，桶数逼近 search.max_buckets 的 65536 上限后被强制截断、结果错误且耗时极高；date_histogram 的间隔设得过细（秒级跨度拉三十天就是两百多万个桶）；以及多层嵌套聚合导致桶数按乘积爆炸。治理动作以查询模板改造为主：高基数维度改为先聚合到粗粒度再取明细的两段式查询、时间直方图按业务口径强制最小间隔为小时级，这两条约束已写入平台查询模板的默认值，存量查询通过例会逐步清理，二五年上半年聚合类慢查询的清零进度在治理看板上对全员可见。

## 7. 监控告警与值班

### 7.1 必告警项与阈值

ES 集群的强制告警基线共八项：集群状态非 green 持续五分钟（P1）；存在未分配分片（P1）；单节点分片数超过六百（P2，治理缓冲）；单节点磁盘使用率超过 85%（P2）、超过 93%（P1）；write/bulk 线程池 rejected 计数五分钟内增长（P2）；JVM 堆使用率超过 85% 持续十分钟（P2，GC 压力前兆，8.x 老年代 GC 表现需结合 GC 日志二次确认）；以及主分片同步延迟指标 refresh 延迟突增（P2）。JVM 堆的配置红线是不超过 31GB（压缩指针边界），超了反而性能下降，这是所有新节点评审的固定检查项。段内存通过 `GET _nodes/stats/indices/segment_memory` 每周采集一次，堆外内存异常增长往往先从这里显形，值班人员对它的例行观察是深挖堆外问题的第一入口。

### 7.2 快照与恢复演练

快照仓库统一使用对象存储（S3 兼容），注册命令为 `PUT _snapshot/logs_repo`，全量快照每日一次、增量每两小时一次，策略由 SL M（快照生命周期管理）统一驱动。快照的意义只有通过恢复演练才能兑现，公司基线要求每季度执行一次恢复演练：新建一个隔离集群，`POST _snapshot/logs_repo/<快照名>/_restore` 恢复最近一次全量加增量，验证抽样索引的文档数与检索结果一致性，演练报告归档并抄送业务负责人。二四年两次真实数据救援（一次误删索引、一次集群级数据损坏）都依赖季度演练中验证过的恢复流程，单次恢复耗时与成功率都有历史数据可查，这也是本手册把演练从"建议"升级为"基线"的原因。
