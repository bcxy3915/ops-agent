Redis 大 Key 与热 Key 治理规范

【编制人】缓存平台运维组 王远航

【适用范围】订单中心、用户中心、营销活动、风控服务等所有使用 Redis 作为缓存或计数存储的业务线，自建机房实例与云上实例均适用，使用版本覆盖 Redis 3.2 至 7.2

一、编制背景与治理目标

Redis 以单线程命令处理模型换来了极高的吞吐与稳定的亚毫秒延迟，但这个模型的另一面是任何一条慢命令都会让排在它后面的全部请求排队等待，因此键的体积与访问频次从系统设计之初就是决定线上稳定性的两个隐藏变量。过去一年平台侧共受理与大 key 直接相关的线上事件十四起，其中七起表现为核心接口毛刺性超时，四起表现为集群单节点内存倾斜引发的逐出风暴与慢查询堆积，三起发生在大集合删除时主线程阻塞超过一秒造成的批量请求失败，事后复盘认定其中九起完全可以在设计评审阶段通过本规范的量化标准提前暴露。基于这一背景，本规范将大 key 与热 key 的判定标准、扫描与发现手段、治理与拆分方案、删除操作的风险控制以及基于按频次淘汰策略的热点统计方案固化为强制要求，治理目标是将大 key 相关事件的发生频率压降到每季度不超过一起，同时保证任何一个新业务上线前其缓存设计中的体积风险与热点风险都有明确的评审结论。需要说明的是，本规范只覆盖键治理相关内容，集群扩缩容操作与哨兵故障转移的处置细则由对应兄弟文档另行规定，值班人员处理事件时不要在本规范中查找这两类操作的步骤。

大 key 与热 key 之所以要放在同一份规范里治理，是因为两者的危害链条经常交汇：一个大 key 如果同时是热 key，一次读取就是大包网络传输叠加高频访问，网卡出口被打满后同节点上所有业务的延迟都会抖动；而热 key 治理中常见的副本拆分手段如果用在一个本身体积超标的键上，等于把一次大读取放大成多次大读取，反而加剧问题。因此本规范要求所有治理动作在执行前必须同时核对两个维度：先确认键的体积是否越过红线，再确认键的访问频次是否构成热点，两个结论都拿到之后才能选择治理路径，任何只看单一维度就动手的治理都曾在历史上造成过二次事件。

二、大 Key 与热 Key 的判定标准

大 key 的判定指的是单个键的 value 体积或集合元素数量超过红线，而不是指键名本身很长，键名长度只影响少量内存占用，不构成稳定性风险。本规范给出的量化红线有三条：String 类型的 value 序列化后超过 10KB 即判定为大 key；Hash、List、Set、ZSet 四种集合类型的元素个数超过 5000 即判定为大 key；集合类型整体序列化后超过 1MB 的同样判定为大 key。三条满足任意一条即触发治理流程，不需要同时满足。之所以把 String 的红线定在 10KB 这个量级，是因为按线上实测，单条 value 超过一万字节后一次 GET 的网络传输与协议解析时间开始进入可观测区间，叠加每秒数千次的访问频次后对网卡的压力不再可以忽略；而集合元素条数的红线来自删除与过期环节的实际测量，五千个元素的一次同步删除在低配容器上已经可以观测到十毫秒级的主线程占用。这里需要提醒各业务线，部分监控厂商的宣传材料把大 key 红线放宽到 1MB 起步，那种标准适用于纯缓存场景的粗筛，我们作为交易链路的缓存提供方必须从严执行。

热 key 的判定指的是单位时间内访问频次异常集中的键，典型场景是秒杀商品详情、热搜词条、头部主播直播间状态。本规范给出的热 key 红线有两条：单键每秒访问次数超过 5000 次即判定为热 key；或者单键访问次数超过所在实例总访问次数的百分之三十即判定为热 key。第二条是比例标准，设计意图是捕捉低绝对量但高集中度的场景，比如一个平时每秒只有两百次访问的小实例，某个键独占了一百二十次，绝对量离红线很远，但该实例的负载已经完全被这个键主导，一旦它出现慢查询整个实例都会被拖住，同样必须纳入治理。两条红线同样是满足任意一条即触发。判定所用的访问频次数据一律以平台监控系统的分钟级聚合数据为准，业务方自行压测得出的频次数据可以作为参考但不得作为豁免依据。

两条红线之外存在灰区，即键的体积或频次处于红线值的百分之五十至一百之间的状态。灰区键不强制治理，但必须在容量月报中登记并标注增长趋势，连续两个月监测到灰区键的指标持续爬升的，第三个月起按超标处理。灰区登记的目的是避免治理动作的漏斗口收得太紧导致业务方疲于应付，同时又不让灰区键变成无人看管的定时炸弹。历史上有一类事件反复出现：键的体积在灰区徘徊了五个月无人关注，业务大促时流量翻倍，键的写入也翻倍，直接越过红线三倍，治理窗口完全错过，最终在大促中出事。灰区登记制度就是针对这类渐进式恶化的场景设立的。

三、扫描与发现手段

（一）例行在线巡检

线上发现大 key 的第一手段是 redis-cli 自带的采样扫描命令，执行 redis-cli --bigkeys -i 0.1 可以对全部键空间进行分片扫描并周期性输出各类型当前最大的键，其中参数 -i 0.1 表示每次 SCAN 循环之间休眠 0.1 秒，用来把扫描本身的 CPU 开销摊薄到更长的时间窗口里，降低对线上请求的影响。例行巡检固定安排在每周三凌晨两点到四点之间执行，由平台值班发起，巡检结果自动落库生成周报。使用这个命令必须清楚它的两个局限：第一，它只输出每种类型的最大一个键，也就是说每个数据类型只有一个 Top1 的信息量，覆盖面有限，一个有几百个九千元素集合的实例在报告里可能一个都不出现；第二，它对键的采样是 SCAN 分片遍历，类型统计有近似成分，数量级参考可以用，精确名单不能依赖它。因此 --bigkeys 的定位是例行的粗筛雷达，它的输出用于触发后续更精确的确认手段，而不是作为治理名单的最终来源。

（二）嫌疑键的精确测量

对巡检报告或业务方上报的嫌疑键，使用 memory usage 命令做精确确认，执行方式如 redis-cli memory usage user:10086:followers，返回该键连同其 value 实际占用的内存字节数，这个数字包含内联编码与序列化开销，是四类发现手段里最接近真实内存占用的。需要特别注意该命令的执行成本：memory usage 在大集合上执行时需要遍历集合的内部结构来累加每个元素的体积，一个百万元素的 Set 执行一次可能需要上百毫秒，因此平台明确规定该命令禁止在高峰期批量执行，确需批量核对的，统一安排在凌晨窗口并控制单批次数量不超过五十个键。值班人员曾经在大促当天下午收到业务方求助后直接对一批嫌疑键批量执行 memory usage，导致该实例出现持续两秒的慢命令堆积，事后被认定为一次操作不当引发的人为事件，这个教训写入规范：任何测量类命令本身也有成本，测量动作必须错峰。

（三）离线全量盘点

覆盖面最完整、对线上性能零影响的手段是 RDB 离线分析。Redis 的持久化机制会周期性生成 RDB 快照文件，将快照文件拷贝到离线分析机后，用 rdb-tools 或 redis-rdb-cli 工具对文件做全量解析，输出全部键的体积分布报告，报告内容包含键名、类型、元素个数、序列化字节数以及在各体积区间的分布直方图。全量盘点固定为每月一次，与容量月报合并发布。相比在线手段，离线盘点有两个不可替代的价值：其一是完整性，RDB 文件里每个键都被解析，不存在采样遗漏，历史上有三个最终造成线上事件的大 key 从未在任何一次 --bigkeys 巡检中出现过，全部是离线盘点首先发现的；其二是趋势可比，连续数月的盘点报告可以按业务维度对齐，键体积的月增长率一目了然，灰区键的登记数据也主要来源于此。离线盘点的限制在于数据时效，它反映的是最近一次快照时点的状态，快照之后新写入的键不在报告里，因此它不能替代周巡检，两种节奏必须并行执行。

（四）热 Key 的发现方式

热 key 的发现比大 key 更依赖工具配合，本规范认可三种方式。第一种是零成本的命令方式，开启按频次淘汰的策略后执行 redis-cli --hotkeys 即可输出当前访问频率最高的键及其频次统计，这个命令的输出直接来自该算法维护的每个键的访问计数器，代价是要求实例的 maxmemory-policy 必须配置为按频次淘汰的系列策略之一，如果实例当前使用的是 allkeys-lru 或 volatile-lru，--hotkeys 命令会直接报错退出，这是使用该方法的前置条件，也是很多值班人员第一次使用时踩到的坑。第二种是客户端 SDK 域名埋点，平台提供的增强版 SDK 会按采样率上报键访问日志到监控平台，聚合后可以得到任意时间窗的键访问排行，精确度最高，能区分业务维度，但要求业务方升级到指定 SDK 版本并显式开启，改造成本相对高，目前接入率约六成。第三种是代理层聚合分析，走自研 proxy 或 codis 架构的业务线可以直接在代理层对访问日志做流式聚合，不需要业务方做任何改造，但只覆盖经过代理的流量。三种方式的选用原则是：能埋点的业务线优先埋点，没有埋点能力的实例用热点键扫描参数兜底，代理架构业务线用代理日志补充，三者不是互斥关系而是分层互补关系。

四、治理与拆分方案

治理方案的选择取决于成因，平台将大 key 成因归为三类，分类施策。第一类成因是业务建模缺陷，典型如把一个千万粉丝用户的全部粉丝 ID 存进单个 Set，或者把一个游戏公会的全部成员列表挂在单个 Hash 上，这类键的体积是业务规模的自然投影，会随业务增长持续变大，单纯清理只能延缓不能根治，唯一正确的治理路径是拆分。第二类成因是数据生命周期失控，典型如用户画像 Hash 只增字段不删字段、任务队列 List 只进不出，数据本应被淘汰但没有人定义淘汰规则，治理路径是补齐过期策略或改造为有界的环形结构。第三类成因是数据放置位置错误，典型如把报表导出的超大文本、图片的 base64 编码串直接塞进 String，这类数据根本不适合进内存缓存，治理路径是整体迁移到对象存储，Redis 中只保留对象引用地址。三类成因的判别依据来自业务方的设计文档与键的实际访问模式分析，治理方案评审时必须先归因再选方案，归因错误的治理等于给错误的设计追加投资。

针对第一类成因的拆分方案是本规范的核心技术路径。拆分的基本手法是哈希取模分片：以粉丝列表为例，将原键 user:10086:followers 拆为 user:10086:followers:0 到 user:10086:followers:N 共 N 加一个子键，写入时按粉丝 ID 对分片数取模路由到对应子键，每个子键的元素个数控制在集合红线以内作为设计上限，读取时由客户端并行请求全部分片再内存聚合。分片数的选择必须在设计阶段按业务三年规模预估反推，宁可初期冗余也不要上线后二次拆分，二次拆分意味着又一次全量数据迁移。拆分改造的写入端与读取端必须同步上线，平台建议采用双写过渡：新逻辑写新键同时写旧键，读取仍走旧键，观察一个完整业务周期确认新键数据完整后，切换读取到新键，再观察一个周期后停止写旧键并择期清理，三步之间的每一步都必须有回退预案。曾经有业务线跳过双写直接切换，切换当天发现新键在过渡期间漏掉了两类写入路径，被迫紧急回切，这起事件让双写过渡从建议升级为强制。

针对第二类成因，治理路径围绕生命周期规则展开。补齐过期时间的操作在平台侧执行 SETEX 或 EXPIRE 即可完成，但执行前必须与业务方确认该键是否存在被多业务复用的情况，一个被复用的键一旦被单方面设置过期，另一个业务可能在毫不知情的情况下读到空值造成逻辑错误，确认流程要求业务方在治理工单中书面回复无复用或列出全部使用方并逐一确认。只增不减的画像类 Hash 推荐改造为固定容量的环形结构，写入超过容量后按插入顺序逐出最旧的字段，具体可以用 HLEN 配合 HDEL 实现，容量值按业务回溯窗口需求设定，平台见过从保留全量两年数据到只保留最近九十天的改造，单键内存从六百 MB 降到二十 MB。针对第三类成因的迁移，操作上先把对象写入对象存储拿到引用地址，再把引用地址以短字符串形式写回 Redis，读取端改为两跳访问，两跳路径的延迟预算需要在改造评审时重新核定，通常热路径上会再叠加本地缓存来吸收第一跳的延迟，这类改造的收益是 Redis 内存占用下降两个数量级，代价是读取链路复杂度上升，只适合非超热路径的数据。

所有治理动作在上线前必须经过预发环境演练，演练数据使用真实线上数据的脱敏副本，验证内容包括拆分后读写正确性、多字段聚合的完整性、并发读写下的一致性以及性能压测对比。演练通过后由业务方提变更工单，工单中必须写明治理方式、影响范围、分批批次、回退预案与观测指标，经缓存平台 SRE 评审通过后安排变更窗口执行。线上执行阶段强制要求分批操作：单批影响的键数量不超过该业务线键总量的百分之十，批次之间观察至少三十分钟的监控指标无异常再继续，出现延迟抖动或错误率上升立即停止并回退。治理完成一周内，平台对已治理键做专项复核，复核内容包括体积是否回到红线以内、访问模式是否发生预期变化、是否出现新的灰区键，复核结论回填治理台账。这套演练加审批加分批加复核的流程不是形式主义，它是从多起治理翻车事件中倒推出来的最小安全集，跳过任何一步的先例最终都付出了代价。

五、删除风险与非阻塞删除

大 key 的删除是治理流程中风险最集中的环节，原因在于删除命令本身就在主线程上执行同步回收。用 DEL 命令删除一个百万元素的集合，主线程需要遍历整个结构逐个释放节点，这个耗时与元素数量呈线性关系，实测一个两百万元素的 Set 在标配容器上的一次 DEL 耗时约八百毫秒，这八百毫秒内该实例上所有业务的所有请求都在排队。更危险的场景是键的被动过期触发同步删除，业务方以为设了过期时间就万事大吉，实际在旧版本上过期回收同样占用主线程，大集合过期瞬间造成的抖动经常被误判为网络问题。平台处置历史上最严重的一起删除事件是某业务在凌晨用 DEL 删一个三千万元素的 Hash，主线程阻塞长达九秒，期间该实例承载的三个业务全部超时，告警电话打到值班组时故障已经自愈，复盘时只留下慢日志里一条刺眼的记录。

规避删除阻塞的正确做法是使用 UNLINK 命令，这是 Redis 4.0 版本引入的异步删除命令。该命令与 DEL 的语义差别在于：DEL 在主线程里同步完成整个结构的释放，而它只在主线程里做引用摘除，即把键从键空间里移除并断开与 value 的关联，这一步是常数级开销，随后真正的内存回收被移交给后台线程池执行，主线程立即返回继续处理后续命令，业务请求完全感知不到回收过程。因此本规范强制要求：凡在 4.0 及以上版本的实例上执行删除，一律使用 UNLINK，禁止对任何体积或元素个数越过红线的键执行 DEL，平台侧已在命令审计规则中加入对 DEL 命令的参数拦截，命中拦截的命令会被拒绝执行并记录。需要注意该命令的后台回收同样消耗机器资源，对超大键的释放会让后台线程 CPU 短时打满，大批量删除时仍然需要控制节奏，单分钟内经该命令删除的大键数量不超过五个。

对于仍在 4.0 以下版本的存量实例，用不上这条非阻塞删除命令，替代方案是业务侧分批删除。以 Hash 为例，用 HSCAN 命令配合游标每次读出一批字段名，再对这批字段执行 HDEL，每批控制在两百个字段以内，批与批之间由脚本 sleep 两百毫秒，把删除的总耗时摊薄到数分钟的时间轴上，List 类型用 LPOP 或 LTRIM 每次截断一段，Set 类型用 SPOP 随机弹出，ZSet 用 ZREMRANGEBYRANK 按序删除，各类型都有对应的分批手法。分批删除脚本由平台提供模板，业务方不得自行编写未审核的删除脚本上线，历史上出现过自写脚本忘了加 sleep 导致分批退化为连续删除、也有 COUNT 参数误写大导致单批过重的案例，平台模板里这些参数已经固化。分批删除执行到只剩下最后几个字段时，可以直接 DEL 收尾，此时键的体积已经回到安全区间。

配置层面的最后一道保险是 lazyfree 系列开关。Redis 4.0 之后提供了 lazyfree-lazy-expire、lazyfree-lazy-eviction、lazyfree-lazy-server-del 三个参数，分别控制过期回收、内存逐出以及隐式删除场景是否走后台线程的释放路径，本规范要求全部生产实例设置 lazyfree-lazy-expire 为 yes，让键到期后的回收交给后台线程，这一条能消除前文所述大集合过期瞬间的抖动。lazyfree-lazy-server-del 建议同步开启，它覆盖的是 RENAME 等命令隐式删除目标键的场景。开启这些参数的代价是内存回收的完成时间不再确定，在内存水位极高的实例上可能出现回收速度赶不上分配速度的窗口，因此内存使用率长期高于百分之九十的实例在开启前需要先做内存治理，把水位降下来再开启，配置变更本身走标准变更流程执行。

六、LFU 热点统计与热 Key 治理

LFU 即 Least Frequently Used，最少频率使用淘汰算法，它在本规范中承担双重角色：既是容量不足时的逐出策略，也是热 key 统计的数据底座。它与传统 LRU 的区别在于排序依据，LRU 按最近访问时间淘汰，该策略按访问频率淘汰，为此每个键对象内部维护一个对数计数器，访问一次计数增加，长期不访问计数随时间衰减，这种设计让长期高频访问的键与偶发访问的键在计数上拉开差距。启用方式是将 maxmemory-policy 配置为 allkeys-lfu 或 volatile-lfu，前者对全部键生效，后者只对设置了过期时间的键生效。计数器的增长速度与衰减速率分别由 lfu-log-factor 与 lfu-decay-time 两个参数调节，平台统一使用默认值，业务线不得自行调整，因为参数一旦偏离默认值，热点键扫描的输出数据就与平台其他实例失去可比性。启用该策略的前置条件是实例内存确实存在逐出压力或业务方明确需要热点统计能力，纯全量缓存的实例按业务语义选择策略即可。

热 key 的治理核心思想是把集中访问的压力打散或下沉，平台认可三种方案并要求按场景组合。第一种是本地缓存兜底，在应用进程内用 Caffeine 之类的组件缓存热 key 的副本，过期时间设置两到五秒，让绝大多数高频读取在应用本地命中而不再穿透到 Redis，这个方案对秒杀商品详情类场景效果最好，注意本地副本的过期时间必须显著小于数据变更可容忍的延迟窗口，否则会出现改价后多副本不一致的业务投诉。第二种是键副本拆分，把热 Key 复制为带随机序号的多份副本键，读取端随机选择一个副本访问，把读压力均摊到多个键上，适用于读多写少的数据，写入时必须同步更新全部副本，副本数量通常取预期峰值 QPS 除以单键安全 QPS 再上取整。第三种是读写分离，把热 key 的读取分流到只读副本实例，写入仍走主实例，适合热点数据更新频率较低的场景。秒杀场景的标准搭配是本地缓存加键副本双保险，单靠任何一种都有失效窗口。所有热 key 治理方案在大促前必须完成压测验证，验证目标流量不低于预估峰值的一点二倍。

热 key 治理与大促保障流程强绑定。每次大促前一个月，平台发起热点风险盘点，业务方按预估流量圈出候选热 key 清单，清单中的键逐一核对治理状态，未治理的必须在两周内完成方案评审并排期实施。大促前两周的压测报告必须包含热 key 模拟测试环节，按预估流量模型放大访问候选热 key，验证本地缓存的命中率与副本拆分的压力均摊效果是否达到设计预期，未达标的热点方案必须返工。大促当天值班人员重点盯防热 key 监控面板，一旦出现单键 QPS 突破热 key 红线且本地缓存命中率下降的组合信号，按应急预案执行临时限流或降级，处置决策记录在值班日志中。大促结束后一周内复盘热点实测数据与预估的偏差，偏差超过百分之五十的项目要求业务方修订流量预估模型，连续两次预估严重失准的业务线将被要求引入流量预估评审环节。

七、流程保障与考核

大 key 治理纳入容量管理常规流程运转。新业务上线前，缓存设计文档必须包含键的体积预估与增长模型章节，评审时由缓存平台 SRE 出具体积风险意见，缺少该章节的设计文档不得进入评审通过状态。存量业务每月生成大 Key 报告，报告数据来自月度离线盘点加周巡检的组合，超过红线的键进入治理台账挂账跟踪，台账记录责任人、整改方案与承诺完成时间，超期未完成的台账项在部门月会上通报。治理完成的键在下月报告中专项复核，确认体积回到红线以内且访问模式正常，连续两个月复核通过的才能从台账销号，销号后六个月内复发同一问题的，治理方案评审人连带追责。灰区键的登记与趋势跟踪同样纳入台账管理，与超标键的区别仅在于处置紧迫度，台账中两类键分页展示防止混淆。

热 key 治理的常态化部分纳入容量月报，大促相关部分纳入大促保障流程。凡因大 key 或热 key 引发线上事件复盘时，必须回填本规范，具体动作包括：若事件暴露出红线标准的盲区，修订量化标准并同步全部业务线；若事件暴露出发现手段的漏洞，补强巡检频率或接入新的统计方式；若事件源于操作不当，将正确操作写入对应章节并评估是否需要平台侧的拦截规则。本规范的修订记录在文档头部维护，版本号按大版本加修订号递进，修订后的规范在部门周会上宣贯，宣贯记录由值班经理留存。各业务线的治理执行情况按季度汇总考核，考核指标为超标键存量的下降率与治理工单的按期完成率，两项指标计入业务线基础设施健康分。本规范自生效日起执行，此前按旧版规范判定与处置的存量问题，一律按本版红线重新对表，新旧标准差异导致新增的存量超标键给予一个月的宽限期，宽限期满后全部纳入考核。
