## 1. 总则

### 1.1 编制目的与适用范围

本手册用于规范公司生产环境 Java 应用的 JVM 内存与垃圾回收调优工作，覆盖内存布局与容量规划、GC 收集器选型与参数基线、大对象与 G1 专项调优、ZGC 特性与迁移评估、堆外内存定位以及容器环境专项六个方面，是应用性能组执行 JVM 参数变更与各业务线处理 GC 类问题的强制依据。本手册适用于 OpenJDK 11、17 与 21 三个 LTS 版本，收集器以 G1 为主、ZGC 为辅，仍在 JDK 8 上运行的应用按过渡条款执行并列入年度升级计划。CPU 飙高与线程栈分析等通用排查手段由故障排查手册承接，堆内对象占用的内存泄漏专项分析由对应专项文档承接，本手册聚焦调优与内存布局主题，跨主题场景请按文档索引转至对应手册。任何 JVM 参数变更必须走灰度加观察期流程：预发压测回归通过后按 1%、10%、50%、100% 四级放量，每级观察不少于一天，全量后总观察期七天，观察期内出现 GC 停顿超标或内存异常上涨的立即回退，回退动作不需要再次审批。

### 1.2 参数管理与职责分工

JVM 参数统一维护在应用发布模板中，禁止在发布脚本或代码仓库中散落硬编码，参数台账由应用性能组按月核对，与实际运行进程的启动参数（通过 jcmd 进程号 VM.flags 采集）做自动比对，漂移实例生成整改工单。业务线开发者可以发起调优申请并附上性能数据，参数的最终裁定权在应用性能组，未经裁定的参数改动即便来自资深开发者也一律不得上线。参数变更单必须包含四项内容：变更前后参数对照、预期收益的量化描述（如 P99 停顿从 300 毫秒降到 200 毫秒以内）、回滚参数串、观察指标清单与超标阈值。每次变更后的 GC 日志须归档保留 90 天，归档日志是后续同类问题分析的数据资产。应用性能组每季度发布 JVM 健康度报告，汇总全公司应用的停顿分位数、Full GC 次数、堆利用率的分布与趋势，健康度末位 10% 的应用列入重点治理清单，治理进度在季度性能会上评审。

## 2. 内存布局与容量规划

### 2.1 内存区域构成

JVM 进程的内存占用远不止堆，完整构成包括堆、元空间 Metaspace、线程栈、代码缓存、GC 自身开销、DirectBuffer 堆外直接内存以及 native 库的 malloc 分配，容量规划必须把这些区域整体纳入而不是只盯 Xmx。堆的大小遵循「初始值等于最大值」原则，即 Xms 与 Xmx 配置相同，避免运行期堆伸缩带来的停顿与页表反复调整；元空间按应用类规模显式设置 MaxMetaspaceSize，公司基线为普通业务应用 512MB，大量使用动态代理与脚本引擎的应用按实测加 30% 余量设置，不设上限的裸奔配置一律禁止，历史上未设限的 Metaspace 曾把容器内存吃穿触发系统层杀进程。线程栈通过 Xss 统一为 1MB，线程数超过两千的应用须单独评估栈内存总量（线程数乘以 Xss）并纳入容器内存预算。代码缓存由 ReservedCodeCacheSize 控制为 240MB 拆分模式，JIT 编译足够的场景维持默认即可。各区域之和加上堆外与安全余量即为进程 RSS 的合理水位，容量规划表的模板由应用性能组维护，新应用上线评审必填。

### 2.2 容量水位与容器占比

容器化应用的 JVM 必须感知 cgroup 内存限制，公司基线要求使用 MaxRAMPercentage 而不是硬编码 Xmx 来设定堆大小，标准值为 75.0，即堆占容器限额的 75%，剩余 25% 预留给元空间、线程栈、DirectBuffer 与 native 分配；重堆外应用（Netty 网关、大数据序列化类）下调到 65.0 并显式设置 MaxDirectMemorySize。UseContainerSupport 在 JDK 10 之后默认开启，升级存量应用时仍须在检查单中逐项确认，曾在一次 JDK 8 到 11 的升级中发现镜像未传参导致 JVM 按宿主机内存计算堆，容器内直接 OOMKilled 的案例，exit code 137 即容器运行时因超限杀进程的信号，与 JVM 自身的 OutOfMemoryError 是两类完全不同的事件：前者调堆占比或扩容器限额，后者按本手册第五章定位。堆利用率的管理目标为老年代在 Full GC（或 G1 的并发周期）后的占用不超过 70%，长期高于 80% 的应用进入扩堆或治理流程。每日巡检通过采集平台核对全量应用的 RSS 与容器限额比值，比值超过 92% 的应用生成 P3 预警并要求三天内出治理方案。

## 3. GC 收集器选型与参数基线

### 3.1 选型决策

收集器选型以延迟目标与堆规模为主要决策变量：绝大多数在线业务统一使用 G1，它是 JDK 11 之后事实上的默认收集器，平衡性最好；吞吐优先的离线计算与批处理应用使用 Parallel GC，其 STW 停顿可能达到数百毫秒以上但对总吞吐损耗最小；延迟目标为 P99 停顿 50 毫秒以内且堆规模 16GB 以上的大堆低延迟应用，评估迁移 ZGC（详见第五章）。CMS 已在 JDK 14 移除，仍在 JDK 8 上使用 CMS 的应用在升级计划中必须同步切换 G1，切换须完成预发压测回归。选型决策记录在应用的性能档案中，变更选型属于一级参数变更，须提供新旧收集器在同一压测模型下的对比数据，对比维度至少包含吞吐损失、停顿分位数（P50、P99、P999）与内存占用，仅凭「新收集器更先进」的理由不构成变更依据。混合部署场景下同一集群尽量统一收集器与堆配置，降低故障排查时的变量噪声，无法统一的须在应用档案中登记差异项。选型决策还要考虑版本约束：G1 在 JDK 17 之后有一系列堆自适应与停顿预测的增强，同样的参数在 11 与 17 上的表现可能差异明显，跨版本升级时收集器参数不能想当然平移，必须重跑压测回归；Parallel GC 的行为在 11 与 17 上基本稳定，适合对变更敏感度低的离线场景；ZGC 则建议只在 JDK 17 与 21 上评估，早期版本缺失分代能力会让吞吐回退放大到两位数。公司维护了一张版本与收集器的兼容矩阵，发布平台在选择基础镜像时会自动校验启动参数与矩阵的匹配性，不匹配的组合直接拦截发布，这个卡点曾拦下多次「镜像升级了、参数还停留在旧版本习惯」的发布申请，事后证明其中两次确实会在新版上产生预料外的停顿抖动。

### 3.2 G1 参数基线与停顿目标

G1 的公司参数基线为：-XX:+UseG1GC 配合 -XX:MaxGCPauseMillis=200 与 -XX:InitiatingHeapOccupancyPercent=45，堆大小按容量规划设定。MaxGCPauseMillis 是 G1 的软性停顿目标，G1 会自适应调整年轻代大小向该值逼近：停顿持续超标时收缩年轻代减少单次回收量，反之扩张年轻代提升吞吐，因此该值并非越小越好，设置为 50 毫秒以下会导致年轻代被压缩到过小、回收频率骤增反而拖累吞吐，在线业务统一 200 毫秒，延迟敏感业务放宽到 100 毫秒并在压测中验证。InitiatingHeapOccupancyPercent 触发并发标记周期的启动点，默认 45 表示整堆占用达到 45% 时开始并发标记，堆增长快（高分配速率）的应用可下调到 40 提前启动并发回收，为 Mixed GC 赢得时间窗，避免被迫 Full GC。G1 日志统一开启 -Xlog:gc*,gc+heap=debug（JDK 11+ 的统一日志格式），日志中的关键事件链为 Young GC、并发标记周期与 Mixed GC，日志按 50MB 滚动保留 10 个文件。任何 G1 参数调整都必须同时观察至少三个完整并发周期后再下结论，单次事件的最差值不作为调整依据，这是调优结论有效性的基本纪律。

## 4. 大对象与 G1 专项调优

### 4.1 Humongous 对象治理

G1 将堆划分为等大的 Region（堆 4GB 到 8GB 时默认 2MB 到 4MB），超过 Region 一半大小的对象即被判定为巨型对象类型，直接在老年代的连续 Region 中分配，这类大对象的治理是 G1 调优的独立专题。巨型对象的三大危害：分配需要寻找连续 Region，堆碎片化后即使总剩余空间充足也可能分配失败直接触发 Full GC；回收时机受并发标记周期约束，分配即入老年代意味着短命大对象也要活到下一个周期才被回收，大对象缓存类业务会显著推高老年代占用；一次数千个大对象的批量加载会在日志中形成成片的巨型对象分配事件，伴随 Region 快速消耗。治理的第一步是量化：统计 GC 日志中巨型对象分配事件的对象尺寸与频率，结合业务日志定位分配来源，典型来源包括一次性查询上万行的结果集、未分页的全量导出、把大文件读入内存的 byte 数组与超长 JSON 报文序列化。治理手段按优先级为：业务侧改分页流式处理（治本）、调大 G1HeapRegionSize 让对象落入普通分配路径（Region 上限 32MB，仅对中等大小对象有效）、对确实需要常驻的大缓冲考虑堆外化。Region 大小调整属于一级变更，调整后须重新统计巨型对象事件与停顿分位数的联动变化。

### 4.2 to-space exhausted 与晋升压力

G1 的 Mixed GC 期间出现 to-space exhausted 日志（或 JDK 11+ 的 Evacuation Failure 表述）意味着回收时晋升对象找不到足够的空 Region 接收，Evacuation 失败会直接触发 Full GC 兜底，是 G1 最典型的调优失败信号。成因有两类：一类是晋升速率超过回收速率，年轻代对象大批快速升代（常见于应用缓存预热、批量任务），老年代水位被推高到回收赶不上；另一类是预留空间不足，G1 在混合回收时要为晋升预留浮动空间， ReservePercent 默认 10%，突发晋升场景预留不足瞬间击穿。处置顺序为：先核对堆利用率与并发周期启动时机，IHOP 偏晚的先下调 InitiatingHeapOccupancyPercent 提前启动并发标记；仍有发生则上调 G1ReservePercent 到 15 或 20 增加预留；晋升速率确实超标的回到业务侧治理升代根因（存活周期误判、缓存未设上限）。该目标空间耗尽事件每发生一次即自动生成工单，同一应用周维度发生两次以上列入强制治理，治理期间该应用的参数冻结，禁止在未定位根因时通过反复调参试探。一次线上事故复盘可以说明纪律的必要性：某报表应用在促销期间连续三晚出现该错误，值班同学连续两次上调堆未果，最终定位是导出任务把两百万行数据一次性物化为对象数组，业务侧改为游标流式导出后事件归零，堆参数反而回退到基线。

### 4.3 G1 调优的标准动作

G1 调优遵循「先测量后动手」的固定动作序列：第一步采集压测或生产等比流量下的完整 GC 日志与分配速率画像（jstat -gcutil 或统一日志的增量计算），第二步对照基线定位偏差项（停顿分位数、并发周期频率、Mixed 回收效果、巨型对象事件），第三步每次只调整一个变量并跑完整压测回归，第四步以三个并发周期为最小观察窗口给出结论。禁止一次调整多个参数，多变量并调后无论变好变坏都无法归因，调优记录表的单变量字段是变更单的必填项。常见偏差的对照处置：Young GC 频率过高且单次极短，说明年轻代过小，检查是否被过激的停顿目标压缩；Mixed GC 后老年代回收比例低，检查并发周期是否被 IHOP 启动过晚压缩了窗口；停顿集中在 Remark 阶段，检查引用处理压力（弱引用大量使用会拉长 Remark）。所有调优结论沉淀回参数基线库，基线库每半年整体复审一次，复审时清理掉已被验证无效的历史参数并合并到公司统一模板。

## 5. ZGC 特性与迁移评估

### 5.1 核心特性与适用判断

ZGC 是面向大堆低延迟场景的收集器，其核心设计是通过染色指针技术在对象指针中直接携带 GC 元数据（标记、重定位等信息编码进指针的可用位），配合加载对象引用时的读屏障，使并发整理成为可能：几乎所有整理工作都与业务线程并发执行，STW 停顿稳定在 1 毫秒以内且与堆大小基本无关。这一特性的代价同样明确：读屏障带来持续的吞吐损失，综合压测显示相比 G1 吞吐下降约 5% 到 10%，并发整理需要更多内存余量（整理期间新旧副本并存），同样负载下内存占用高于 G1。因此适用判断为三个条件同时满足：延迟目标 P99 停顿 50 毫秒以内（G1 调优仍无法达标）、堆规模 16GB 以上（小堆场景 G1 停顿本就有限）、业务对吞吐 10% 量级的损失可接受。不满足条件的应用留在 G1 体系内优化，把 ZGC 当成万金油的迁移最终都会因为吞吐回退被业务方投诉。JDK 21 起默认启用分代模式（-XX:+ZGenerational），分代 ZGC 把年轻对象与老对象分区域管理，弥补了早期 ZGC 不分代导致短命对象也要经历并发整理的吞吐短板，实测吞吐损失从 10% 收窄到 5% 以内，公司迁移评估基线统一以 JDK 21 分代模式为参照。

### 5.2 迁移评估流程

ZGC 迁移按四步评估流程执行：第一步为可行性筛查，按 5.1 节的三条件打分，通过者进入评估池；第二步为预发压测回归，以生产等比流量在预发跑三轮 G1 与 ZGC 的对比（每轮不少于两小时），对比维度为停顿分位数、吞吐、CPU 使用率与 RSS 峰值，ZGenerational 模式下额外观察年轻代 Region 的分配速率；第三步为灰度放量，按 1%、10%、50%、100% 四级切换并各观察一天，重点核对接口 P99 延迟与错误率无劣化；第四步为全量后七天观察期，期间每日 GC 报告自动对比迁移前后基线。迁移决策的量化门槛为：P99 停顿改善不低于 50% 且吞吐劣化不超过 8%，两项同时达标才允许全量，任何一项不达标都终止迁移并回退。ZGC 参数集极简，公司基线仅设置 -XX:+UseZGC 与 -XX:+ZGenerational（JDK 21 显式声明以兼容后续版本演进）加统一日志，停顿目标类参数在 ZGC 下不再需要设置。迁移完成的应用在性能档案中登记收集器类型，后续所有调优动作按 ZGC 路径执行，G1 时代的参数（MaxGCPauseMillis、IHOP 等）必须彻底从启动串中清除，残留无效参数虽不报错但会干扰后续排障时的参数审计。

## 6. 堆外内存定位与 NMT

### 6.1 NMT 定位流程

当进程 RSS 显著超过 Xmx 与各非堆区域之和时，说明存在堆外内存增长，定位的第一工具是 JVM 内建的 NativeMemoryTracking 能力。开启方式为在启动参数追加 -XX:NativeMemoryTracking=summary，性能损耗实测在 5% 以内，公司基线允许在线业务常驻开启 summary 级别；detail 级别按需临时开启。采集命令为 jcmd 进程号 VM.native_memory summary，输出按类别拆分 JVM 原生内存：Java Heap、Class（类元数据）、Thread（线程栈）、Code（代码缓存）、GC（GC 自身开销）、Internal（含 DirectBuffer 记账）、Other 与 Symbol 等，每个类别给出已提交与已保留两级数值。定位流程为三步：第一步做基线快照，第二步间隔一段增长窗口后做第二次快照，第三步执行 jcmd 进程号 VM.native_memory baseline 后 diff 对比，直接看总量无法归因，只有两次快照的类别级增量才能指向问题区域。典型归因示例：Internal 类别增长对应 DirectBuffer 上涨，去核查 NIO 框架的缓冲池配置与 MaxDirectMemorySize；Thread 类别增长对应线程数上涨，核对线程池的水位与泄漏；GC 类别上涨在换大堆或换收集器后属预期。NMT 的边界也要清楚：它只记账 JVM 请求的内存，glibc malloc 的碎片与第三方 native 库（压缩、加解密库）的分配不在账内，NMT 各类别对不上 RSS 差额时，问题在 native 层，转入 6.2 节流程。

### 6.2 glibc 碎片与 jemalloc 替换

glibc 的 ptmalloc2 分配器在多线程长期运行的 Java 进程中容易产生内存碎片：free 后的内存长期驻留不归还操作系统，表现为 RSS 单调缓慢上涨而 NMT 各类别平稳，64 位进程的 arena 机制还会放大这一效应。确认碎片问题的方法为对比 /proc 下进程的 RSS 增长曲线与 NMT 总量曲线，两者剪刀差持续扩大且 pmap -x 输出中存在大量零散的小内存块映射，即为碎片特征。处置方案为用 jemalloc 替换默认分配器：通过 LD_PRELOAD 预加载该分配器动态库（如 LD_PRELOAD=/usr/lib/jemalloc.so），其按 size class 分桶的分配策略对长周期多线程进程碎片控制显著，公司多个网关与推送类应用替换后 RSS 峰值下降 20% 到 30% 且增长曲线走平。替换属一级变更，须在预发以等比流量验证功能无回归（个别依赖 glibc 行为的 native 库有兼容风险，须回归加密与压缩链路）并观察 RSS 曲线至少三天；容器环境的替换通过镜像基础层统一实施，替换开关记录在应用档案。同时配置该分配器的 prof.active 关闭以避免不必要开销，需要采样时再按需开启。替换后 30 天为观察期，RSS 曲线与容器限额比值纳入日报，确认稳定后变更单关闭。值得注意的是该分配器治理的是碎片而非泄漏，若 NMT 已明确指向某类别增长，应先治理对应问题而不是绕道换分配器，工具选择错位会掩盖真实根因，这是 6.1 节必须先于 6.2 节执行的原因。

## 7. 容器环境与变更管理

### 7.1 容器内存专项

容器内 JVM 的参数纪律有三条：第一，堆必须通过 MaxRAMPercentage 相对容器限额设定，禁止沿用物理机时代的绝对值 Xmx，镜像在不同规格节点混布时绝对值参数会反复超限；第二，堆外总量必须有显式边界，MaxDirectMemorySize 按业务实测加余量设置，未设限时 JVM 默认按堆等值预留，网关类应用曾在未设限状态下被 DirectBuffer 悄悄吃掉双倍内存；第三，容器限额要为非堆留足 25%，重堆外应用放宽到 35%，限额审批时应用性能组按 2.2 节规划表复核。OOMKilled 事件（容器退出码 137）的处置流程为：先从监控确认是堆内还是堆外驱动（RSS 曲线与堆使用曲线分离即堆外），堆内驱动按 OutOfMemoryError 类型分派到对应流程，堆外驱动按第六章 NMT 流程定位；处置完成后必须复核该应用的限额与占比基线是否合理，单纯扩限额而不修根因的处置不得超过两次，第三次起强制进入治理流程。每季度审计一次全量应用的容器限额与实际 RSS 峰值的比值，长期低于 50% 的缩限额释放资源，连续高于 85% 的扩限额或治理，审计结果同步到资源管理部门。

### 7.2 参数变更全流程管理

JVM 参数变更的完整流程为六个环节：申请（业务方或性能组发起并附性能数据）、评审（性能组裁定并出参数串）、预发（压测回归并留存报告）、灰度（四级放量）、观察（全量后七天）、归档（参数台账与 GC 日志入库存档）。台账系统记录每个应用当前生效的完整启动参数串及其变更历史，任何一次变更的历史都可回溯到变更单与压测报告。GC 日志按公司统一格式采集到分析平台，平台自动产出停顿分位数日曲线、并发周期频次与堆利用率热力图，这些看板是观察期内判断变更成败的统一依据，不采纳入为口述的「感觉变好了」。回退预案是变更单的必备项，回退参数串须事先验证可执行（预发回退演练），观察期触发的回退按预案直接执行再补记录。年度审计由应用性能组牵头，核对台账、实际进程参数与公司基线模板三方一致性，三方不一致的应用列入整改清单，整改完成率与各部门的变更合规率纳入年度运维质量报告，这份报告同时向技术委员会汇报，作为 JVM 基线演进（包括收集器换代与 JDK 升级节奏）的决策输入。
