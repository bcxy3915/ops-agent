## 术语与缩写

| 术语/缩写 | 说明 |
|-----------|------|
| upstream | Nginx 中定义的一组后端服务器，请求按策略转发至该组 |
| 被动健康检查 | 依赖真实请求失败计数摘除节点的检查机制，相对主动探活而言 |
| 四层拒绝 | TCP 层连接被拒的报错，区别于七层应用错误 |
| fullchain | 包含叶子证书与全部中间证书的完整证书链文件 |

| 429 | 限流触发后返回的标准 HTTP 状态码 |
| 峰值突发 | 瞬时流量超过平均速率的短时脉冲 |

## 1. 总则

### 1.1 系统定位与运维职责

公司生产入口流量全部经过四层负载均衡后再交给 Nginx 集群，当前共有十二台接入节点分三个机房部署，每台承载约三千 QPS，承担反向代理、TLS 终结、限流防护与静态资源分发职责。接入层是全公司故障传导的第一现场，任何后端服务的异常都会先在 Nginx 的错误日志与状态码分布上显形，因此值班人员对本文档的掌握程度直接决定故障定位速度。接入层运维组对 Nginx 配置实行统一模板管理，所有节点配置由配置中心渲染下发，禁止登录单台节点手工修改——历史事故复盘证明，单台手工改配置导致的配置漂移曾是入口层雪崩的第二大根因，二四年十月的节点不一致事件后，该纪律升级为强制要求，违反者按操作纪律条款追责。

### 1.2 变更纪律与红线

所有 Nginx 配置变更必须走统一流程：在配置仓库提交变更并经过同组人员 Code Review，随后由发布系统将配置渲染到灰度节点，先在灰度节点执行 `nginx -t` 语法校验并 reload，观察十分钟监控指标后再全量下发。三个绝对红线必须遵守：第一，任何情况下不允许跳过 nginx -t 直接 reload，语法错误会导致 reload 静默失败、节点配置停留在旧版本，造成集群配置不一致；第二，不允许在流量高峰时段（每日十点到十一点、二十点到二十一点）执行配置变更，除非是止血性质的应急变更且需值班经理批准；第三，limit 相关配置（限流区域定义与限流动作）的阈值调整必须提前一天在容量评审群公示，避免误伤正常业务引发批量 429 事故。

### 1.3 与兄弟文档的边界

本文档聚焦应用层运维，即"流量进来之后 Nginx 怎么转发、怎么保护、怎么留痕"，不展开两个专题：一是前述高并发系统级调优，二是四层负载均衡设备自身的运维。与后端服务健康治理相关的联动流程（服务降级、熔断策略归属）由各业务微服务手册约定，Nginx 侧只负责按 upstream 摘除策略执行被动隔离。值班人员在跨文档场景下应注意判断故障归属：四层负载均衡的告警转网络组，upstream 业务侧告警转服务负责人，Nginx 自身配置问题归本文档处置流程。

## 2. upstream 转发模型与健康检查

### 2.1 upstream 配置基线

upstream 是 Nginx 反向代理的核心概念，它把一组后端服务器抽象成一个命名集群，proxy_pass 将请求转发给该集群，再由选定的负载均衡策略决定具体落点。公司基线配置如下：负载均衡策略统一采用 least_conn（最少连接优先），比默认轮询更适应长短请求混合的场景；每个 server 节点必须显式声明 `max_fails=3 fail_timeout=30s`；长连接复用统一开启 `keepalive 64`；server 行禁止写死域名而必须使用内网 IP 加端口，若必须用域名则需配套 resolver 指令并使用变量写法，否则 Nginx 启动时解析失败会直接拒绝启动，这是批量节点宕机的经典诱因。基线样例如下，各业务可按需追加节点但不能删除参数：

```nginx
upstream order_servers {
    least_conn;
    server 10.0.20.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.20.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.20.13:8080 max_fails=3 fail_timeout=30s backup;
    keepalive 64;
}
```

### 2.2 被动健康检查的工作机制

开源版 Nginx 不具备主动健康检查能力（商业版的 health_check 指令才有），公司采用的替代机制是 max_fails 与 fail_timeout 组合的被动健康检查，其工作原理是：Nginx 把与后端建立连接、发送请求、读取响应各阶段中出现的失败（连接拒绝、超时、五零二/五零四类无效响应）计入该节点的失败计数，三十秒窗口内累计失败达到三次即把该节点临时摘除三十秒，期间请求全部落给其余健康节点。理解这套机制有两个运维要点：其一，摘除完全依赖真实业务流量驱动，低流量时段故障节点可能长时间不被摘除，因此凌晨发布出现问题时不能依赖"Nginx 会自动摘"的假设，必须人工介入；其二，被动计数重置意味着节点恢复后的第一个批次仍会被打入少量真实请求验证，若后端尚未真正恢复会出现短时二次失败，属于预期行为。节点全部不健康时 Nginx 依然会向不可用节点转发，因为`proxy_next_upstream`默认只对错误与超时做重试兜底，这会表现为入口大面积 502，处置见第三章。

### 2.3 upstream 长连接复用

默认情况下 Nginx 与后端使用短连接，每个请求完整经历 TCP 三次握手、请求、四次挥手，高 QPS 场景下后端会积累大量 TIME_WAIT 且 accept 队列被握手开销打满，P99 显著劣化。开启 keepalive 64 后，Nginx 为每个 worker 与后端维持最多六十四条空闲长连接，请求复用现有连接、消除握手成本。但这个配置有两个强依赖的前置条件：location 中必须同时声明 `proxy_http_version 1.1` 与 `proxy_set_header Connection ""`，缺失任何一条，客户端到 Nginx 是长连接、Nginx 到后端却依然是每请求一连接的短连接，且配置不报任何错误——静默无效是该陷阱的可怕之处，公司曾在压测中困惑"开了 keepalive 为什么后端 TIME_WAIT 不降"，根因正是漏了第二行。验收方法是统计后端 `ss -s` 输出中 estab 连接数与 TIME_WAIT 比例的变化，配置正确时 TIME_WAIT 占比应从百分之八十降到百分之二十以内。

## 3. upstream 故障排查

### 3.1 502 与 Connection refused 定位

502 Bad Gateway 意味着 Nginx 无法从 upstream 获得任何有效响应，是值班处置频率最高的入口告警。定位第一步永远是读 /var/log/nginx/error.log，报错串直接区分根因：`connect() failed (111: Connection refused) while connecting to upstream` 表示 TCP 握手阶段就被后端主机明确拒绝，四层层面无进程监听目标端口，即经典的连接被拒报错，指向后端进程未启动、端口配置不一致或监听地址写成了 127.0.0.1 而非 0.0.0.0；`connect() failed (110: Connection timed out)` 表示 SYN 包无响应，指向网络策略、安全组或后端主机宕机；`upstream prematurely closed connection` 表示连接已建立但后端中途断开，指向后端进程崩溃或中间设备强制回收连接。三种报错的处置路径完全不同，值班人员必须在十分钟内完成报错串归类，这是 502 分诊的硬性要求。

针对连接被拒报错的标准处置动作按序执行：先用 `ss -lntp | grep <端口>` 在后端主机确认监听状态，无监听则转后端服务负责人处理进程；有监听则对比 Nginx upstream 配置的端口与后端实际监听端口是否一致，公司历史上因服务容器化后端口从 8080 改为 8081 但 Nginx 配置未同步，出现过持续四十分钟的批量 502；若单节点异常则检查该节点发布状态。需要注意的特殊情形是后端 backlog 打满：SYN 队列溢出时握手同样失败、报错同样是连接被拒，区别在于 ss -s 中溢出计数增长，该情形说明后端处理能力不足，应扩容 upstream 节点或回调限流，而不是重启后端。

### 3.2 504 与分阶段计时

504 Gateway Timeout 表示连接与请求已送达后端但响应超时，处置前必须先回答"慢在哪里"。公司 access 日志的 log_format 中固定记录了三个分阶段变量：$upstream_connect_time 记录 TCP 建连耗时、$upstream_header_time 记录收到响应首字节耗时、$upstream_response_time 记录完整响应耗时。判读经验是：connect_time 高（超过一秒）说明建连阶段受阻，检查后端 accept 队列与网络往返；header_time 与 connect_time 差值大说明后端业务处理慢，问题在业务侧而不在接入层，此时调大 proxy_read_timeout 只是止血兜底，默认六十秒已足够宽松，无脑调大只会把故障从"快速失败"拖成"长时间堆积"，加剧雪崩风险。每周慢请求例会上，责任组按 $request_uri 聚合 P99 排名前十的接口推动优化，这是治理 504 的长效机制。

一个值得所有值班人员记住的 504 真实案例发生在二四年双十一前的全链路压测：入口 P99 突然劣化到四秒、504 放量，分阶段计时数据显示 connect_time 高达一点二秒，而正常基线是三毫秒以内。沿建连慢的线索追查，发现 upstream 中某一台后端发布了新版本、监听队列被打满导致握手排队，而 Nginx 的被动健康检查只在连接完全失败时计数、排队慢并不计入失败，所以节点始终未被摘除。这个案例固化了两条经验：分阶段计时必须成为日志基线，没有它这起故障会浪费数小时在"猜业务慢还是网络慢"的来回拉锯上；max_fails 只覆盖硬失败、软劣化要靠耗时告警兜底，公司此后把 connect_time 超过五百毫秒的占比纳入接入层告警项，软劣化类故障的平均定位时间从小时级压到了十分钟内。

### 3.3 499 与 413 的场景处置

499 是 Nginx 独有的状态码，表示客户端在 Nginx 将响应回传前主动断开连接，典型触发场景是用户刷新页面或客户端超时放弃。少量 499 无需处置；持续放量时它实际上是一个"用户体感变慢"的领先指标，说明响应速度已超出用户耐心阈值，应按 504 思路排查整体耗时分布并同步观察后端容量水位。413 Request Entity Too Large 则是请求体超过 client_max_body_size（默认仅 1M）的硬性拒绝，常见于文件上传与批量导入接口，处置方式是在对应 location 显式调大该指令并在配置仓库登记变更，注意全局与 location 的作用域优先级，曾有业务在 server 块调了 10m、却被 http 块的 1m 覆盖预期导致偶发 499 的疑难案例，最终通过作用域梳理解决。该指令带有安全属性（防恶意巨型请求），调大前需业务方在变更单中说明合理上限，禁止无上限放开。

## 4. 限流限连

### 4.1 limit_req_zone 声明与限流原理

Nginx 限流采用两级结构：http 块中用 limit_req_zone 声明限流区域（定义维度、内存与速率），location 中用 limit_req 动作引用该区域。公司对外 API 的基线声明为 `limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/s`，即以客户端二进制 IP 为键、每秒一百请求。两个参数的运维细节值得展开：其一，10m 的共享内存大约能容纳十六万个 IP 的状态记录，超出后按 LRU 淘汰，若公司出口流量中有大量 NAT 共享 IP，需评估同一键下多用户的叠加效应并适当放大速率或改用含会话头的复合键；其二，$binary_remote_addr 比 $remote_addr 节省约一半内存，是标准选择。区域声明属于全局配置、动作属于业务配置，两个层级由不同团队维护，新增业务接入限流时必须在配置仓库走需求单明确区域名与速率，禁止自建孤岛区域造成内存碎片。

### 4.2 burst 与 nodelay 的配合

rate 定义的是恒定速率，真实业务流量存在秒级脉冲，直接套用 rate 会把脉冲内合法请求错杀为 429。标准配置组合是 `limit_req zone=api_limit burst=200 nodelay`：burst=200 允许请求在桶内排队暂存最多二百个，配合该参数后排队请求不再按固定间隔延迟释放而是立即转发处理，整体语义变为"平稳期每秒一百、允许瞬时突发二百、超出部分返回 429"。未启用该参数时突发请求会被按 rate 间隔依次放行，用户端表现为大量请求排队等待数秒才被处理，体感极差，因此公司基线强制要求 burst 与该参数成对出现。限流命中默认返回 503，公司统一改为 `limit_req_status 429`，让客户端与监控能正确区分限流与后端故障；被限流的 IP 记录在 error.log 中，level=error、文案为 limiting requests，高频告警出现时先区分是"业务被恶意打"还是"正常流量增长撞线"，前者加黑名单或上调 WAF 策略，后者按容量流程评估上调速率。

### 4.3 连接数限制与组合防护

请求速率限制之外，单 IP 并发连接数限制由 limit_conn_zone 与 limit_conn 承担，基线为 `limit_conn addr 20`，防止单一源用长连接占满后端资源，与限流叠加形成双保险。需要强调的是 limit_conn 与 limit_req 的键都是 IP，在大量用户共享出口 IP 的场景下会产生误伤，此类业务必须提前报备并改用会话维度键。CC 攻击的完整防护组合是：WAF 侧按指纹封禁 + Nginx 限流限连兜底 + 地区级灰度放行，三层各自有独立阈值与告警，值班人员发现限流告警爆量时应同步拉取 WAF 攻击面板确认是否为攻击事件，并准备好与安全组的联动话术，这是接入层值班手册中唯一需要跨团队协同的高频场景。

## 5. HTTPS 证书管理

### 5.1 证书链完整性与中间环节缺失问题

证书链问题是最隐蔽的 HTTPS 故障：叶子证书单独部署后，多数现代浏览器因本地缓存与自动补链机制访问正常、仅地址栏提示非完全绿色，而部分严格校验的客户端（老版本 Java、移动端 App、内网安全设备）会直接报 unable to find valid certification path，形成"开发环境好好的、生产部分用户报错"的诡异现象，根因就是服务器只下发了叶子证书、缺失证书链的中间环节。完整信任链的构成是：终端内置的根证书（CA 机构在系统根库中）→ 中间证书（签发方与根之间的桥接）→ 叶子证书（域名证书），服务器必须把证书链的中间环节一并下发、客户端才能从叶子逐级回溯到受信根。二四年八月支付回调失败事故正是漏发证书链中间环节导致支付渠道侧校验失败，耗时六小时才定位，此后公司把证书链完整性检查列入上线前强制项。

### 5.2 完整证书链文件部署与验证方法

规范做法是部署时始终使用 fullchain 文件：将叶子证书与全部中间环节证书按"叶子在前、中间在后"的顺序拼接为一个文件（证书商一般直接提供完整链证书文件或 cert.pem 加 chain.pem），ssl_certificate 指令指向该完整文件，而不是仅指向叶子证书单文件。验证工作不依赖浏览器而是用 openssl：执行 `openssl s_client -connect <域名>:443 -servername <域名>` 后观察两个关键输出，一是 Certificate chain 段是否列出两到三级证书、二是 Verify return code 是否为 0，只要服务器正确下发中间环节证书、Verify return code 就应为 0；若链中只有一级且 return code 非 0，即为部署错误。另一个高频坑是 ssl_certificate 与私钥不匹配，部署后 reload 前用 `openssl x509 -noout -modulus -in <完整链证书文件> | openssl md5` 与私钥同法输出的 md5 比对，一致才允许 reload，该检查已内置在配置发布流水线中。OCSP Stapling（ssl_stapling on）的启用前提同样依赖完整证书链与 ssl_trusted_certificate 配置，链不完整时 stapling 会静默失败。

### 5.3 证书到期监控与应急续期

证书到期是可用性事故中"完全可以零成本预防却反复发生"的一类，公司基线要求三重防护：监控平台对证书剩余有效期分别设置三十天告警与七天告警，告警通道同时发值班群与责任人；证书管理责任人每月一号核对证书台账，台账记录每张证书的域名、签发方、到期日与部署节点；续期操作在到期前二十一天完成，禁止压哨。续期本身的标准流程是：签发新证书后按 5.2 节流程生成完整证书链文件、md5 比对私钥、灰度节点 reload、openssl 验证链、全量下发。应急场景（证书已过期、告警被漏掉）下，先用 ACME 签发临时证书止血、恢复主域名可用，再走正常续期流程，应急过程中的所有操作必须在两小时内补录变更单。历史数据显示二四年告警漏接事件百分之六十发生在节假日轮换期，因此节前检查清单将证书剩余有效期列为第一项。

## 6. 日志与监控

### 6.1 日志格式基线

公司 access 日志的 log_format 在基线上强制包含九个字段：$remote_addr、$time_local、$request_method、$request_uri、$status、$request_time（Nginx 处理总耗时）、$upstream_response_time（后端处理耗时）、$upstream_addr（实际命中的后端节点与端口）、$http_x_forwarded_for（真实客户端链路）。$upstream_addr 的价值是把"哪台后端在响应"落成可查证据，排查节点不均衡或单节点问题时能直接按该字段聚合统计；$upstream_response_time 支持多节点重试场景输出逗号分隔的多值，此时应取最后一个值参与统计，这是自研日志分析脚本必须处理的边界。error 日志的 level 公司统一为 error，降为 warn 曾在单日产生两百 GB 日志、挤占日志盘并错过关键事件，属于已复盘归档的操作教训。

### 6.2 慢请求分析与状态码巡检

每周例行巡检用 awk 对 access 日志做两类聚合：按接口聚合时取 `$upstream_response_time > 1` 的样本统计各 URI 的慢请求占比，输出前十名进入慢接口治理例会；按状态码聚合时统计 5xx 与 429 的时序分布，连续两周环比上升的域名需要值班组发起排查工单。日常值班对状态码的解读口径固定为：499 放量看整体耗时、429 看限流配置是否合理、502 看连接是否被拒还是其它错误、504 看分阶段计时，四个口径分别对应第三章的处置路径，不允许值班人员凭经验无依据猜测。日志本地保留七天，长期归档由日志平台采集，接入节点的日志盘水位告警阈值设为百分之八十。

### 6.3 监控指标与告警分级

接入层的核心监控指标包括：QPS 与带宽（容量水位）、5xx 比例（后端健康度）、429 计数（限流命中）、$upstream_response_time 的 P99（耗时健康度）、以及各 upstream 节点维度 QPS 是否均衡。stub_status 开放在内网管理端口，reading/writing/waiting 三个计数用于人工巡检连接分布。告警分级为：5xx 比例超过百分之一持续五分钟触发 P2、任一 upstream 节点被摘除触发 P2、证书剩余不足七天或全节点 5xx 超过百分之十触发 P1。所有告警必须在值班群以"指标名 + 当前值 + 已采取动作"三段式回报，未按格式回报的告警在复盘时按响应超时处理。

日志采集链路的可用性监控容易被忽视，值得单独立规。接入层的 access 日志由采集器（Filebeat/Vector）以尾部追踪方式发送到日志平台，采集链路断开时人工排查仍可登机读文件、但大盘与告警全部失明，等于监控半盲。基线要求两项保障：其一，采集延迟指标（采集器当前读取位置对应的时间戳与当前时间的差值）超过三十秒触发 P3 告警、超过五分钟触发 P2，值班人员按"登机验证 - 本地留档 - 修复回灌"三步处置；其二，日志盘满档保护，接入节点日志本地保留七天、满档时旧文件会被轮转删除，采集断开超过轮转周期就存在永久丢失风险，五分钟 P2 的响应时限正是按轮转周期倒推出来的。这两项保障在二四年四季度上线后，接入层日志断采的平均发现时间从人工翻日志的两小时缩短到告警触发的五分钟以内。

## 7. 变更管理与平滑发布

### 7.1 平滑 reload 与二进制升级

配置变更通过 `nginx -s reload` 生效，其原理是向 master 进程发送 HUP 信号，master 校验新配置后启动新 worker、向旧 worker 发送优雅退出信号，旧 worker 处理完存量连接后退出，全程不断连接。reload 的一个隐含风险是长连接不会强制中断，即持有长连接的旧配置 worker 会存活到连接自然断开，必要时需结合主动踢连接手段。二进制升级采用热替换流程：备份旧 nginx 可执行文件 → 覆盖新二进制 → `kill -USR2 <master pid>` 让新旧 master 并存 → `kill -WINCH <old master>` 平滑停旧 worker → 观察无误后 `kill -QUIT <old master>` 退出旧 master，任一阶段异常都可回退旧 master，全程流量无损。二进制升级每年最多两次，必须提前演练并逐节点滚动。

### 7.2 变更单据与复盘要求

所有接入层变更必须在配置中心创建变更单，写明变更内容、影响面、回退步骤与验证方法，灰度验证不少于十分钟、全量后观察不少于三十分钟。变更引发事故的复盘产出三件套：时间线还原、根因分析与本手册的对应章节修订，修订动作在事故关闭后五个工作日内完成。手册本身每季度评审一次，评审会由接入层值班组全员参加，对失效的参数基线与新增的运维场景做同步更新，保证本文档始终与生产实践一致。
